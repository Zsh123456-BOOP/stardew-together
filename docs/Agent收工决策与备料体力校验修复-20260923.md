## 问题与修复

上轮春1日09:40，模型看到500金、开放的种子店、0体力/约30分钟的到店候选，仍以体力12和昏倒风险否决采购。原 `SleepBlock` 实际仅检查理由长度，并未使用时间、体力、剩余工作参数。模型把采购与锄地浇水混为一体，执行前校验未发现矛盾。

- `DecisionReviewPolicy` 核对结构化取舍。`player.sleep` 与同样结束一天的 `agent.pause` 共用原生 ToolSpec；当前最多3项替代活动须逐项说明 `energy / time / low_value / defer`。若候选成本不超过当前体力或剩余时间，不能用对应条件不足排除它。允许明确的价值取舍和延期，不强制买种子或固定睡觉时间。
- 候选明确区分到店询价与后续购买/种植。建设立项等复合动作的0体力不被当成整个项目的0成本；没有报价时不虚构利润。仍使用现有行动耗时估算，不声称路线或收益保证。
- 检查依据放在常驻 `decision_review`，受上下文保护；详细拒绝与通过记录写 `decision_review`、`sleep_review` 事件。普通动作无需增加模型请求。睡觉入队本身不应使零体力候选消失，检查时忽略其自身占用。
- 玩家自主木/石/纤维/矿物等备料，须提供 `labor_review` 的材料用途、后续活动及明确 `reserve_stamina`。声称保留已承诺照料时，预留不得低于现有照料预算；选择推迟则须说明代价。总库存目标已满足时继续复用原来的不再劳动逻辑。已有目标依赖和原生任务采集保留各自的明确数量契约。
- 备料记录包括已有库存、批准目标、本次缺口、照料需求和不进食时的体力支出上限。总消耗取决于实际节点、工具与掉落，未观测的总成本标为未知；原生执行器逐动作核验预留，不把支出上限冒充预计成本。
- 连续3次评估拒绝且无实际进展时暂停并保留日志；文字变化、查询或时间流逝不清空计数。新日、原生进展或接受修正会重新计数。评估拒绝不写入禁止重试的世界失败条件，也不与通用执行失败计数重复处理。

这是一层事实一致性校验，不是完整的收益最优化算法。`low_value/defer` 的经济判断和文字解释仍由模型负责，不能据此宣称模型已具备可靠长期经营能力；新增契约的实际token开销也待日测日志统计。
