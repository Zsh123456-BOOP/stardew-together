# 连续任务与局部恢复修复

## 故障依据

上轮 a87f5d71b7b441028b955977fe06696e 的原生日志与实际 API 请求显示：53次决策，27株已种已浇，剩10金与146体力，19:40暂停，没有正常过夜。14:00模型说不买但提交24份；采购流程完成后仍反复被推荐询价；19:20砍木漏体力字段，加上两次收工时间理由矛盾，被共同累计为全局暂停。没有证据证明是模型看不到库存；候选生成、流程所有权和失败恢复也有程序缺陷。

## 本次实现

- 采购从 start_planning、planning、executing 到完成/受阻均持有玩家任务通道。正常任务运行时保留查询结果到空闲再交付，真实菜单选择与危险仍可唤醒。采购中的普通商店菜单不作为重新派工信号；同轮选种后的 buy/travel/work/plan.submit 不另建竞争玩家任务。
- 候选使用已观察价格、季节可收获性和库存核验购买能力；已评估/完成的投资不会因为播种改变株数、释放背包而再次推荐。新收入或新的一天可重新评估，显式工具仍可选择其他投资。未消费的当日报价可直接选种，无需返回商店重新询价。
- farm.plan 先核对实际未种库存，再提出移动要求；裸数字种子ID规范化。未买种子明确导向 farm.select_seeds 的完整采购播种流程。空选种只拒绝采购，不隐式启动另一轮自有种子规划。正数量但完全买不起时明确报错，不静默当作拒绝。
- 玩家自主备料缺省 reserve_stamina 按当前未完成农务预留，并将实际值传给执行器。显式预算保持原值；与照料承诺冲突则局部拒绝。用途可简述，特殊照料取舍仍可用原结构表达。
- 模型收工协议简化为 reason 与 defer 候选ID列表。成本由原生事实提供，不要求模型重新填写长篇估算；必须确认决定推迟的当前候选，不能不提剩余农务直接跳过。旧 alternatives 仅保留在运行时用于历史兼容，不再发送给模型。
- 收工/备料错误按动作与根因分别累计，不再写入全局停止原因；失败任务终止，其他工作继续。参数与计划类型错误按局部可修正错误处理，真正的原生证据/状态故障仍保留暂停。采集无目标的失败条件只在真实采集目标改变后释放，不因清了无关石头而忘记失败。

## 验证边界

674项域检查已通过（新增24项）。域检查覆盖上一轮的现金、预算缺项、三次不同错误、活动任务阶段、已有种子、过期候选和短收工协议。游戏Mod Release构建通过，0警告、0错误；接着进行只读原生启动预检。域检查与预检不能证明全天经营质量，更不能证明模型不会再产生推理错误。

本次没有更换模型、强制固定种植数量或规定睡觉时间。当前方案阻止程序主动反复推荐同一投资，不以自然语言理由推断/覆盖交易数量。判断、产出、重复查询和异常仍需这一天的日志验收。
