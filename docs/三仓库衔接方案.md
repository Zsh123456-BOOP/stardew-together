# 星露谷陪伴 Agent：三仓库源码审查与衔接方案

日期：2026-09-18。状态：三个仓库已克隆并固定版本；Squad 测试已按要求移除；本文件是源码审查结论和实施设计，尚未接通或在游戏里验证这三个 Mod。

后续实现更新：本文件保留初始源码审查快照。Squad 指定角色控制与 DeepSeek 人设闭环现已实测，当前实际完成范围见 `陪伴阶段A验收.md`、`陪伴阶段B验收与运行.md`；不代表三个上游 Mod 已原样合并。

## 1. 值不值得做，什么才算 Agent

能读取环境、根据目标作出决策、调用工具执行、观察结果并调整行动的系统，可以称为 Agent；底层采用确定性寻路和规则战斗，不影响这个定位。采用 LLM 也不自动意味着它有自主行为。

本项目定位为“基于真实游戏状态、有可配置人设和关系记忆的陪玩队友”。现有 Mod 已覆盖大量跟随、农务、战斗和 AI 聊天功能，重复这些功能的区别有限。真正需要验证的新增价值是：

1. 人设影响行动选择：爱钓鱼、怕矿洞，会自主提议活动，对指令接受、协商或拒绝。
2. 关系与承诺持续有效：记得“挖完三块矿就去钓鱼”，中断后还能履行。
3. 说话与行为一致：接受任务后确实执行；被阻挡、被打断或物资不足时如实报告。
4. 玩家可随时纠正：取消、改目标、要求跟随，以及明确选择强制执行。

这些是本项目的差异化目标，不代表已经证明市场上没有类似功能。只有组合安装三个 Mod，尚不足以证明完成了上述能力。

现有 Farmtronics 版本已经实测了非视觉读取、执行、回执和中断恢复；它是技术验证底座，尚未实现这里描述的自主陪伴。上层模型暂由 Codex 充当，不宣称已经有可独立运行的 LLM 服务。

## 3. 根据实际代码，三个项目分别取什么

| 项目 | 适合承接的部分 | 需要补的部分 |
| --- | --- | --- |
| Squad | 原版 NPC 招募、跟随、地图寻路、挖矿、战斗、动画、掉落收集 | 对外 API、指定 NPC 派工、每角色控制权、任务回执 |
| AI Dialogue | 聊天交互、人设字段、关系读取、记忆组织的参考 | 行为决策结构、可编辑人设、承诺状态、与 Squad 的唯一行动入口 |
| MCP | 工具定义、Agent 调用入口的参考 | 将工具调用路由到新桥接接口，返回任务 ID 和真实结果 |

游戏端继续 C#，模型决策和评估先用 Python。已有本地 HTTP 桥接可复用；MCP 作为可选外壳，不影响内部业务设计。第一轮不为复用 541 行 TS 服务引入另一个常驻进程。

### 3.1 Squad：能执行动作，但接口不符合我们的需求

审查入口（路径相对 Squad 仓库）：

| 文件／方法 | 当前行为 | 接入决策 |
| --- | --- | --- |
| `TheStardewSquad/ModEntry.cs` | 对外公开多个 Manager 属性，但没有覆盖 `GetApi()` | 设计窄接口 `ICompanionControl`，通过 SMAPI API 暴露；属性 public 不等于其他 Mod 已能获取实例 |
| `Framework/InteractionManager.cs:AssignManualTaskFor` | 接收玩家和地块，识别任务，选择最近的能执行的队友；返回 void | 不能直接用作“指定某人挖某矿”的稳定 API；补 actor、task type、结果字段 |
| `Framework/FollowerManager.cs:AssignTaskToMate` | 私有；处理占位、路径和任务切换 | 指定派工应走统一分配生命周期，避免直接写 `mate.Task` 漏掉占位清理 |
| `Framework/FollowerManager.cs:ClearMateTaskAndReset` | 清任务、路径、移动和动画状态 | 可作为停止动作的内部入口；停止生效后才回报 cancelled |
| `Framework/Tasks/UnifiedTaskManager.cs` | 根据全局任务模式和固定优先级自动选活；战斗可抢占 | 增加按角色过滤和控制权，保留快速战斗，不让 LLM 控制每次挥击 |
| `Framework/Squad/ISquadMate.cs`、`SquadManager.cs` | 当前 NPC、任务、路径、招募者等可读 | actor 使用存档、招募者 ID、NPC 内部名共同标识 |
| `Framework/Wrappers/MapInfoWrapper.cs` | 从游戏地图、物体和地形读通行状态 | 复用游戏状态，不接截图识别 |

上述 Framework 路径均在 `TheStardewSquad/` 下。

必须修正的能力边界：

- **钓鱼**：`TaskManager.ExecuteFishingTask` 主要处理姿势动画；`FollowerManager.OnPlayerCaughtFish` 在玩家钓到鱼时触发队友的概率收获。即使任务模式设为 Autonomous，也不能因此宣称实现了独立钓鱼产出。第一版只支持“陪玩家钓鱼”；真正独立钓鱼需要单独的等待、收获、结束状态机。
- **离开玩家远距离做事**：`UpdateSquadMember` 在有任务且离玩家超过约 15 格时会清任务追赶；不同地图也有跟随处理。因此先做玩家附近的陪伴，不承诺“玩家下矿，队友在另一张地图钓鱼”。
- **寻路**：`GenerateAndFollowPath` 存在 `StuckCounter > 20` 后传送回玩家的兜底。不能把这种恢复计为正常寻路成功；产品可显式记录 `recovery_warp`，严格寻路评测则应禁用并返回阻塞。
- **完成**：`mate.Task == null` 可能是完成、取消、目标失效、战斗抢占或追赶玩家；`ExecuteTask()` 的 bool 也不足以作为我们的完整结果协议。
- **物品**：使用 Squad 的实际物品归属逻辑（队伍库存／玩家库存及配置），不能沿用 Farmtronics 的“每个机器人独立背包”假设。记录拾取来源和物品变更，防止把玩家自己收集的矿算给队友。

### 3.2 AI Dialogue：取聊天和记忆，行动统一交给 Squad

路径相对 AI Dialogue 仓库，以下文件位于 `AIDialogueTestMod/`：

- `ModEntry.HandleActiveGenerationResult`：当前把模型返回的文字传给 `InvitationManager.HandleDialogueResult`，再显示对话。新流程在这里转为提交结构化意图，由统一控制层返回任务状态。
- `DialogueResponse.cs`：只有 Text、Options、OptionResponses；需增加 decision、候选技能、目标和承诺字段。不能靠“句子里看起来答应了”决定派工。
- `CharacterProfileRepository.InitializeProfiles`：人设写在 C# 中；我们改为独立 JSON 配置，支持兴趣、性格、主动程度、交流风格和自定义关系称呼。
- `AIDialogueManager.GatherGameContext`：读取原生友情点、约会、婚姻；作为关系事实来源。自定义“恋人”人设称呼不自动改写游戏婚姻状态。
- `DialogueMemoryManager.RecordImportantEvent`：是重要经历记忆的接入参考；任务执行证据应先存结构化事件，成功后才生成“已经一起做过”的记忆。
- `InvitationManager` 有自己的寻路与传送。配置中已有 `EnableInvitationActions`，集成时关闭原邀约行动，防止与 Squad 控制同一 NPC。

第一轮不启动 AI Dialogue 自己的模型请求链，再另外启动 Python 模型链；只保留一个决策入口。聊天 UI、人设和记忆是否直接复用源码，取决于后续可用许可；接口职责不依赖直接复制代码。

### 3.3 MCP：工具门面，不再生成第二套伙伴

`mcp-server/src/index.ts:sendAction` 当前写文件队列并返回 `Command sent.`。`smapi-mod/ModEntry.cs` 创建并每帧更新自己的 BotManager；这套角色和 Squad 招募的 NPC 不是同一对象。

因此不能把两个 Mod 原样运行，就期待 MCP 自动控制 Squad。设计为：工具 → 我们的命令桥接 → Squad 指定角色 API。停用原 MCP 的 BotManager、CompanionAI 和影子 Farmer 行动链。

我们的现有桥接已有认证、主线程处理、会话校验、命令 ID 去重、查询和取消，可继续使用。但 `IFarmtronicsControl`、bot ID、地图返回与动作语义都是 Farmtronics 特定的，需抽出通用控制协议，不能声称可以直接换 DLL。

## 4. 统一控制层设计（待实现）

```text
玩家聊天／地图变化／任务结束／一段时间空闲
                 ↓
Python：游戏状态摘要 + 人设 + 原生关系 + 承诺与经历
                 ↓
LLM：接受／协商／拒绝／自主提议，并选择可用技能
                 ↓
校验决策、角色与参数 → 分配任务 ID → C# CompanionAdapter
                 ↓
Squad：选目标、找站位、寻路、工具动作、快速战斗
                 ↓
实际状态和执行事件 → 核实结果 → 任务状态、对话、记忆
```

LLM 只选择目标；程序从地图枚举真实对象并提供候选 ID，避免模型编造坐标和物品。普通事件合并后再决策；战斗、卡住和跟随通过游戏端及时处理，网络等待不阻塞主线程。

建议新增 API，名称为本项目设计，不是上游现有能力：

| 接口 | 作用 |
| --- | --- |
| `GetCompanionState(actorId)` | 当前地图、任务、能力、原生关系、可用目标、控制权 |
| `StartTask(request)` | 指定角色、技能、范围和终止条件，返回 task ID 与 accepted/rejected |
| `GetTask(taskId)` | queued/running/paused/succeeded/failed/cancelled、原因、进度和证据 |
| `CancelTask(taskId)` | 请求停止，在动作安全边界确认 |
| `ReadEvents(afterSequence)` | 任务变更、地图切换、战斗抢占、拾取、角色离队等事件 |

返回 accepted 只代表通过派工校验；与人格层的 accept 以及执行 succeeded 分开。所有变更带 session ID 和幂等 ID；旧会话、重复提交和迟到模型响应都要明确处理。

示例：程序确认当前地图有可用矿石候选之后，模型才可能输出：

```json
{
  "decision": "negotiate",
  "speech": "陪你挖三块矿，然后一起去河边，好吗？",
  "proposal": {
    "skill": "mine_nearby",
    "target_filter": "copper_node",
    "max_targets": 3,
    "stay_near_player": true
  },
  "proposed_commitment": "完成后一起去河边"
}
```

协商不等于执行：玩家接受后才创建任务及承诺记录。强制执行由玩家显式操作设置，只跳过意愿拒绝，不绕过目标可达、角色能力和资源约束。模型不得自行把拒绝转换为强制。

### 控制权与状态管理

- 一个 NPC 同时只有一个任务所有者。原版日程由 Squad 招募／解散生命周期处理，AI Dialogue 不再写位置。
- 显式任务执行时阻止 Squad 自动选择无关劳动；紧急防御可抢占，保存高层目标，战斗后重新校验并恢复。
- `TasksEnabled=false` 是全局开关，也会影响自动战斗；不能把它当最终的每角色锁。第一版单 NPC 的局部验证可简化，正式适配应按角色过滤 `FindUnifiedTask`，保留必要 `FindAttackingTask`。
- LLM 不直接写好感值。先使用游戏原生关系及 Squad 的既有陪伴增长；新增关系变化由单一规则服务按事件限额更新，防止重复加分。
- 人设配置持久化；疲劳、心情等新增状态是我们自己的游戏机制，明确标注，不能当作原版 NPC 已有状态。
- 承诺有 proposed、accepted、in_progress、fulfilled、broken 状态；动作失败或中断不能记成 fulfilled。
- 记忆按存档、玩家、NPC 隔离；退出存档释放控制权并作废旧命令。

### 完成验证

| 技能 | 实际验收条件 |
| --- | --- |
| 跟随 | 在同一地图保持约定距离；取消／离队结束；不会瞬间标为永久完成 |
| 挖三块矿 | 目标被队友动作消除的事件累计达到 3；收集矿石数量另查真实掉落归属，不混淆节点数与矿石数 |
| 陪钓 | 队友到达合法钓位并进入陪钓状态；产出遵循目前玩家触发机制，结束需明确条件 |
| 保护玩家 | 一段时间或当前遭遇中执行有效防御；战斗结束后回到跟随或恢复被打断目标 |
| 自主提议 | 空闲时选择符合人设且当前可执行的活动，记录决策原因，拒绝或失败后不过度重复打扰 |

## 5. 最快接通的顺序

### A：单 NPC、单地图的确定性控制闭环

先通过 Squad 正常招募一个 NPC。补最小 API：读状态、对指定角色派一次挖矿任务、查询真实结果、取消后恢复跟随。暂不接聊天和人格。

推荐实现路径是给固定 Squad 本地实验版本补窄 `GetApi()`，让新增 C# CompanionAdapter 通过 SMAPI 获取它。需要触达现有私有分配生命周期时，在上游增加小型公开包装；不要到处反射写私有字段。上游正式提供 API 后再迁移为外部依赖。

验收：指定的 NPC 完成指定目标；玩家先完成目标时不能记成 NPC 贡献；无法到达时返回失败；取消后无残留占位。此阶段再进行隔离构建与游戏实测。

### B：人设决策与聊天衔接

增加可编辑的人设 JSON、结构化决策协议、关系快照、任务回执转对话。仍由 Codex 作为实际 LLM 发出决策，通过工具执行；不依赖尚未配置的模型 Key。

验收：同一请求在不同人设／情境下能合理接受、协商或拒绝；拒绝不派工；玩家强制后可派工；未完成时不会说“完成了”。

### C：事件触发的主动性与承诺恢复

新增空闲、地图变化、战斗结束、任务结束事件；有限自主选任务、冷却及记忆。先只在玩家附近行动；独立钓鱼产出、跨地图独自工作、多 NPC 协作单独排期。

验收示例：“怕矿洞但答应陪你挖三块矿” → 接受或协商 → 遇怪暂停 → 防御结束继续 → 三块完成 → 提醒约好的河边活动。通过后再接独立模型服务与 MCP 外壳。

每阶段实测通过后本地 Git commit。展示和简历分别说明上游提供的动作能力、本项目新增的决策／控制／验证能力，报告实际测得的成功率、人设一致性、打断恢复和模型调用量，不预填成绩。

## 6. 构建和复用边界

- 三个游戏端均为 .NET 6 C#，语言不是主要障碍。本轮没有构建或安装三个候选 Mod，源码可衔接不等于游戏内兼容已验证。
- Squad 使用 ModBuildConfig 4.4.0；`TheStardewSquad.csproj` 还有独立的 `DeployMods` AfterBuild 目标，仅检查 `GameModsPath` 非空，不能只传 `EnableModDeploy=false` 就认为不会部署。后续构建必须把 `GameModsPath` 显式指向项目隔离目录，或在构建副本移除该部署目标。
- AI Dialogue 的 csproj 硬编码 Windows GamePath、x64；Mac 游戏也是 x86_64，但构建时仍须覆盖游戏路径、核实引用。当前 Git 跟踪文件中未找到 `manifest.json`，需要补齐可加载打包清单，不能直接当作完整安装包。
- Squad 与 AI Dialogue 的固定源码树未发现明确许可证文件；MCP 的 LICENSE.txt 为 Apache-2.0，README 写 MIT，存在不一致。当前只完成本地源码研究和用户要求的测试移除；发布含第三方修改代码的包前需把复用授权核实清楚。尚未联系作者，也未发布第三方代码。
- 删除的是上游测试源码，不会因此提升游戏性能；目的仅为按用户要求精简本地源码。未来只为新增控制协议和关键场景保留必要验证，不恢复整套上游测试。
