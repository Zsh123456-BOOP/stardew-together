## 2. 根因复核

### R1：信息闭环——模型在盲飞（最严重，实测＋静态确认）

```
ContextCompression.cs:59–61   inventory_plan → {details_available_via:"world.read"}
AgentContext.cs:9             world.read     → {status:"observed", current_context:"…见实时经营状态"}
```

上下文说"详情问 `world.read`"，`world.read` 回答"详情见本轮上下文"。**闭环，模型永远拿不到真实背包。**

交接报告第 5 节的实测：12:30 那次请求，模型据此判断"12 空槽"，**实际 12 格全满**。

同样处理的还有 `day.read`、`day.plan`、`plan.read`、`progress.roadmap`（`AgentContext.cs:7–8`）——**模型能观察世界的主要入口全部返回指针而非数据。**

后果链：模型看不到真实状态 → 反复提交同一动作 → 14 次 `work.run` 被 `known_failure` 拒绝、5 次响应作废 → **压缩省下的 token 远小于空转浪费的 token。**

这是 R2–R4 之外所有"AI 显得笨"现象的共同放大器。**必须最先修。**

### R2：候选视野只有劳动（静态确认）

`OperatingOpportunities.cs` 共 47 行，产出 6 类候选：收获、浇水、读信、收机器、钓鱼、顺路采集一个。

**没有任何"获取能力"类候选**：接任务、采购、解锁、工具升级、背包扩容、查百科。

需要澄清一个误判：**钓鱼候选确实检查了鱼竿**（`player.Items.OfType<FishingRod>().Any()`）。所以"没鱼竿却出现钓鱼选项"不是候选产生的，而是模型绕过候选自行调用 `work.run goal=fish`。

**但用户的判断在更深一层成立**：系统没有把"缺某物 → 该物从哪来"表达成可执行候选。模型缺鱼竿时，看不到"鱼竿来自 Willy 的信/任务"这条路径，只能瞎试。

### R3：出行整备只管"带什么"，不管"卸什么"（实测＋静态确认）

`TaskPreparation.cs` 只处理 `loadout_missing`（缺工具材料）。**没有出行前按目的地卸载无关物品的逻辑。**

实测：春 2 钓鱼途中背着纤维/石头/煤/木材，第一次满包才往返农场，12:50 一次性存入 31 件全是与钓鱼无关的材料。

这直接贡献了运输时间和容量阻断。

### R4：没有途经机会拾取（静态确认）

唯一的拾取候选在 `OperatingOpportunities.cs:26–33`，限制为：仅在 `!committed`（没有在执行任务）时、`break` 只产出一个、路径 ≤12 格。

**执行任务途中经过可拾取物，不会拾取。**

### R5：容量恢复深度未复位（Codex 已定位，本轮阻断根因）

`InventoryWork.cs:151–152` 存货成功后清除 `ReliefAction`/`StorageTile`，**未把 `ReliefDepth` 复位为 0**；`SemanticWork.cs:249` 只为 `ChildKind==capacity_relief` 复位，仓库路径走 `storage_travel`/`storage_move` 不经过该分支。

后果：第二次独立满包被误判为嵌套递归 → 所有候选以 `relief_depth_limit` 排除 → `CapacityReliefRuntime.cs:98` 把这个**内部控制流错误写成物理容量约束**（版本 105）→ `GuardCapacity` 连存货本身也禁止 → 死锁。

**Codex 的修复方向我认可**：深度定义为"一次尚未完成的嵌套恢复链深度"，成功恢复并返回父任务即结束该链，新满包从深度 0 重新评估，保留上限 1。

**追加要求**：内部控制流错误**绝不允许**生成物理约束。`CapacityReliefRuntime.cs:98` 必须区分"候选物理不可行"与"因深度限制未评估"，后者不得写入 `CapacityConstraint`。

### R6：声明期失败不计数（Codex 已定位）

`RootFailureWatch` 只看有 `command_id` 的 `task_finished`；声明期拒绝只有 `tool_result`，全部漏计。实测第三次重复拒绝发生在春 2 15:10，观察者 18:30 才暂停。

**Codex 的方案我认可**：统一记录声明尝试与执行尝试的 `attempt_id`，两者均按 actor、根因、条件版本计数，满三次保存现场停止。**不得提高阈值来凑天数。**

## 3. 修复方案与优先级

| 编号 | 内容 | 依据 | 优先级 |
| --- | --- | --- | --- |
| **F1** | 修复信息闭环 | R1 | **P0，最先** |
| **F2** | 容量恢复深度生命周期 + 禁止内部错误污染物理约束 | R5 | **P0（本轮阻断）** |
| **F3** | 声明期失败计入重复监控 | R6 | **P0（本轮阻断）** |
| **F4** | 出行整备增加"卸载无关物品" | R3 | P1 |
| **F5** | 候选生成增加"获取能力"类 | R2 | P1 |
| **F6** | 途经机会拾取 | R4 | P2 |
| **F7** | 运输时间取证与归因 | 本文 §1 | P1（先取证，不猜） |

### F1：修复信息闭环（P0）

1. **压缩必须保留关键标量。** `inventory_plan` 被降级为指针时，必须保留：`slot_count`、`free_slots`、`occupied`、当前生效的容量约束及其解除条件。这些是标量，占用极小，**不允许被压缩掉**。
2. **按需查询必须真正返回所查信息。** `ModelToolObservation` 对 `world.read`/`day.read`/`plan.read`/`progress.roadmap` 的指针式替换，只有在**该信息确实完整存在于本轮上下文中**时才允许。若该字段已被 `ContextCompression` 降级，**必须返回真实数据**。

   实现建议：压缩时记录被降级的字段集合，`ModelToolObservation` 查阅该集合决定返回指针还是数据。两者共享同一事实来源，禁止各自判断。
3. **修完后重新测量 token。** 预期：单次输入可能上升，但因空转减少，总量应下降。**若总量上升且空转未减少，回来报告，不要自行加大压缩。**

### F2：容量恢复深度（P0）

按 Codex 方向实施，追加：`CapacityReliefRuntime.cs:98` 必须区分候选被排除的原因。因深度限制未评估的，**不得**写入 `CapacityConstraint`；只有实际模拟判定不可行的才能写入。

### F3：声明期失败计数（P0）

按 Codex 方向实施。`attempt_id` 统一，按 (actor, 根因, 条件版本) 计数，满三次保存现场停止。

### F4：出行整备增加卸载（P1）

出行计划生成时，除现有"缺什么"外，增加"带了什么不该带"：

- 目的地与目标已知 → 计算本次行程需要的物品类别（工具、饵料、预期产物空间）
- 背包中与本次行程无关、且非预留非任务物的材料 → **出发前一次性存入最近可达仓库**
- 复用 R-A1 的 `CapacityPlan.Simulate` 判断需要腾出多少
- **不改成"每个小动作前都回仓库"**——只在跨地图出行或预期产物明确时触发

### F5：候选生成增加"获取能力"类（P1）

`OperatingOpportunities` 增加以下候选类型，每类都必须带**真实可行性证据**，不可行就不产出：

| 候选类 | 触发条件 | 证据要求 |
| --- | --- | --- |
| 接任务 | 任务板有可接且条件满足的任务 | 已读取的真实任务 ID 与条件 |
| 采购 | 有现金、商店在营业时间、有已批准用途的缺口 | 现金、营业窗口、缺口来源 |
| 能力获取 | 缺少某工具/解锁，且存在已知获取路径 | 路径来源（邮件/任务/商店/制作） |
| 工具与背包升级 | 现金满足且当前容量或效率构成实际瓶颈 | 瓶颈证据（如近 N 次容量约束次数） |
| 百科查询 | 当前目标存在未解析的依赖 | 未解析的依赖项 |

**关键：** "缺鱼竿"必须能生成"获取鱼竿"的候选，而不是让模型去猜。这条链路（缺失物 → 获取路径）是本次 F5 的核心，不是可选项。

`progress.dependencies` 与 `knowledge.*` 已有能力，F5 主要是**把它们接进候选生成**，不是新建知识系统。

### F6：途经机会拾取（P2）

在既有路径执行过程中，对**已在路径相邻格**、容量允许、非保护的可拾取物，顺手拾取。

约束：
- 只对路径相邻格，**不得为拾取偏离路线**（偏离属于 R-B1 清障寻路，不在本轮）
- 必须通过 `CapacityPlan.Simulate` 校验
- 单次行程拾取次数设上限，避免走走停停
- 预留物与任务物保护规则不变

### F7：运输时间取证（P1，先取证再优化）

运输 56%/45% 是最大单项。但**清理目标选择用的是 BFS 就近优先**（`CleanupRouting.cs:17`，注释明确"stops at the nearest reachable work stand"），算法本身没有选远目标。

所以"走很远去清理"另有原因，**必须先取证再改**。要求报告：

- 按任务类型分解运输时间：跨地图 / 农场内 / 往返仓库 / 无效折返
- 每次跨地图出行的往返次数与原因
- 清理任务的实际目标序列与逐段路径长度
- 是否存在同地点工作未合并（去了又回、回了又去）

**取证结论出来之前不改动线算法。**
