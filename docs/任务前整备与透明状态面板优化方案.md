# 任务前整备、连续执行与透明状态面板优化方案

日期：2026-09-21。状态：已开始实施，逐项验证中；实施证据见《任务前整备与常驻面板实施记录》。

依据：用户本次优化要求；`阶段A阻断修复方案-容量模型与清障寻路.md`；`双身体陪玩架构方案.md`；最新原生证据 `work/capacity-baseline-3days-1/`。现有停止规则、D2/D5/D6、原生执行与阶段边界继续有效。本文提出的规则替换是待实施内容，不表示当前已有。

## 1. 结论与目标

采用“每个高层任务开始前自动检查装备和容量，需要时一次整备”的方式。不是每挥一次工具或每接一个任务都强制回仓。后一种做法会把容量停顿换成来回运输，尤其会打断在矿洞、商店或已准备好的农田里的工作。

玩家/模型决定做什么，程序决定本次带什么、存什么、去哪个已授权箱子、需要取多少材料。一次整备同时服务同一趟行程里的后续工作；容量足够且没有缺少必需物时直接开工。

新增右侧半透明面板，显示真实目标、决策理由摘要、当前动作、前置条件与阻碍。让用户知道角色是在劳动、运输、等待模型，还是已经卡住。面板不编造模型思考过程，不把聊天承诺当成行动完成。

## 2. 已确认问题与本轮范围

| 问题 | 当前证据 | 本次设计处理 |
| --- | --- | --- |
| 容量约束存在仍反复存货 | 同一版本 10 出现 9 次全候选不可行 | 对失败的整备路径也按事实版本记忆、派单前阻拦 |
| 有空位却要求先腾很多格 | 模型曾请求 5 个空格；部分模式默认 2 格 | 用本次操作序列替代无依据的格数指标 |
| 物品长期带在身上 | StoreCount 对工具、所有种子、大件、任务物统一排除 | 区分随身必需、此行需要、可安全入库；保护用途不等于必须随身 |
| 清理反复让路 | 任意其他未终结任务都可能触发让路 | 只给真正就绪、优先级更高且不依赖清理的任务让路 |
| 名为播种实际调用收获 | 本轮真实调用与零进展回执 | 生产目标绑定实际后置条件，零进展不能完成种植目标 |
| 动作间隔与真正掉帧混在一起 | 语义层 250ms 轮询；未有完整帧耗时归因 | 记录交接延迟与帧耗时，事件驱动续接，限制单 tick 开销 |
| NPC 说话却不劳动 | 阶段 A NativePlayerOnly 明确禁用派工 | 面板及措辞明确仅陪同，不提前开放阶段 B |

本轮不修改背包原生容量、不启用默认丢弃/出售、不改清障寻路、不迁移伙伴库存。右侧面板是阶段 A 的观测功能。

## 3. 统一的任务前整备流程

流程：接受目标 → 验证目标/参数/依赖 → 生成此行物资清单 → 容量模拟 → 必要时存取仓库 → 核验 → 执行原任务 → 核验真实进展。

### 3.1 先决定“此行”，再决定背包

以当前任务及已批准、依赖明确的连续任务为边界。例如“播种→浇水→收成熟作物”共同准备；未知的未来投资不计入。

物资分四类，分类由原生数据与已批准计划计算：

1. **必须随身**：当前/此行必用工具、明确的安全装备、获准使用的必要补给、必须随身且不能可靠转移的特殊物品。
2. **本次消耗与交付**：种子、肥料、加工原料、燃料、建筑材料、已承诺交付物；按实际批次及品质准备。
3. **此行产物**：已知品种/品质/数量，以及未知掉落。用于预测入包，不是假定物品已经获得。
4. **可入库物**：与此行无关的资源、其他季节种子、暂不用的设备、非必需工具等。仅在确认原生允许存取且之后能取回时转移。

任务物、献祭预留材料不能被消耗或出售；若原生允许存箱，可存入已授权且保持预留登记的箱子。遇到特殊物品无法确认是否能离身，保守留在身上并显示原因。不能再把“保护用途”和“永远不入库”当成同一规则。

### 3.2 哪些命令触发整备检查

| 高层任务 | 带什么 | 何时自动存取 |
| --- | --- | --- |
| 规划区清理、伐木、采石 | 本片区所需工具、批准补给 | 预测产物放不下时先卸无关货；同类材料仍可堆叠则继续 |
| 播种及照料 | 此田块种子/肥料、锄头、水壶 | 缺种肥先取；模拟清障→翻土→播种→浇水全过程；单纯种植会消耗种子，不因最后一格直接回仓 |
| 收获 | 实际成熟作物所需容量、后续已批准补种物资 | 按品种、品质和分批收获模拟；种类多且装不下才预先卸货 |
| 钓鱼、采集、下矿 | 相关工具/装备、鱼饵、批准补给 | 出发前清理无关货；途中按真实产物更新。未知掉落不能保证全部装下，保存可恢复位置并说明风险 |
| 动物照料/收产 | 必需工具、饲料、后续加工原料 | 单纯抚摸不要求空格；收产品按已知对象预测，缺饲料与工具才取货 |
| 机器投料/收货 | 本批输入、燃料 | 先模拟实际顺序；投料本身能腾格时直接投料，不先回仓 |
| 制作/烹饪 | 已批准配方的本批材料 | 按原生扣料→heldItem→入包模拟；材料被消耗后能腾格就直接制作 |
| 采购 | 获准预算、兑换物、行程必需物 | 模拟已批准购买清单及原生支付/入包顺序，必要时出发前卸货；临近关门需把整备耗时算进去 |
| 建造/升级/放置 | 已批准材料、设备、待升级工具 | 一次取齐必要物资；验证地点/营业时间；后续产物或升级工具回收空间也纳入计划 |
| 交任务/捐赠 | 已承诺交付物及返程所需物资 | 交付能腾格则直接做；领奖有产物时一并模拟，保护同 ID 不同品质物品 |
| 走路、聊天、查看百科、补水、睡觉 | 当前状态所需 | 不因动作本身自动回仓。收工整理是独立可选步骤，不得打断已经决定的返家过夜 |

这个表按物理操作能力分类，不为每个物品新增规则。新技能必须声明输入、可能输出、原生顺序和工具需求；没有声明的能力不能随便套“留两格”。

### 3.3 如何自动决定存什么

先固定本次必须带的物品，再计算可入库部分。优先转移能释放整个格子的无关物品；只转移半组但不腾格，通常对容量没有帮助。相关材料只携带所需量与明确的补给余量。

同一趟完成存入和取出。通过 `CapacityPlan` 同时模拟玩家与仓库的有序转移：仓库能接收多少才从玩家扣多少；需要先从箱子取出物品腾仓位时，也必须验证玩家的中间容量。不能分别计算后假定两个容器的交换必定可行。

选择仓库时考虑现有路线长度、绕行时间、是否能一次完成装卸、箱子剩余容量、锁状态及原生可达性。复用当前路径查询，不在本次加入挖开障碍的导航能力。已授权标记箱可自动操作，未授权的展示/收藏箱不擅自取放。

若容量足够：无缺料且不顺路就直接工作；路过同一服务点且确实能减少后续容量风险，可一次卸下无关货。不能为了“背包看着干净”绕远。

### 3.4 无箱子、箱满、材料不足

仍按深度最多 1 的腾格解析：检查可行生产消耗、现有仓储、已批准预算内扩容；全部不可行则输出具体阻碍，不递归修建箱子，也不反复重试 store。

造箱缺 48 木材时，不能在同一次腾格解析里递归采木。将缺口作为独立仓储前置项目交回经营计划；仅在已批准且当前容量/体力允许时执行。例如已有木材堆可再叠 48 木材，可以形成可执行方案，而不是把“无仓库”视为所有劳动都不可能。

同根因同事实版本的失败整备结果缓存复用；库存/仓库/授权用途等相关事实变化才重新解析。缓存需包含本次行程清单，新的真实物资需求可以重新评估，但换任务 ID 或改说法不解锁旧失败。监督器第三次观察到同根因重复实际失败时停机并保留证据。

## 4. 清理额度和连续执行调整

将“建设/种植必需清障”和“额外整理农场”区分。前者是项目本身的依赖，计入项目耗时与体力；后者使用必要农务之外的可用预算。

拟替换当前每日 30 目标、35% 体力、180 分钟和额外 20% 预留的叠加规则：以今天已批准的农务、返程、补给、营业截止为预算依据。额外清理有工作区域和实际终止条件，仍保留有限尝试、不可达保护等运行约束；不等于无限清图。

任务只在真正就绪且优先级更高的工作出现时于安全点让路。依赖当前清障的播种任务不能反过来抢占清障；让路保存父任务进度，不能把未清完的目标记成已完成。

普通动作成功后，用完成事件触发下一子动作；重扫描按区域变化增量更新。保留单 tick 运算预算、有限推进次数和原生动画约束，不能把 250ms 全部简单改成零造成主线程重循环。模型只处理需要新选择的情况，补给与续作不逐次调用。

记录 action_finished→next_started 延迟、等待模型时间、寻路/扫描/回执/渲染耗时；先量清楚停顿归因，再判断是否改善。零效果回执与目标完成分开：播种完成必须以原生作物、种子消耗及田块进度为证。

## 5. 右侧半透明状态面板

### 5.1 常驻内容

默认放右侧原生日期/金钱 HUD 下方，避开底部背包和体力条。宽约 280–340 UI 像素，随分辨率调整，可折叠、调整透明度；默认不抢键鼠焦点。窄屏或菜单打开时折成一行状态，避免遮挡原生菜单。

示意（演示数据，不是当前存档状态）：

```text
同行 · 正在整备
今日目标  种下 15 株防风草
选择理由  已有种子，先建立第一轮收入

当前步骤  去主仓库卸下无关资源
物资安排  留种子、锄头、水壶
          存石头、树液；预计释放 2 格
接下来    清理田块 → 翻土 → 播种 → 浇水
实际进度  播种 0/15

小禾      陪同中 · 本阶段未开放劳动
最近结果  已存入石头 12
```

遇到阻碍时示意：

```text
等待条件 · 暂停存货
没有已授权仓库；造箱还缺 48 木材
同一容量状态，不再重复存货
下一步待选  准备造箱材料 / 执行可行农务
```

第二个示例中的替代项只有经当前状态核验可行才出现；没有可行项就如实显示“暂无可行替代”，不提供虚假建议。

### 5.2 信息来源与可信度

- “选择理由”来自模型显式输出的简短决策说明，或程序的已记录规则解释；标识来源。
- “当前步骤/进度/最近结果”只读执行器、任务队列和原生回执。
- 区分计划、执行中、已验证完成、阻碍、等待模型、已暂停。计划用未来时，结果用已验证数量。
- 不显示模型内部推理链，不额外请求模型生成一段看似思考的文字；目标是可验证的决策摘要与执行轨迹。
- 阶段 A 明确 NPC 仅陪同，聊天不能声称自己已经砍树/收货。阶段 B 以后才展示真实伙伴独立任务。
- 折叠详情可查看最近数条决策/回执、任务 ID、容量版本和阻碍；日志用相同 ID 对齐，便于反馈。

### 5.3 渲染与性能

复用 `ModEntry.cs` 的 `RenderedHud`、现有 `Font`、`AutonomyPanelLines` 和任务状态源，不引入浏览器、外部 UI 框架或新模型调用。

更新线程生成轻量不可变显示快照，状态变化时更新；耗时与等待计时可低频刷新。Render 回调只绘制缓存文本，不扫地图、查库存、序列化完整状态或写文件。缓存换行/测量，限制事件条数，使用已有支持中文的字体，检查中文省略与窗口缩放。透明背景配清晰文本，不能透明到看不见。

## 6. 日志、验证和实施顺序

新增事件：整备需求/物资清单、每项保留或存入原因、仓库候选及排除原因、容量预测/原生实际差异、整备去重命中、子动作衔接延迟、业务完成证据、面板快照对应任务 ID。真实物品按 ID/品质/数量核验，私密凭据不入日志。

建议实施顺序：

1. 先补 R-A3 重复整备阻拦及监督器第三次停机；不依赖 UI 修复逻辑。
2. 接入纯任务物资清单与双容器容量模拟，复用现有原生存取、制作与仓储选址；所有纯域文件手写注册 csproj。
3. 接通行程整备、清障依赖、有效完成条件和事件续作；任何新增范围先以本文明确边界为准，不借机迁移阶段 B。
4. 同一轮加入右侧只读面板，真实状态与日志共用来源，静态示意不当成原生证明。
5. 集中原生验证：最后一格与可叠加满包继续劳动、无关工具/种子安全存取、两容器中间容量、仓库满/缺箱材料、同根因不重派、清理到播种不互相阻塞、卸货返回原任务、暂停续接、UI 中文/缩放/菜单遮挡与帧耗时。
6. 上述通过后，从独立起点重跑三天基线。G3 分布真实测量后再由用户定阈值；未确认前不启动十四天。十四天门槛和 G1/G2/G4 不降低，清障寻路仍排在闸门之后。

以上为原始设计。实施与尚未完成项以实施记录为准。取消无依据的空格预留不意味着无限背包；自动整备不意味着自动出售、销毁或升级背包。暂不加入丢弃策略。


## 7. 2026-09-21 面板反馈修订

按用户反馈，面板不再承载诊断输出：删除 JSON、完成证据、任务 ID、版本号、原始回执和错误码。只显示中文的目标、当前工作、下一步、简短安排说明，以及暂停/受阻原因。技术细节继续写日志。

默认半透明常驻；字号加大、高度随内容收缩，文字自动换行；滚轮仅在面板内生效，点击标题收起，原生菜单打开时自动收起。长内容滚动查看。界面显示的是明确的计划和执行状态，不是模型内部推理。
