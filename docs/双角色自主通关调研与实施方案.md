# DeepSeek 双角色自主游玩：调研与实施方案

日期：2026-09-19。状态：调研与实施设计，尚未新增玩家控制或正式睡觉工具。当前可运行版本仍为 Together 0.6，不能宣称已具备自主通关能力。

## 1. 新目标与角色选择

本阶段的核心目标改为：DeepSeek 自己读取游戏状态、检索百科、制定和调整计划、调用动作、核验结果、睡觉过夜并继续经营；逐步覆盖完整游戏与全部成就。人格、聊天与共同生活保留，先通过长程自主游玩验证底层能力。

用户已表示两种角色的具体形式以方便实现为准。采用 **玩家本体 Farmer + 一个 Squad 同行 NPC**，两者由同一个 DeepSeek 决策服务调度；不要求两个模型，也暂不引入第二个联机客户端。

同行 NPC 是存档中的村民，但不是联机玩家 Farmer。当前 `CompanionControl.GetCharacter` 返回 NPC，伙伴货物保存在本项目的队伍库存中；这不意味着 NPC 自动获得玩家的技能、配方、任务和成就身份。

| 角色 | 执行职责 | 进度归属 |
| --- | --- | --- |
| 玩家本体 | 全部必要原生操作，特别是制作、学习配方、放置、交付、献祭、购物、建造交互、剧情、小游戏、睡觉 | 按原生逻辑记入被控制玩家及存档；必须逐项验证 |
| 同行 NPC | 已适配的采集、农务、运输、战斗等协作劳动 | 分开记录行动者、物资去向与实际进度变化；不能把获得物品当作获得技能或完成成就 |

以后接管真实第二个 Farmer，可以扩展执行器；目前没有必要为证明单个存档的经营能力先承担联机同步、各玩家进度和睡觉表决等额外工作。

这是 Mod 辅助的状态驱动 Agent。它与纯视觉、按键输入基准的观察和动作条件不同，不能直接比较任务成功率。

## 2. 是否已有 AI 通关项目

检查了项目仓库、官方文档、论文和部分关键源文件。**在本次检索到的公开资料中，没有找到可核验的“LLM 从正常新档持续自主游玩，完成全部成就”的记录。** 这不是证明全网不存在；自动耕种演示、提供工具接口、给定初始资源的任务成功、全成就目标声明，也不等于已经完成全成就。

### StarDojo：玩家动作与任务评测的主要参考

[仓库](https://github.com/StarDojo2025/stardojo) · [项目论文与介绍](https://stardojo2025.github.io/stardojo/) · [动作接口](https://github.com/StarDojo2025/stardojo/blob/main/docs/docs_src/action_space.md)

提供 SMAPI 游戏环境、状态读取、动作接口和任务评测，包含移动、使用工具、制作、物品选择、菜单交互。论文介绍 1,000 项任务及 Lite-100 子集；其公开结果不能作为全成就通关证据。

对现在的目标，比只做 NPC 陪伴时更有价值：它有玩家操作层。选择性参考状态、菜单和动作实现，接入我们已有 C# 工具入口。原项目的视觉观测不是本项目的必要依赖。

源码注意事项：`StardojoMod/actions/Actions.cs` 的 `InteractWithBed` 直接调用 `Game1.NewDay(6f)`；不能据此声称已完成真实回家、上床和过夜结算流程。动作接口文档还注明 `navigate` 默认关闭。复用前逐项检查路径、原生消耗、统计和异步完成条件。[动作源码](https://github.com/StarDojo2025/stardojo/blob/main/StardojoMod/actions/Actions.cs)

### Orak：结构化状态与连续多日经营参考

[仓库](https://github.com/krafton-ai/Orak) · [星露谷环境](https://github.com/krafton-ai/Orak/blob/release/src/mcp_game_servers/stardew_valley/game/stardew_valley_env.py) · [安装说明](https://github.com/krafton-ai/Orak/blob/release/docs/setup_stardew_valley.md)

它的星露谷经营任务以春 14 日早上的资金衡量前 13 天的种植经营；支持结构化文字状态，适合参考多日计划与状态摘要。其设置包含特定初始存档和每日精力限制，不是原版完整通关结果。

现有星露谷安装说明仅支持 Windows，动作还依赖快捷键、固定坐标和部分传送；`go_house_and_sleep` 使用 H 热键回屋后按固定方向、时长和屏幕坐标操作。不能原样搬到我们 macOS、不同房屋布局、无视觉的正式 Mod 中。[技能实现](https://github.com/krafton-ai/Orak/blob/release/src/mcp_game_servers/stardew_valley/game/skills.py)

### SPIKE：规划、记忆、卡住后重规划的参考

[仓库](https://github.com/wencanjiang/SPIKE) · [论文](https://arxiv.org/html/2605.18636v1)

核心是低频战略规划、快速执行、事件触发重新思考及分层记忆。论文报告 StarDojo Lite-100 成功率 18.0%，另有不同预算口径的结果；这些数字是有限任务集成绩，不能解释成游戏完成百分比。其观察与记忆包含视觉和向量检索，直接整套接入不符合我们当前轻量、无视觉的方案。

本项目借鉴事件驱动的决策时机：新一天、任务结束、资源变化、路径失败、解锁变化时再调用 DeepSeek。执行中的移动、碰撞、挥工具和快速防御继续由 C# 处理。结构化事件与现有轻量记忆可先替代其复杂检索组件。

### Hunter-Thompson/stardew-mcp：直接控制玩家的轻量案例

[仓库及工具说明](https://github.com/Hunter-Thompson/stardew-mcp) · [执行源码](https://github.com/Hunter-Thompson/stardew-mcp/blob/main/mod/StardewMCP/CommandExecutor.cs)

与此前参考的 **amarisaster/StardewValley-MCP 是不同仓库**。它用 C# Mod + Go MCP 服务 + Copilot SDK，给模型状态/字符地图、A* 移动、工具、物品、交互和进门等接口，并运行自主循环。可参考玩家控制的接口粒度。

仓库同时公开了直接加钱、刷物品、瞬间成熟等作弊工具；工具数量不能当作正常游玩能力。没有找到全成就实测记录，本次也未确认该仓库的明确许可证，因此先参考接口，不能直接当可自由合并的源码。

### Stardew Checkup：只读验收参考，不是游玩 Agent

[仓库](https://github.com/MouseyPounds/stardew-checkup)

读取存档，检查成就、完美度、关系、姜岛等缺口。适合用作独立于 LLM 的结果核验参考，结合运行时真实事件，不以模型自己说完成为准。它的版本适配也需要核对；不能默认覆盖之后新增的所有机制。

上述 StarDojo、Orak、SPIKE、Stardew Checkup 仓库标明 MIT。未来实际移植代码时保留各自许可和署名；本轮仅调研，没有向本项目导入上游实现。

## 3. “通关”与“全部成就”的验收范围

定义三个分别记录的目标，后一个不会因前一个通过而自动通过：

1. **长期自主经营**：每天自己安排工作、分工、恢复失败、回家睡觉；有经营产出与持续进度，不靠原地等待或不断睡觉凑天数。
2. **存档 100% 完美度**：覆盖相关收集、制作、料理、关系、技能、怪物、建筑与姜岛目标；按实际游戏版本的数据逐项列缺口。
3. **平台全部成就**：在完美度之外，还包含草原王通关及不死亡挑战等要求；这些需要额外的小游戏状态与控制器，不能从主游戏战斗能力推定已支持。

社区中心完成与 Joja 完成是路线冲突，全部成就应使用“主档 + 独立另一条路线档”规划，分别保存证据；不能要求单档同时正常完成冲突路线，也不能修改完成标记补齐。[成就列表](https://stardewvalleywiki.com/Achievements) · [路线核验参考代码](https://github.com/MouseyPounds/stardew-checkup/blob/master/stardew-checkup.js)

开发存档通过不等于 Steam 成就已解锁。平台验收必须确认 Steam 正常连接，并分别报告原生存档进度与平台成就结果。旧 AgentLab 中的测试物资、跳转和条件设置不能冒充从零开始的完整游玩记录。

## 4. DeepSeek 的完整工具循环

```text
长期目标与实际进度缺口
  → DeepSeek 查询状态 / 地图 / 百科 / 原生可用交互
  → 建立计划并分派玩家、伙伴任务
  → C# 执行动作，持续报告任务 ID 与实际结果
  → DeepSeek 核对结果；失败则换路径、工具、时机或目标
  → 保存当日结果、未完成安排和下一日计划
  → 调用玩家回家睡觉工具
  → 原生结算与存档 → 新一天继续
```

改造现有“从少量候选活动中选一个”的调用方式，使模型能够连续调用只读工具，再执行动作，再读取结果。百科同时供模型主动检索和玩家查阅，维持现有结构化查询、名称/别名/模糊搜索，不引入 BM25 或向量服务。

每项任务区分 `actor_id`、原生操作身份、资源来源、消耗、物资接收者和目标进度。两个角色可以并行劳动，但同一机器、箱子物资、地块和玩家输入须有明确控制权，不能重复消耗或互相覆盖。

长期目标以结构化数据持久化；短期上下文仅包含当前计划、相关百科依据、近期失败与实际结果。失败重试设上限；模型调用按任务统计次数、token、费用与等待时间，避免无变化时反复询问模型。网络失败时保存待办，已有安全动作可以结束；不得编造新决策。

## 5. 正式睡觉工具设计

对模型开放 `player.return_home_and_sleep` 高层工具。内部必须完成以下状态机：

1. 读取当前日期、时刻、精力、玩家地图、真实房屋与床位置。
2. 收尾或暂停两个角色的任务，保留次日可恢复的目标；展示尚未完成的农务、季节风险和即将过期任务，供 DeepSeek 决定是否提前结束一天。
3. 沿真实可用出口返回住所；处理途中事件、地图变化和动态障碍。床由家具状态读取，不写死坐标、不任意传送。
4. 走到可用床位，触发原生交互并选择睡觉。
5. 正确处理过夜中的出货结算、升级和职业选择等界面；需要选择的内容返回给模型，不关闭后假装已经处理。
6. 等待原生保存和 `DayStarted`；核对日期推进、资金/出货/作物/机器变化与保存结果，才回报成功。
7. 保存失败、阻挡、超时或未知交互返回具体原因；重复请求不会再次多睡一天。退出重载后先核对存档日期和操作记录。

本地已有 `LabScenarios` 的 `bed` / `sleep` 仅是 AgentLab 测试便捷入口：包含传送到床、设置入床状态及调用原生睡觉应答。它没有完整返回路径、模型调用、连续夜间界面处理与幂等回执，不能直接换名字作为正式功能交付。

第一阶段仍为单机玩家 + NPC，因此由玩家睡觉推进世界；NPC 的“休息”动作不等于保存与过夜。如果将来换成真正的两个 Farmer，还须增加联机睡觉就绪同步。

## 6. 覆盖完整游戏的实施顺序

| 阶段 | 要交付的运行能力 | 通过标准 |
| --- | --- | --- |
| A：玩家执行与每日循环 | 玩家状态、地图、菜单、移动、基础工具、真实回家睡觉；DeepSeek 工具循环与玩家/伙伴分工 | 模型实际指挥双方劳动，完成一个生产循环并自行过夜、续接计划；包含阻塞恢复 |
| B：农场经营与生产 | 库存取放、制作/料理、放置、加工、采购、建造升级、种养和季节预算 | 从缺材料到真实获得并使用目标产物，正常扣资源，跨日持续经营 |
| C：完整世界与任务 | 下矿换层、装备/食物、战斗、各地点交通、献祭、博物馆、任务/特殊订单、剧情选择、姜岛 | 依赖链中的每个必要步骤都有真实接口和完成证据 |
| D：长期收集与成就 | 配方获取、全部相关收集、关系/家庭、节日、后期解锁、草原王小游戏、冲突路线档 | 逐项核对原生进度；明确未支持项，不用“其它成就”一项笼统代替 |
| E：持续自主验收 | 正常新档、模型全程决策、存档恢复、预算统计、无人工派工记录 | 持续运行直至对应验收目标完成；停留于 7 天或某个里程碑只能算阶段通过 |

“玩得好”同时记录收支、浪费/损失、种植是否来得及成熟、任务错过情况、恢复次数、人工干预次数及每日有效进度。伙伴互动另记录人格一致性、主动分享和承诺兑现，不能用成就数量代替朋友感评价。

当前缺口不止睡觉：0.6 尚缺完整玩家执行器、迭代工具调用与多类原生交互。先补最短的真实每日循环，再按成就依赖补全动作；不能只把全成就写进提示词就称为可完成。

## 8. 现有系统怎样控制 NPC

2026-09-19 再次核对实际调用链：

```text
游戏主线程读取真实状态、候选目标、已有安排
  → ModelClient.Ask 调用 DeepSeek
  → 返回结构化决策：选活动，或 1～3 步技能
  → Together 校验、创建 Job、选择真实目标
  → ICompanionControl.StartAction(actor_id, skill, target_id)
  → Squad 适配器寻路、动作、交互与资源处理
  → PollAction 返回实际结果
  → 更新任务、记忆、库存与心愿进度
```

证据入口：`mod/Together/ModEntry.cs` 的 `CompleteReply`、`Dispatch`、`Poll`；`LifeRuntime.cs` 的 `TickLife`、`StartOption`；`mod/SquadAdapter/CompanionControl.cs` 的 `StartAction`。

所以 NPC **已经由 AI 经接口控制**。NPC 的类型不妨碍成为 Agent，也不妨碍进一步扩展动作。目前有三个具体缺口：

- 技能范围有限，尚无完整玩家操作接口。原生任务身份与统计不能由伙伴动作默认继承。
- 模型自主活动主要选择 `OptionsFor` 提供的选项；玩家请求生成的技能计划也有固定范围。尚无模型自行交替调用状态、百科、动作与结果查询的通用持续循环。
- 百科已有检索问答、事实与心愿材料链，但它不是模型在一次长期执行中随时可以主动调用的工具。状态变化后的重新规划仍受现有各流程分别管理。

此外，`TickLife` 在无配置或额度耗尽时会按程序选项执行；模型错误也可能转为本地规则活动。正式 DeepSeek 能力评测要标记决策来源；离线时暂停新的高层决策，不能把规则接管的整段经营算作模型自主完成。寻路、碰撞、动画和基础战斗等确定性技能仍属于正常执行层。

## 9. 具体接入与迁移决定

| 来源 | 决定 | 实施方式 |
| --- | --- | --- |
| Together + Squad | 保留 | 继续作为 NPC 执行、百科、心愿、记忆与回执的主体 |
| StarDojo | 选择性移植或参考玩家端实现 | 优先检查菜单读取/选择、制作、工具交互；按本机原生语义改造成 `PlayerExecutor`。保留 MIT 署名，不带入调试设置、任意传送或直接改进度的接口 |
| SPIKE | 不整套迁移 | 在当前 C# 决策循环中实现“稳定执行时少调用；目标完成、失败、环境变化时重规划”；使用现有结构化记忆，不引入其视觉和向量检索依赖 |
| Hunter-Thompson/stardew-mcp | 参考接口设计 | 当前无明确许可证确认，暂不复制源码；无需新建 Go 服务或引入 Copilot SDK，继续直接接 DeepSeek |

MCP 是可选工具传输协议；实现模型调用工具不要求引入另一个 MCP 服务。模型看同一份工具注册表，内部由 C# 路由到玩家、NPC、知识与进度模块。

建议新增模块与工具名（以下均为拟议接口，不代表当前已可调用）：

| 模块 | 对模型开放的能力 | 内部职责 |
| --- | --- | --- |
| `AgentToolRegistry` | 列举当前支持的工具和参数 | 校验角色、参数、会话、预算和执行前置条件 |
| `WorldTools` | `world.read`、`map.read`、`inventory.read`、`menu.read` | 主线程读取有版本标识的真实状态，分页返回 |
| `KnowledgeTools` | `knowledge.search`、`knowledge.get`、`goal.requirements` | 接入现有百科、来源事实与材料计算 |
| `PlayerExecutor` | `player.move`、`player.interact`、`player.use_tool`、`menu.choose`、`player.sleep`，后续扩展制作等 | 原生玩家身份的持续操作，不直接设置成就或完成标记 |
| `CompanionExecutor` | `companion.assign`、`action.status`、`action.cancel` | 封装现有 Squad API，复用任务与目标占用检查 |
| `DeepSeekRunner` | 连续查询、行动、结果核验与计划更新 | 保存工具调用结果和未完成目标；异步请求模型，不从后台线程访问游戏对象 |
| `ProgressTracker` | `progress.read`、`progress.missing` | 从原生状态计算成就和阶段缺口，记录实际变化及归属 |

第一批实现按依赖顺序推进：统一工具与回执 → 玩家移动/交互 → 正式睡觉状态机 → DeepSeek 持续循环 → 两角色分工及跨日计划。接着覆盖生产、世界交互、进度与成就依赖，顺序见第 6 节。

第一组完整验收场景为：模型读取新档 → 查防风草种植条件 → 给两角色分配已支持的任务 → 种下真实种子并持续浇水 → 自行回家睡觉及处理夜间界面 → 次日重查天气和作物 → 成熟后收获、出货并核验收入。连续运行至少 7 个游戏日，且真实完成生产循环；仅过了 7 天不算通过。追加一次运行中退出重载和一次真实阻挡，核验未完成计划与恢复。

这只是全成就工程的第一个可验收里程碑，不是新的最终交付范围。后续每项能力完成再做阶段提交，最终仍须以正常存档的完整成就进度证明结果。
