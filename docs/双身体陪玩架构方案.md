# 双身体陪玩架构方案

日期：2026-09-20。本文是方案与方向决策，**不代表任何新功能已实现或已验收**。实施由 Codex 承接，验收标准见第 6 节。

关联：[统一经营内核重构实施方案与代码审查](./统一经营内核重构实施方案与代码审查.md)（A01–A16 缺陷仍然有效）、[四天开发运行复盘与优化结果](./四天开发运行复盘与优化结果.md)（本文的运行数据来源）、[自主通关开发方案与复用清单](./自主通关开发方案与复用清单.md)（全项目范围）。

本文**替代**上述文档中关于"AI 应该控制谁"的隐含假设。此前所有能力都长在玩家本体（`Game1.player`）上，本文改变这一点。

## 1. 目标与停止条件

**产品目标**：一个能陪玩家玩星露谷的 AI 伙伴。玩家正常操作自己的角色，AI 用自己的身体承担苦力劳动、备料、跑腿和陪伴互动。

**能力目标**：同一套能力内核在"接管模式"下能自主完成全部成就，以此证明能力不设上限。

**两者共享一套工具和决策内核，只有"当前行动者"指向不同。**

**红线（不可协商）**：

> **零伪造。** 不得向任何 Farmer 直接写入经验、配方、成就、金钱或统计计数。所有进度必须由原生动作产生。违反这条的实现一律不接受，即使它能让演示更好看。

这条红线是本方案存在的前提。第 3 节 D2 解释它如何与"玩家进度不能落后"共存。

### 2.5 可行性推算（待验证的外推）

全成就约需 2–3 个游戏年 ≈ 300 个游戏日。按当前 40 次/天推算：

- 模型调用约 12,000 次，输入 token 约 1.1 亿。**按 DeepSeek 价位不构成瓶颈。**

## 3. 核心决策

### D1：两个身体

AI 伙伴同时拥有两个实体，每帧同步：

| | 可见身体 | 隐形身体 |
| --- | --- | --- |
| 类型 | `NPC`（沿用现有小禾 / Squad） | `BotFarmer : Farmer` |
| 职责 | 外观、导航、玩家可走近对话、村民反应 | 背包、体力、工具、制作、技能 |
| 现有资产 | Squad 全套寻路/跟随/任务体系保留 | Farmtronics `BotFarmer` 可参考 |

**理由**：`NPC` 永远无法获得真背包、真体力和原生制作；`Farmer` 无法被玩家按 E 对话、不被村民感知、且会废弃 Squad 已有的导航投入。两者不是二选一。

**外观不改变**：玩家看到的仍是现在的小禾。

**代价（待验证）**：两个实体的位置、朝向、`currentLocation` 必须严格同步。不同步会出现"人在这里、工具作用在那里"。物品交接必须守恒，不得在两个背包之间丢失。

### D2：归属零伪造，按"产物类 / 行为类"分工

星露谷的进度按 Farmer 存储。AI 若用自己的身体劳动，其经验、配方、图鉴归它自己，玩家会被锁死（例如采矿等级不足则玩家造不出熔炉）。

**但绝大多数耗时劳动不产生独占归属**：

| 类别 | 内容 | 归属处理 |
| --- | --- | --- |
| **产物类** | 砍树得木材、挖矿得矿石、浇水促生长、照料动物、机器投料收货、搬运、备料、跑腿 | AI 执行，产物交给玩家；玩家出货或使用时，**归属天然是玩家的，无需任何转记** |
| **行为类** | 钓鱼图鉴计数、烹饪计数、制作计数、技能经验 | **必须玩家本人执行**。AI 负责备料、选点、开路、陪同 |

**已确认接受**：行为类由玩家自己做。**不实现任何经验/配方/成就的转记。**

现有代码已有这个概念的雏形：`FarmerHarvestCreditNeeded()`，以及工具描述中"任务原生计入玩家的步骤由 Farmer 执行"、"NPC货物不等价"。本方案要求把它提升为贯穿全局的显式规则。

**落地要求**：每个工具必须声明它属于产物类还是行为类。行为类工具在陪玩模式下不得由 AI 身体执行，只能生成"请玩家来做这一步"的提示或队列项。

### D3：两种模式共享同一内核

| | 当前行动者 | 玩家能同时玩 | 归属 | 用途 |
| --- | --- | --- | --- | --- |
| **陪玩模式**（主产品） | AI = NPC + 隐形 Farmer；玩家 = 自己 | ✅ | 100% 原生，靠 D2 分工 | 日常游玩 |
| **接管模式**（能力证明） | AI = `Game1.player` | ❌ | 100% 原生 | 冲全成就、挂机 |

同一套 138 个工具、同一个决策内核。差别只在"当前行动者"指向谁。

**全成就在接管模式下完成，不打折、不伪造。陪玩产品在陪玩模式下交付，玩家进度不被锁死。**

### D4：授权层 `CompanionCharter`

不做三套智能。做**一个满血内核 + 一层授权配置**。

```
授权域：农务 / 采集 / 加工 / 采购 / 建造 / 战斗 / 社交 / 剧情首次解锁
归属策略：产物类自动 | 行为类保留给玩家（默认）
主动性：0–100    表达度：0–100    人格：Profile
```

用户提出的三档由预设值实现：

| 档位 | 授权域 | 主动性 | 表达度 |
| --- | --- | --- | --- |
| 高级智能 | 全开 | 高 | 高 |
| 简单智能 | 仅重复劳动，首次解锁/剧情/探索留给玩家 | 中 | 高 |
| 工具人 | 仅劳动 | 低 | 关 |

现有散落的边界机制应收敛到这一层：`farm.zones` 分区保护、`progress.pursue` 的 targets 白名单、`day.routine` 分工表、`Profile.Preset`（已有 5 档人格）、`Temperament`（已有 5 维数值）。

### D5：作用域优先，不依赖 `who` 参数（2026-09-21 由阶段 0 穿刺确立）

**依据**：[双身体阶段0穿刺报告](./双身体阶段0穿刺报告.md)。穿刺 B 通过，穿刺 A 在拾取处失败，两者的差别恰好证明了这条原则。

- 穿刺 B 把**整段原生制作（含菜单构造）**放进 `ActingFarmer.As(bot)` 作用域 → 通过。材料从隐形 Farmer 扣除、箱子进其背包、制作计数记在它头上，玩家的背包和全部计数**零变化**。
- 穿刺 A 用 `Axe.DoFunction(..., bot)` 传 `who` 参数砍树 → 砍树成功；但随后 `Debris.collect(bot, chunk)` → `Farmer.addItemToInventoryBool` → `if (IsLocalPlayer)` 门槛 → 返回 false。`IsLocalPlayer` 比较自身与 `Game1.player.UniqueMultiplayerID`（原生 `Farmer.cs:1877`），作用域外两者不同。

**结论**：原生 API 对"行动者"的处理不统一——有的尊重 `who` 参数，有的直接比对 `Game1.player`。逐个审计哪个是哪个既昂贵又不可靠。

> **原则：一切需要"以某个 Farmer 身份执行"的原生调用，默认放进 `ActingFarmer` 作用域，不依赖传 `who` 参数。**

这条原则让方案更简单而非更难：它正是"那 760 处 `Game1.player` 不需要重写"能够成立的原因。

**作用域粒度规则**（与第 5 节约束 2 的单 tick 纪律并存）：

- 作用域包裹的是**单个原子原生调用**（一次挥斧、一次拾取、一次制作），不是整段劳动流程。
- 跨 tick 的部分（寻路、走动、等待动画）在作用域**之外**，由 NPC 身体和现有 Squad 导航负责。
- 禁止把一整段"走过去→砍→捡→走回来"包在一个作用域里——那必然跨帧，违反纪律。

**已知的连带效果（符合 D2，不是缺陷）**：在作用域内劳动，原生经验与统计（如 `Tree.performTreeFall` 的伐木经验、`TreesChopped`）会记在隐形 Farmer 身上。这正是 D2 期望的——AI 的技能是 AI 自己的，产物才交给玩家。副作用是 AI 会在自己承担的劳动上真实变强，属于正向。

**仍待验证**：穿刺报告 5.1 节列出了一份从原生反编译代码中静态确认的 `Game1.player` 隐式依赖清单（制作菜单、配方原料消耗、成就检查、烹饪分支等）。B 只实测覆盖了箱子制作实际走过的分支。**该清单是后续每类能力迁移时的必查表，不是已验证通过的证明。**

### D6：伙伴库存的唯一真相是 `BotFarmer.Items`（2026-09-21 由第二次穿刺确立）

**依据**：穿刺 A 第二次尝试暴露了两条拾取控制路径的冲突。Squad 的 `DebrisCollector`（`external/the-stardew-squad/TheStardewSquad/Framework/DebrisCollector.cs`）通过 `HarmonyPatches.Debris_UpdateChunks_Prefix` 拦截 NPC 附近掉落，吸向 NPC 后写入公共箱 `TheStardewSquad_SquadInventory_<玩家ID>`，并**删除整个 debris**。Together 探针因此扫不到它。

**冲突本质**：伙伴同时存在两个候选库存，而它们不可能都是真相。

| | Squad `SquadInventory`（货袋） | 隐形 `BotFarmer.Items` |
| --- | --- | --- |
| 形态 | 共享箱，非每伙伴独立 | 每伙伴 36 格真实背包 |
| 原生堆叠/容量规则 | 箱子规则 | Farmer 规则 |
| **能否用于原生制作/烹饪** | **否** | **是**（穿刺 B 已实测） |
| 现有工具依赖 | `work.run withdraw`、`CompanionControl.CargoAccept`、容量与交接链 | 无 |

原生制作从 `Game1.player.Items` 扣料（穿刺报告 5.1 节 `CraftingRecipe.cs:280–286`，无显式 `who` 参数）。在作用域内，这就是 `BotFarmer.Items`。**材料若落进 Squad 货袋，伙伴永远无法用它制作。**

> **决策：`BotFarmer.Items` 是伙伴库存的唯一真相。Squad 的自动采集与货袋写入对受管伙伴一律关闭。**

**迁移归属**：`work.run withdraw`、货袋容量计算、`CompanionControl.CargoAccept`、存取货交接链指向新库存——**属于阶段 B，不在阶段 0 范围内**。

**阶段 0 只需做到**：让受管伙伴不被 Squad 自动采集器接管，使作用域内拾取路径能获得一次干净验证。实现方式沿用本项目既有惯例——`build_companion.py` 锚点补丁中的 `CompanionControl.IsManaged(mate)` 分支（该模式已在 `FollowerManager`、`UnifiedTaskManager`、`TaskManager` 等多处使用），不是测试夹具专用的临时开关。

## 4. 阶段划分

### 阶段 0：穿刺验证（最先做，不通则整个方案作废）

两条独立的穿刺链，各自验证一个死穴。**在 AgentLab 专用存档执行，不碰经营存档。**

**穿刺 A —— 两个身体能否合体**

> NPC 小禾走到一棵树前 → 隐形 Farmer 同步到位 → 砍倒 → 木材进隐形 Farmer 背包 → 走到玩家旁边 → 木材交到玩家背包

死穴：位置/朝向同步精度；跨背包交接的物品守恒。
证据要求：交接前后两个背包的物品数量守恒，工具作用坐标与 NPC 站位一致。

**穿刺 B —— 行动者切换是否安全**

> 在 `ActingFarmer.As(隐形Farmer)` 作用域内跑通一次原生制作（合成一个箱子），出作用域后确认 `Game1.player` 引用完好、渲染未串、玩家背包未被改动

死穴：原生制作菜单有多少路径绕过 `who` 直接读写 `Game1.player`。
证据要求：箱子由隐形 Farmer 的材料制成并进入其背包；玩家的 `craftingRecipes` 计数**不得变化**（验证零伪造）；一个完整 tick 后 `Game1.player` 仍是玩家。

**通过标准**：A 和 B 各自取得上述原生证据。任一不通，先报告原因再决定是否调整方案，**不得绕过去继续扩面**。

### 阶段 A：活下去（与阶段 0 并行，与身体选择无关）

目标：每日存活率 75% → 99%+。这是能验证任何长程行为的前提。

1. **失败分三档**，替换现在唯一的全场停机：
   - 局部放弃：该目标今天不做，换别的，**继续跑**
   - 安全降级：放弃今日剩余计划，程序无条件回家睡觉，明天重来
   - 真停机：仅限世界状态不一致、日志写失败、存档异常

   现有的"同一角色连续失败 6 次"和"模型回复非法"应降到第 1–2 档。

2. **夜间守护**：22:00 后若无有效计划，程序直接接管返家睡觉，**不经过模型**。现在 `player.sleep` 由模型调用，模型异常则过不了夜。

3. **模型不可用 ≠ 停机**：连续非法回复 3 次后切到纯程序日常（`day.routine` 已具备），照常过夜，次日再试。

4. **自动续跑**：崩溃后从最后一次原生保存自动继续。现在 `scripts/watch_farm_week.py --continue-from` 需要人工核对。

**验收：连续 14 个游戏日无人介入。** 不是 4 天——4 天的数据外推不到 300 天。

### 阶段 B：能力迁移到双身体

- 把劳动类能力从 `player.*` 的隐含假设中解耦，改为显式"当前行动者"参数
- 借助 `ActingFarmer` 作用域复用现有 57 个 `player.*` 工具，**不重写那 760 处引用**
- 每个工具标注产物类/行为类（D2 落地）

**验收**：伙伴闲置率从 49% 降到 15% 以下；玩家钓鱼期间伙伴能独立完成一整套有用途的农务；行为类工具在陪玩模式下被正确拒绝并提示玩家。

### 阶段 C：目标图驱动排期

现有原料：`ProgressGraph.cs`（已写、**尚未编入域检查**）、`progress.catalog`、`progress.dependencies`。

缺的是让这张图驱动排期，而不是让模型每轮临时推理。全成就是一张 600+ 节点的依赖图（40 成就 + 145 出货 + 67 鱼 + 129 制作 + 80 烹饪 + 95 博物馆 + 130 核桃 + 建筑 + 友谊 + 完美度分项）。

- **程序负责**：依赖图、关键路径、季节窗口（多数鱼与作物一年仅一季）、前置解锁、预算
- **模型负责**：图上并列可行分支的取舍，以及真实失败后的改计划

**验收**：模型调用从 40 次/天降到 10 次/天以内，且覆盖率不下降。

### 阶段 D：跨季跨年

`plan.submit` 现在最远 7 天；生产方向仍停在 `maintain`。全成就需要温室、姜岛、酿酒陈酿、果树成熟、婚姻生子的原生等待期。

**验收**：一个完整季节 → 一个完整年。

### 阶段 E：陪玩模式与授权层

- 运行期行动者分配（D3）
- `CompanionCharter` 授权层（D4）
- **聊天与行动并存**：F8 不再等于暂停。当前 `ModEntry.cs:86` 打开面板即 `PauseAutoplay`，`AutoplayRuntime.cs:52` 方向键即暂停——陪玩模式下这两条必须失效。

### 阶段 F：互动深度

送礼、主动提议、关系演进。基础设施已存在：`Social.cs` 的 `RelationshipState` / `ConversationTopic` / `SharedHabit` / `DiaryEntry`、`MemoryArchive`。**本阶段主要是接通与打磨，不是从零建。**

## 5. 给实施方（Codex）的约束

1. **零伪造红线**：任何向 Farmer 写入经验、配方、成就、金钱、统计计数的代码一律不接受。穿刺 B 的验收就包含"玩家计数不得变化"这一条。

2. **`ActingFarmer` 作用域纪律**（`Game1._player` 是全局静态，换错人会波及渲染、UI 和其他 mod）：
   - 只在**单个 update tick 内**同步换进换出，绝不跨帧
   - 作用域内**不得 await**
   - 玩家可交互的菜单打开时不得切换
   - 必须提供断言：出作用域后 `Game1.player` 必须是原值，否则立即停机并保留证据

3. **版本脆弱性**：`_player` 依赖反射，游戏更新可能改名。参照现有 `native_crafting_handler_changed` 的做法——锚点失效要**大声失败**，不要静默降级。

4. **域检查注册**：`tests/Together.DomainChecks.csproj` 设了 `EnableDefaultCompileItems=false`，新增域文件必须手写 `<Compile Include>`，否则**不会被编译也不会报错**。`ProgressGraph.cs` 当前就不在列表里。

5. **夹具隔离**：所有测试夹具只在 `Settings.EnableLab` + 世界就绪 + `Game1.player.Name=="AgentLab"` 三重门禁下执行。不得在经营存档跑夹具。

6. **上游改造方式**：Squad 的改动走 `scripts/build_companion.py` 的 `replace_once` 锚点补丁 + `mod/SquadAdapter/`，不改 `external/`。

7. **先穿刺后扩面**：每个阶段先取得穿刺证据，再铺开实现。不得因为"局部测试通过"就宣称业务闭环——这是项目既有纪律。

## 7. 已知风险与未验证项

| 项 | 强度 | 说明 |
| --- | --- | --- |
| 原生制作对 `Game1.player` 的隐式依赖深度 | **实测（部分解决）** | 穿刺 B 通过：整段调用放进作用域即可，依赖被统一指向隐形 Farmer。但报告 5.1 节的依赖清单仅覆盖箱子制作分支，烹饪、职业条件、手柄入包等分支仍未验证 |
