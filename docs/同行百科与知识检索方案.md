# 同行百科与知识检索方案

日期：2026-09-19。状态：调研与设计，尚未实现；本次不改动游戏运行代码。

## 1. 推荐结论

将百科做成 Together 内置的“共同手册”：玩家可直接查阅，伙伴可检索同一份知识，并结合当前存档解释、提醒和提出分工。

以 Lookup Anything 为主要技术参考，按 MIT 条款选择性移植必要的数据提取与条件解释逻辑。底层优先读当前游戏实际加载的数据；独立实现统一的 KnowledgeService，让百科界面、聊天、经营规划共用。Lookup Anything 可选安装，不作为新功能的强制依赖。

采用“结构化查询 + 名称/别名/模糊检索 + 机制主题映射”的检索增强回答。按用户确认，不使用 BM25，也不将其保留为可选实现。初版不引入向量数据库、独立 Python 服务或额外 embedding 接口。

产品形态统一融合三类能力：Lookup Anything 对应事物资料，UI Info Suite 2 对应实时状态提示，Almanac 对应农事日历与时间安排。玩家在 Together 的同一功能内使用，LLM 调用同一个数据服务；功能融合不等于直接合并三个项目源码，代码复用仍遵循下述许可边界。

核心区别是：百科知道“这个东西是什么”，伙伴还应知道“我们缺不缺、今天能不能获得、我愿不愿意陪你去”。

## 3. 玩家能怎样使用

百科入口放在同行菜单的工具入口，打开独立手册页面，避免继续挤压现有标签栏；快捷键可配置，不抢 Lookup Anything 默认 F1。

页面包含搜索框、分类、条目正文和“与我们有关”区域。条目支持最近浏览、收藏及返回上一条；人物、配方、材料、地点之间可点击跳转。

| 信息区 | 内容 |
| --- | --- |
| 基础资料 | 名称、类别、获取条件、用途、配方、赠礼等已支持字段 |
| 当前存档 | 实际持有与存放位置、收集/献祭缺口、已知关系、已解锁条件 |
| 今天是否合适 | 当前季节、天气、时段、地图和技能条件，解释缺少哪项条件 |
| 伙伴讨论 | “问问伙伴”“和另一个条目比较”“加入共同计划” |
| 依据 | 来源类别、适用版本、观察时间、计算假设与不支持的规则 |

直接查资料不调用模型；玩家点击“问问伙伴”或自然聊天提问时，才调用 DeepSeek 组织回答。断网时仍能查手册、看库存、用已支持的计算器。

若用户同时安装 Lookup Anything，我们的菜单按其文档暴露 HoveredItem/HoveredNpc，让玩家能用 F1 打开它的详细页；这只是可选界面联动，不是知识数据来源。

默认提供“随探索解锁”模式，也可切换完整资料模式。隐藏内容先在服务端过滤，再提供给 UI 和模型，不能只在界面遮住。未知人物偏好、剧情、未发现区域等按明确策略处理；每类无法可靠判断发现状态的内容应保守隐藏或提示。

## 4. 知识来自哪里

分开保存三个层次，避免把静态规则、实时情况和共同回忆混在一起。

| 层次 | 数据内容 | 获取与刷新 |
| --- | --- | --- |
| 游戏知识 | 物品、作物、鱼、配方、机器、人物、地点、收集目标的可读取定义与条件 | 从 SMAPI 当前加载的游戏内容建立目录；语言或相关内容失效时重建对应索引 |
| 存档事实 | 库存、质量、已献祭、已收集、任务进度、天气、玩家状态、当前作物阶段 | 复用并扩展 WorldReader/ProgressReader，在游戏主线程取快照，查询时核对新鲜度 |
| 相处记忆 | 你们的计划、承诺、偏好、实际经历和探索记录 | 复用现有持久化与记忆检索，附事件来源，不把模型编写的解释回灌为游戏事实 |

优先级：当前运行时有效规则与实例状态 > 对应版本的已验证适配规则 > 自有机制说明。外部攻略仅可补充解释，不覆盖当前 Mod 已修改的数据。

标准内容修改会反映在加载后的数据里；自定义 C# 行为、特殊钓鱼算法或未公开条件不一定可解析。Provider 必须报告支持程度：完整、部分、未知，不能承诺兼容所有内容 Mod。

库存也有观察范围：现有读取主要覆盖背包、队友物资及农场/建筑内储存，不能据此声称“全世界没有这个物品”。百科扩展已加载并允许读取的容器范围，同时显示未覆盖地点；多人模式按实际玩家权限和归属读取。

每条事实至少包含：稳定 ID、类型、显示名、别名、字段、条件、来源、游戏版本、内容修订号、存档/玩家标识、观察时间、发现限制、支持状态。物品用 QualifiedItemId，人物/任务/地点使用带类型和来源命名空间的 ID；显示名只用于检索，不能作唯一键。

图标直接使用玩家本机已有游戏资源，不将游戏资产或整套解包数据打进公开安装包。需要移植的上游代码保留出处和许可；百科解释文本自己编写。初版不批量抓取并分发 Wiki 正文，后续引入外部文章时逐源核对许可、署名和版本。

## 5. 检索怎么选：RAG 与模糊搜索一起用

“RAG”描述先检索再回答的流程；模糊搜索是检索的一种手段，两者并不冲突。本项目重点是先找到正确对象，再执行条件判断，最后让模型解释。

| 用户输入 | 检索方式 | 原因 |
| --- | --- | --- |
| 完整物品名、人物名、ID | ID/规范名称精确查询 | 消除同名和类别混淆 |
| 中文俗称、英文名、少量错字 | 人工别名词典、前缀/子串、字元匹配、受限编辑距离 | 支持自然输入，结果可解释 |
| “春天下雨能钓的、献祭还缺的鱼” | 解析筛选条件后查结构化数据，再结合实时存档求交集 | 文本相似度不能保证季节、天气和缺口条件都满足 |
| “为什么树一直不长”“机器为什么不工作” | 按实体类型、问题关键词和主题标签定位机制说明，并对实例检查条件 | 适合原因解释，同时保留实际诊断证据 |
| “之前一起找的那个材料” | 先检索真实共同记忆，取得候选实体 ID，再查百科 | 记忆和通用知识各司其职 |
| 很模糊的外观或用途描述 | 用类别、标签、用途关键词匹配；召回不足时列候选或追问 | 不保证任意语义改写都能命中，不能把猜中当确认 |

排名顺序：精确 ID/名称 > 确认别名 > 前缀/子串 > 模糊候选；机制说明通过“实体类型 + 问题主题 + 关键词/同义表达”映射到条目，不做全文相关性评分。拼音可作为可选别名，低优先级处理，防止同音误选。中文使用规范名称、别名和字元匹配，不能仅靠英文空格分词。

只对合理长度的名称放宽错字匹配；单字、同名或分数接近的结果显示候选让用户选择。候选结果附“别名命中/可能错字/相关用途”等原因。低置信召回不能进入自动派工。

初版使用 C# 内存实体字典、别名索引、类别/标签查找表和机制主题映射，缓存到本地可重建文件，不引入全文搜索框架或独立服务。只在相关数据变化时更新索引，查询时检索，不每帧扫描全部资料。若大型内容包实测索引体积和启动耗时有问题，再优化分片与缓存；以基准结果决定，不预先堆叠组件。

关系用普通类型化列表表示，如配方→材料、鱼→地点条件、物品→献祭槽位。不需要独立图数据库。深层配方查询设深度上限并检测循环。

使用验收题库统计同义改写的 Top-5 召回、错误候选率和耗时，优先完善别名、问题主题和标签。自然语言问题可由 LLM 转成受限的实体与条件查询，但返回的 ID 和条件必须经过程序验证；没有命中时说明未找到或请求澄清，不能用模型猜测填补事实。

## 6. 数值与条件由程序计算

模型不能自己猜“来得及成熟”“还差几个”“一定钓得到”。提供具体计算器：

| 计算器 | 必须考虑的因素 | 输出边界 |
| --- | --- | --- |
| 作物计划 | 当前日期与生长阶段、肥料/职业、复收、是否浇水、季节/温室规则 | 最早日期及假设；无法验证的规则标记未知 |
| 钓鱼条件 | 地图/区域、季节、天气、时间、技能、鱼饵/装备、解锁与特殊条件 | 当前满足/不满足/未知，列缺少条件；满足条件不保证下一竿钓到 |
| 献祭/任务缺口 | 实际槽位、可选项、质量、已提交量、任务计数、库存与预留 | 区分“已有材料”“可交付”“原生任务完成”，防止重复分配同一物品 |
| 配方与加工 | 已学配方、替代材料/类别、现有库存、机器规则、燃料和批量 | 缺料及可加工数量；条件输出和随机产物按范围表达 |
| 种植与经营比较 | 实际可购种子、价格、剩余天数、资金/地块、授权预算 | 明确成本、预计收益假设、劳务需求；不承诺随机品质或未来天气 |
| 礼物与收集 | 已知喜好、生日、赠送限制、库存用途与预留、原生收集进度 | 建议和依据，避免把珍贵任务物资直接当礼物消耗 |

所有条件查询应无副作用：不能为了预测钓鱼调用会推进随机数的实际钓鱼过程，也不能通过预览产物消耗材料或改进度。复制必要输入，使用纯计算/只读条件适配。

## 7. 给 LLM 的接口与回答流程

拟新增的内部只读工具：

| 工具 | 用途 |
| --- | --- |
| knowledge.search(query, kinds, limit) | 找实体/机制条目，返回 ID、短摘要和匹配理由 |
| knowledge.get(id, sections) | 获取指定字段、关联实体和来源 |
| knowledge.evaluate(id, question_kind, context) | 计算现在能否获得、能否成熟等受支持问题 |
| knowledge.compare(ids, criteria) | 按程序支持的维度比较，并返回计算假设 |
| farm.requirements(goal_id) | 复用进度与库存服务，返回指定共同目标的实际缺口 |

这些是我们要实现的接口，不是 Lookup Anything 已提供的 API。参数限制种类、ID、数量和计算模式，不接受任意代码、SQL 或路径。

现有 ModelClient 只做一次结构化决策回复，还没有通用工具循环。新增 KnowledgeAnswerService，不把当前劳动决策协议改成可随意调工具：

1. 点击条目询问：直接用条目 ID 与问题类型查数据，通常只需一次模型调用解释结果。
2. 自然语言：本地识别明确实体、上下文指代及常见问题；涉及复合条件时，由模型返回受限的检索请求，程序验证并执行。
3. 一次补充检索后仍无法确定对象或条件，列候选/追问，不循环猜测。最多两轮检索，单轮最多三次只读调用。
4. 将少量相关证据送给模型生成答案，约束返回 answer、evidence_ids、uncertainty、suggested_goal；没有证据的数字、日期和完成状态不得宣称确定。
5. 事实卡由程序直接生成；自然语言回复校验来源 ID，关键数值优先使用已计算字段。证据不足或校验失败时退回事实卡，说明目前不能确定。

响应区分“规则事实”“这份存档的观察”“伙伴的建议”。界面用可点击依据卡展示来源，无需每次对话念一串文档名称。

自然问答默认最多三次模型请求（查询规划、必要补充、最终表达），直接命中路径只用一次。检索候选默认 8 条、最终证据最多 5 份，初始证据预算约 2500 tokens，按实际延迟调整。每一次模型请求都计入已有费用/次数预算；预算不足时显示本地事实卡，不自动增加玩家费用上限。

模型请求异步执行，但所有游戏 API 读取在主线程完成，只传不可变快照。附存档 ID 和状态修订号，防止玩家切档后显示上一个农场的信息。跨天气、时间、库存变化的结果刷新或明确显示观察时间。

## 8. 怎样让它更像朋友

百科既用于回答，也用于伙伴做决定，但知识不会覆盖人设。

**一起解决问题。** 玩家问“今天能补点献祭吗”，先查缺口与可执行机会，再由喜欢钓鱼的伙伴偏向提出钓鱼分工。胆小的伙伴可能愿意帮忙备料，却不愿深入矿洞。所有建议以真实存在的候选和已授权行动能力为边界。

**交流具体发现。** 伙伴完成一次真实采集后，可以说“这个我们还缺，我留到收货箱了”，但只有存放结果已确认才可这样说。仅计划去找时要说“我想去找”。

**有你们自己的手册。** 通用条目旁显示真实记录：“你收藏过”“上次一起去过”“已答应帮你准备”。可以给条目写便签，把计划和回忆连接起来，不能捏造曾一起经历的事。

**主动分享有时机。** 时间/天气窗口、共同目标缺口、新发现才触发候选提醒；每天限量、同一话题去重，尊重安静与放假模式。提醒要能跳过、稍后再说、加入计划，不持续打断劳动和聊天。

**查询不自动改农场。** “怎么得到这个”只回答；“帮我准备这个”才交给现有协商和调度器。工具知道某个配方，并不表示伙伴已经有制作、购买或提交任务的能力；查询结果必须同时显示能做的协助和仍需玩家完成的步骤。

拟议体验示例（非当前存档事实）：玩家问“剩下的鱼今天能不能补？”→ 检索实际缺口 → 计算当前可捕获候选 → 伙伴提出一个符合兴趣的选择 → 玩家同意共同安排 → 原调度器执行 → 实际回执更新手册与日记。若今天条件不合适，就解释原因并给可行替代，不编造一条好消息。

## 9. 代码衔接与实施顺序

继续使用 C#，与当前 .NET/SMAPI 构建方式保持一致。

| 拟新增/修改模块 | 职责与现有衔接 |
| --- | --- |
| Knowledge/Providers | 原生数据、选择性移植的 Lookup Anything 逻辑、自有机制说明适配；统一输出 DTO |
| Knowledge/Catalog、Search | ID/别名/文本索引、语言切换、发现过滤与缓存 |
| Knowledge/Evaluators | 作物、钓鱼、缺口、配方、礼物等无副作用计算 |
| Knowledge/KnowledgeService | UI、LLM、规划器唯一的事实入口，提供来源和支持程度 |
| WorldReader、ProgressReader | 补充百科所需状态，不继续把所有知识塞入现有大快照 |
| KnowledgeAnswerService、ModelClient | 有界检索编排、证据回答、预算统计、超时与降级 |
| EncyclopediaMenu | 独立手册 UI、模糊搜索候选、详情、收藏与可选 F1 联动 |
| PlanningRuntime、SocialRuntime | 订阅与目标相关的机会，生成有限提醒；接回原有任务/记忆系统 |

实施阶段：

1. 建实体目录与 Provider，覆盖物品、作物、鱼、人物、配方、机器、地点、任务/收集进度；每类明确字段支持范围。
2. 建别名、轻量模糊匹配及机制主题映射，接实时状态与计算器，输出可追溯事实卡。
3. 建手册界面，再接模型检索回答；相同查询必须使用相同数据服务。
4. 接共同目标、伙伴主动分享、便签与回忆，保留现有行动权限和执行核验。
5. 全部功能形成闭环后集中验收，修复发现的问题，再提供体验包。实施阶段按用户既有要求分别本地 commit。

本次仅提供这份方案，不执行上述实施步骤，也不安装三个参考 Mod。

## 10. 集中验收标准

以下为将来实施后的验收目标，不是已经通过的结果。

- 检索题库至少覆盖：中英文名称、别名、错字、同名、模糊用途、复杂条件和跨条目追问；有标准实体的问题统计 Top-1/Top-5，歧义问题必须返回候选。
- 数值题逐项与原生实际状态核对：季末生长、肥料/职业、复收、天气/时间/鱼饵条件、质量献祭、随机献祭、库存预留、配方替代、机器条件与任务计数。
- 模型答复中的关键数字、日期和完成状态能追溯到证据；模型不可用时本地查询仍正常。
- 未发现内容在 UI、搜索结果、关联链接和发往模型的证据中均按设定过滤。
- 内容修改、语言切换、过夜、换地图、切档、多人身份变化后刷新正确，不把旧规则和旧库存当最新事实。
- 检查自定义内容的部分支持提示，不将不支持的特殊机制判为“不存在”或“肯定可以”。
- 查询无副作用：不消耗物资、不推进 RNG、不改任务、资金或世界状态。
- 温缓存本地检索目标 P95 小于 50ms，索引在不可变快照上构建；游戏线程采集按帧分批。首次索引耗时、峰值内存和大型内容包表现另行实测，不将目标当已达成。
- 一次问题不超过设定检索/模型预算；长文本、异常模型输出、空结果和网络失败都有可读回退。
- 朋友式情景验收：一次共同目标提问→有依据的建议→接受/协商→真实劳动→更新缺口→隔日接续；以及拒绝建议、安静模式、非工作闲聊不被百科催促打断。

这一模块的价值在于把知识变成可靠的共同决策依据：让玩家查得方便，让伙伴说得有根据，并能在已有能力范围内一起把事情做下去。
