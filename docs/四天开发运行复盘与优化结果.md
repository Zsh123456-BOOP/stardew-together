## 4. 从日志与代码确认的剩余问题

### P0：失败记忆仍过度依赖无关状态，任务语义不够统一

L轮仍有4次“木材没有批准用途”、2次`stock_target_requires_1_to_9999`。不能归因于Flash单纯不听话。

代码位置：`mod/Together/ManagedWorkRuntime.cs:8`、`mod/Together/FailureKnowledgeRuntime.cs:5`、`mod/Together/FailureKnowledge.cs:30`。

现在`count`在一般劳动中表示操作数量，在部分物资任务里又被当作库存目标；模型常用的`count=0`连续劳动语义在这里变成非法库存目标。失败条件摘要还混入全背包、玩家体力、地图对象等；与失败无关的状态改变也可能解除记忆。动作完整参数参与失败键，换措辞或参数可能成为另一项失败。

下一组修改：

- [ ] 把“清理某区域”“库存补到多少”“为某生产项目采集”分成明确工具参数契约；所有入口统一生成同一目标标识。
- [ ] 非法目标在派单前返回具体合法候选，不能进队列后连续失败。
- [ ] 失败按原因记录最小解除条件：无目标看目标区域版本；缺容量看对应角色空间；未批准用途看生产计划版本。别用整个世界状态解除一个局部失败。
- [ ] 已成功完成的目标更新同一记录，防止旧失败摘要覆盖新成功证据。
- [ ] 验证“相同失败只改变体力或无关背包物品仍不重试；真正改变前置条件才恢复”。

### P0：伙伴没有足够的可执行工作，候选可达性也不可靠

L第4天原生日志估计：伙伴`idle_no_ready_work`约363秒，占有标签采样区间约49%；玩家约57秒，约8%。它不是整天没干活，但分工显著不足。日志还出现2次伙伴无合格目标、1次玩家找不到目标和1次伙伴共享仓储阻碍。

代码位置：`mod/Together/OperatingOpportunities.cs:8`。当前候选主要面向玩家，采集候选只核验有地图出口，尚不等于目标站位可达；固定时间估算也无法反映真实路程。

- [ ] 玩家与伙伴分别生成能力、路径、货袋和劳动预算均满足的候选。
- [ ] 先保持同片区任务，按真实路径成本选择邻近目标；已批准田区/道路清理与物资补缺分别计算。
- [ ] 候选为空时记录各项排除原因，不能只给“没有工作”。
- [ ] NPC交接与玩家仓库操作共享容量信息，出发前预留接收位置；无接收空间时先补容量。
- [ ] 验证玩家钓鱼时伙伴能独立完成有用途的农务或清障，且不靠无目标囤料填满劳动额度。

采样中的静止包括挥工具、菜单、等待和休息，不能直接算成发呆。以上比例只使用原生阶段标签作估计，不当作精确工作时间。

### P1：思考触发仍会卡顿，异步HTTP并未解决准备阶段耗时

L慢帧记录：`investment`单阶段最大394.73ms、`decision_day`128.84ms、`decision_serialize`127.70ms、`semantic`123.67ms。它们并不一定发生在同一帧，不能简单相加；但已足以说明用户感到的顿挫有代码证据。

代码位置：`mod/Together/AutoplayRuntime.cs:130`、`mod/Together/AutoplayRuntime.cs:202`、`mod/Together/ContextCompression.cs:5`。HTTP已在后台，但当天经营计算和反复JSON序列化仍在游戏线程执行。

- [ ] 主线程只提取有版本的必要原生数据；后台仅计算脱离游戏对象的不可变快照，不能在线程池直接访问`Game1`。
- [ ] 土地、配方、价格、空间布局按相关变化增量更新，普通移动不重算整套投资方案。
- [ ] 上下文按字段预算一次构造，减少`Size()`反复序列化整棵JSON树。
- [ ] 日志写盘异步之外，日志内容构造也要测量；遥测本身本轮最大55.74ms，不能让观察器制造新的卡顿。
- [ ] 用相同场景比较慢帧P95/P99、决策准备耗时与目标变化是否漏处理，再判断优化有效。

### P1：经营能出货，但尚不会稳定扩产

本存档生产方向仍为`maintain`，没有新加工资产；前期现金从500降到100后，直到修复出货才回流。保存到第5天不代表已完成种植→收获→销售→再投资，更不能证明后期牧场酿酒能力。

- [ ] 第5天收获后，按实际现金及未来照料负担比较补种、工具、仓储与加工投资。
- [ ] 库存目标绑定项目总需求、已投入和剩余量，消费材料后不能机械补回旧库存上限。
- [ ] 稀缺/任务预留与运营储备分开，继续减少固定“每种都留若干”对空间和销售的影响。
- [ ] 记录真实产能、资金回收日期和劳动成本，避免只按售价选择作物或机器。
- [ ] 为21→20株的变化补对象删除/作物损失事件；防护设施需求应由证据计算。

### P2：菜单与模型调用还可以减少

第5天宠物剧情最终自动处理成功，但消耗12次模型响应。期间发生随机命名后沿用旧菜单token的拒绝；程序没有错误重用旧菜单，因此安全性成立，但交互效率很低。

- [ ] 将命名封装为“选择名称→原生提交→结果确认”的小型事务，普通确认由程序续接。
- [ ] 不能照搬计划版本重基策略去盲目更新菜单token；菜单内容和按钮含义可能已经变化。
- [ ] 模型事实摘要保留日期、状态来源与证据ID；模型叙述中的“体力150”等值不能覆盖同期原生快照。
- [ ] 报告分开统计经营、剧情、重试和无新增信息查询，先减少机械回调再考虑更贵模型。
