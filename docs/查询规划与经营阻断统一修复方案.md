# 查询规划与经营阻断统一修复方案

日期：2026-09-22。状态：本轮修复已落地，最终组合检查通过，准备按用户授权启动独立七天试玩。实现、原生验证与尚待长程取证的边界见《查询规划修复实施与七天启动记录.md》。以下原始审查保留作为前后对照。

## 1. 目标与依据

合并解决两个问题：

1. 模型自行选择关键词查询，在得到资料后制定计划；提交的任务不再被程序强制查百科打断。
2. 修复当前运行中的返家失败、可选出货反复插入、追赶 NPC、混合种子空方案及相关记忆问题。

模型决定经营方向、采购品种和金额、是否继续社交及如何使用体力。程序负责准确观察、计算、原生执行、任务续接和结果核验。不增加“查询过才准执行”、固定采购金额、社交次数或清理额度。

证据分级：

- **实测**：当前运行的原始请求、回执或业务日志已出现。
- **静态确认**：代码路径明确存在，不等于已经测得每一种后果。
- **待验证**：需原生复现确认，不用推断代替根因。

当前审查运行：`79798237b00341cb8527f299d5095e2c`，存档 `449746621`，隔离运行时 `work/MemoryV2TrialMods`。相关证据在 `work/current-pause-review/` 和该运行的日志目录，不进 Git。当前只完成一次原生过夜，春 2 日 19:40 因 `survival_return_failed_three_attempts` 暂停。

纠正上一份说明：实际采购为零，但不能全部归因于模型主动不买。春 1 日 14:30 模型明确提出查看 SeedShop 报价；强制百科核对在执行前拦截该批调用，下一轮改为社交，商店任务未续接。模型也有主动保留现金的选择，两者必须分别统计。

## 2. 审查确认的问题

| 编号 | 证据 | 问题与代码位置 |
| --- | --- | --- |
| Q1 | 实测＋静态确认 | `DecisionContinuation.ApplyDecisionCalls` 在创建执行批次前调用 `ReviewNewTasks` 并直接返回，整批原调用没有进入正常续接对象。 |
| Q2 | 实测＋静态确认 | `MemoryContextRuntime` 从参数自动拼检索词，遗漏 `shop/location`。SeedShop 查询退化为 `shop`，返回其他商店；`fish/store` 也混入不相关资料。 |
| Q3 | 静态确认 | `reviewedTasks` 在执行前即加入，缓存键混入日期、容量版本；`pendingTaskReview` 仅在运行重置处清除，可能长期携带过时核对资料。 |
| Q4 | 静态确认 | `ContextBudget.Pack` 无条件把 recent 裁为两条；`ContextCompression` 也会裁减查询结果。多查询的较早结果可能在首次交给模型前丢失。当前没有“尚未送达结果”的独立保护。 |
| Q5 | 静态确认 | `AutoplayRuntime` 先调用 `ContextCompression.Pack`，`AutoplayModel` 内的 `ContextBudget.Pack` 再调用一次。第二层继续删字段，第一层已生成的观察指针和降级集合没有贯穿整个流程。存在重新形成信息闭环的风险，需契约回放验证。 |
| Q6 | 静态确认 | `PlanningKnowledge` 直接查底层索引并允许所有条目；显式百科走 `KnowledgeService`，遵循资料范围并附详细事实。两条入口的语义不同。 |
| B1 | 实测＋静态确认 | `QueueClosingShipment` 在睡觉前自动插入出货，不检查该收工计划刚刚的失败。最多 24 条、按每个 sleep ID 计数，只是数量限制，不能阻止重建 sleep 后继续插入。 |
| B2 | 实测＋静态确认 | 社交、出货、返家均报路线错误。`NextExit` 把没有地图链、首段出口不可达、搜索范围耗尽合并为 null，调用方只报 `no_known_route`。具体受阻实体尚未确认。 |
| B3 | 静态确认 | `CheckKnownFailure` 按工具匹配；出货与睡觉不能直接共享已证实的路段阻碍。睡觉失败条件主要按时间、体力、农务计算，未按实际路线根因区分。 |
| B4 | 实测＋静态确认 | 一次追 Jodi 产生 25 次寻路。`TickSocial` 在 NPC 换格后每 500ms 可重算；`SocialReach` 与跨图执行另算路线，前者未核验所有中间路段和门禁。 |
| B5 | 实测＋静态确认 | 混合种子五次规划返回空列表。`FarmPlanningRuntime` 只查固定作物定义，未知定义直接 continue；执行前也要求固定定义。`evaluated_seeds=options.Count` 实际是成功方案数，不能解释筛掉原因。 |
| B6 | 静态确认 | `BusinessOpportunities` 的未种种子候选也只认固定作物定义；只修 farm.plan 不会接通候选。播种续作还直接比较 seed ID 与 crop.netSeedIndex，特殊种子的原生对应关系需核对。 |
| M1 | 实测＋静态确认 | 昨日总结只取最后 12 条 action_result；本轮遗漏早晨农务。发给模型的当天日记只按活动种类聚合，丢掉物品、地点和具体时间；完整明细实际已存在。 |
| M2 | 实测＋静态确认 | 模型把今日干地误认为昨日未浇水。历史结果和今日维护状态都有，但缺少按地块/日期清晰对应的摘要。摘要校验只核对证据 ID，不能证明文字解释正确。 |
| M3 | 实测＋静态确认 | 记忆检索会把鱼店社交失败关联到钓鱼。`MemoryProjector` 递归提取嵌套实体，目标实体与附带资料实体没有区分。 |
| C1 | 静态确认 | 工具说明仍同时写“默认不额外保留体力”和“默认24点停止”，而 `DailyBudget.EnergyReserve=0`。核心简版与完整定义重复维护，已发生语义漂移。 |

附加待验证项：`DecisionSnapshot` 跨 8 次调用组装快照，位置、体力、时间变化会重置组装。若希望劳动期间处理只读查询，需验证是否会长期无法形成快照；不能为解决它直接冻结玩家或删掉所有一致性校验。

## 3. 修复工作包

### R1. 移除任务提交后的强制核对

- [x] 删除 `ApplyDecisionCalls` 中的 `ReviewNewTasks` 拦截。
- [x] 删除其专用的 `reviewedTasks`、`pendingTaskReview`、唤醒与清理分支；替换仍描述“强制核对”的上下文说明。
- [x] 保留已有任务队列、真实前置检查和回执核验，不引入查询许可。
- [x] 同步替换旧 preflight 测试：原测试证明“第一次拦截、第二次放行”，并未证明任务完成；新测试必须证明一次提交即可进入原生执行。

已知事实足够时，模型直接提交；事实不够时，模型先查询。

### R2. 模型选词，统一查询入口

- [x] 复用 `knowledge.search/get`；搜索增加可选分类、精确实体与批量查询能力，兼容现有单 query 参数。
- [x] 关键词由模型给出，可附查询目的；程序仅做名称、别名、ID 解析、分类筛选、去重排序，不根据一段长计划擅自猜任务。
- [x] 精确对象优先；每个结果标明匹配对象、匹配依据、资料范围、原生来源和未验证条件。无匹配或歧义明确返回，不用弱相关条目填满列表。
- [x] 自动附带资料与显式查询复用同一服务，尊重既有百科范围设置。已知配方、库存与目标摘要可直接提供，不要求付费再问一遍。
- [x] 百科规则与实时服务查询分开：营业/进入条件用现有服务工具，实际报价用原生商店菜单；百科基础售价不作为采购报价。

### R3. 查询结果可靠送达，任务不丢失

- [x] 增加按请求标识关联的查询回执存放与送达状态：查询完成、已放入某次模型请求、被后续决定引用/替代。日志只能证明送达和引用，不能宣称模型已正确理解。
- [x] 同轮多个独立查询一起返回；首次尚未送达的结果不进入“只留两条历史”的裁剪规则。大结果分页，但保留每个查询的结论、限制及续读入口。
- [x] 模型依赖新查询结果作选择时，下一轮再提交具体动作；已经声明的规划目标和待解决问题保持存在。
- [x] 同轮混合查询与动作时，明确哪些动作依赖新结果。仅把依赖结果的草案标成等待决策，不伪报已执行；已有独立工作继续。查询不默认清空任何活动任务。
- [x] 模型修改计划必须有明确取消/替代记录；暂停、读档或模型回复过期后，查询可重读，已执行动作不能重放。
- [x] 拆分只读查询续接与行动落地的失效条件：不把每一次普通走格当成静态配方查询失效；实际购买、交付仍用最新库存、现金、菜单与任务版本核验。

### R4. 合并上下文压缩，消除第二次丢失

- [x] 保留一个最终打包入口，复用已有压缩算法；移除运行时提前打包再进入预算器重复打包的流程。
- [x] 字段降级集合、查询结果保护和观察指针由同一次最终打包决定。凡指针指向的完整字段被删，必须恢复真实结果或给可读取的准确证据入口。
- [x] 删除无条件 recent 裁为两条的规则，改按“是否已送达、是否仍服务当前决策”处理。
- [x] 缓存按事实类型失效：配方随资料版本，营业随日期/事件，报价随原生菜单和货价状态，库存随实时变化；不再以容量版本让静态百科反复核对。
- [x] 统计完整调用量、实际 token、缓存命中、有效查询和空转。不能以压缩比例冒充总成本下降，也不自行降低信息质量来凑节省。

### R5. 收工与可选出货解耦

- [x] 删除“每次准备执行 sleep 都自动插入出货”的隐式副作用。可售物作为建议或模型已选择的明确任务存在。
- [x] 已选择的出货若受阻，可以跳过可选部分继续返家；必须交付的任务仍按真实依赖报告，不暗中当作完成。
- [x] 显式“先不出货、直接睡觉”落实为收工计划中的状态，不靠分析长段自由文本猜测；这不是新的用户批准流程。
- [x] 自动经营出货、显式出货、睡眠和存活兜底共用路线条件，不能换工具名绕过阻碍。
- [x] 夜间守护与原生睡觉/保存保留。无证据的相同重试不重复走；新出口、阻挡移动或地图条件变化后才执行有依据的恢复。连续三次同处失败仍停机留证，不改阈值掩盖问题。

### R6. 路线根因取证与统一可达性

- [x] 首先在隔离 AgentLab 中复现 Town (13,85) 的返家状态。记录地图链、候选出口坐标、首段站位、路径搜索结果、角色碰撞框、阻挡类型、门禁和搜索预算。
- [x] 将 `NextExit` 的结果改为成功路线或结构化原因，区分：没有已知地图链、出口站位不可达、动态阻挡、门禁、搜索预算耗尽。预算耗尽不能登记为“物理上不存在道路”。
- [x] 社交预览、普通跨图、出货和睡觉共用路线结果与相同碰撞/门禁来源；不再用一个粗略预览承诺执行一定可达。
- [x] 路线失败记忆按受影响路段、起点连通区域、出口及相关阻挡条件关联；只有确实共享该路段的任务受影响，不能升级为整张 Town 禁用。
- [x] 动态人物阻挡先短暂让行或选择已核验的替代站位；静态阻挡检查其他合法出口。清楚区分“返回途径不可用”与“可选出货点不可用”。
- [x] 据复现结果修具体算法。当前不预先断言 NPC、树或垃圾桶就是根因，不靠瞬移、关闭碰撞或新增清障系统掩盖路线错误。

### R7. 移动 NPC 的接近与社交取舍

- [x] 只在当前接近路线失效、交互位置确实变化或出现阻挡时重算；NPC 每换一格不必推翻整条路。
- [x] 使用原生交互范围和真实可达站位；目标跨图时核对入口、时段及返回路线，防止追进封闭区域后再发现不可达。
- [x] 给模型实际距离、已花时间、任务/生日等用途和其他可行动作。追赶长期无进展时返回这些事实，由模型决定继续、稍后再找或改做其他事。
- [x] 不设置社交每日配额，也不禁用介绍任务。避免用“强迫购物”替代模型取舍；修复的是不准确的成本、不可行候选和无进展追踪。

### R8. 混合种子完整接通

- [x] 读取原生种子到作物的解析规则，统一供候选、农田规划、执行前复核和播种后验证使用。固定种子、混合种子和其他特殊类型分别标注支持状态。
- [x] 混合种子规划给出当季可能结果及生长/收益范围，不预先假定一定种出某种作物。查询不能消耗或改变游戏随机数状态。
- [x] 播种仍走原生扣种与生成作物；续作依据实际产生的作物和种植事务核验，不能只要求特殊种子 ID 等于生成作物的 seed ID。
- [x] 空方案必须给 `无匹配种子/季节不适用/空间不足/劳动不足/类型未支持` 等具体原因，并分别报告检查数量、可行数量和排除项。
- [x] 同样参数、同样相关条件的空规划合并记录；无结果不是“种子售价零所以不能种”。允许真正改变条件后的重试，不强制先做另一个动作才能重试。

### R9. 经营选择、记忆与日常事实

- [x] 修正当日日记摘要，复用 `DiaryDisplay` 已有的物品、地点、时间、数量、支出与证据；按相同事件聚合，不把不同物品只加成一个种植总数。
- [x] 昨日总结以整天结构化日记和重要失败/未完任务为基础；不只拿最后 12 次动作。关键计数由原生回执生成，模型只补充解释，不能覆盖这些计数。
- [x] 明确并列“昨日已浇水”和“今日需浇水”；雨天与地块实际水分按当日读取，不能从今日干燥反推昨天失败。
- [x] 记忆索引区分行动目标、结果实体与附带参考资料；精确到 NPC/商店/任务/物品，避免一次社交失败把所有相关地点都记成失败对象。
- [x] 对有报价、无报价、现金改变、收获完成、获得新种子等情况给准确经营比较。是否采购仍由模型决定，不能以零采购自动判定工具坏了；报告要区分“候选未生成、结果未送达、模型拒绝、执行受阻”。

### R10. 可观察性与接缝纪律

- [x] 路线日志补足失败层级、被排除出口、首次阻挡、动态人物、重规划原因；不能只记总寻路次数。
- [x] 查询日志记录选词、命中、结果送达、关联计划、被替换原因；行动日志分别记录队列接收、原生开始和结果核验。
- [x] 统计等待模型、路线计算、实际运输、正常动画、无进展停顿、主线程耗时，检查新增查询是否增加卡顿。
- [x] 面板保留“正在/原因/接着”，受阻时附具体原因；只有实际进入查询时才显示查询，模型的意向文字不能显示为已执行。
- [x] 每项修改核对：保护是否有旁路；事实是否有第二来源；全局玩家状态写入是否满足不变量；新增恢复有没有执行结果和终止条件。

## 5. 实施顺序与验收

实施顺序：R1–R4 查询和结果交付 → R5–R7 出货/返家/路线 → R8–R9 种植及记忆 → R10 日志与展示。路线复现先取证，禁止凭旧截图预选一个碰撞体修补。

开发期完成相应编译、纯算法和历史请求回放；全部实现后在同一次隔离游戏会话集中检查以下组合，不反复启动游戏只测一个点：

| 组合 | 必须取得的证据 |
| --- | --- |
| 自选词并行查询 | 3–6 个独立查询全部出现在下一次模型请求，精确种子店不返回其他店冒充答案。 |
| 查询与队列并存 | 查询前后原任务 ID、进度和物品消耗守恒，无取消、重复提交或强制重新批准。 |
| 直接执行已知动作 | 已知配方/已知工作一次提交进入执行，没查百科也不拦截。 |
| 未知、歧义、加载中 | 给准确状态和改词/续读入口，保留目标；不伪造答案，不当作原生执行失败。 |
| 商店链 | 合法进店→柜台→原生报价→模型选择→真实采购→播种；经营试玩允许模型有依据地不买，工具链测试单独证明买得到。 |
| 可选出货失败 | 不误报出货成功，不反复插回 sleep 前；有可行返家路线时完成原生过夜。 |
| 路线复现与动态 NPC | 复现失败位置，输出精确根因；解除对应条件后可恢复。换工具不重试同一路段，也不禁掉不相干路线。 |
| 混合种子与续作 | 原生扣种、真实生成、跨批次续作、浇水验证一致；无法规划时有具体原因。 |
| 跨日记忆 | 早晨种植和晚间社交同时纳入日摘要；昨日完成与今日维护分开，失败去重保留条件和次数。 |
| 上下文边界 | 强制触发预算裁剪，验证关键标量、未送达查询、当前计划与补读接口仍完整可达。 |

组合通过后才具备重启全新七天试玩的条件。用户已授权本轮通过后启动，不进行外部持续监督。七天记录每天资产/现金/作物、工具分布、查询送达与采用、采购不执行的分类原因、运输/劳动/等待、失败恢复、实际模型用量。七天不代替原有十四天阶段门槛，不拼接旧失败运行。

守恒、原生结算和夹具三重门禁不变。新增纯域文件显式注册到 `Together.DomainChecks.csproj`。任一环节连续三次同处仍失败，保留窗口、日志和状态后报告；不放宽阈值、伪造结果或用单元检查代替原生证据。
