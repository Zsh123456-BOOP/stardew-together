## 2. 本轮停止的直接原因：三处都在菜单接缝

### 2.1 未解锁格被标成空格（实测，`NativeMenuTools.cs:43–46`）

```csharp
labels[slot.bounds]="inventory:"+field.Name+":"+i+" "+
    JsonSerializer.Serialize(AgentToolRegistry.ItemInfo(i<inv.actualInventory.Count?inv.actualInventory[i]:null));
```

遍历的是 `inv.inventory`（**显示格**），越过 `actualInventory.Count` 的格传 `null` → 生成 `{"empty":true}`。

玩家只有 12 格，菜单却报出 `c12`（第 13 格）为空。原生 `InventoryMenu.cs:318` 对 `num >= actualInventory.Count` 直接拒绝接收。

**注意：F1 的 `free_slots=0` 是正确且完整可见的。** 错误来自另一条观察路径——菜单读取——把未解锁格叫作空格。**同一事实有两个来源且互相矛盾，这是 F1 教训的重演。**

### 2.2 `menu.choose` 是业务保护的绕行入口（实测＋静态确认）

春2 12:50：背包 12/12、木材 79、**农场没有任何仓储**。

`PlayerProduction.cs` 的 `CapacityAdapter.After` 预测正确并拒绝（`capacity_no_free_slot`），**且没有扣料**。但它此前已打开 `CraftingPage`，失败后菜单仍在。

模型随后 `menu.choose(c41)` → `NativeMenuTools.Choose` **直接转发原生点击，不做任何容量/授权/保护校验** → 原生制作消耗 50 木材 → 箱子滞留手持栏（`held=(BC)130`），没进背包、没放置。

### 2.3 `input_sent` 被当成有效进展（实测，`NativeMenuTools.cs:71/76/88`）

```csharp
return new{status="input_sent",menu=Read(),inventory=...};
```

**无条件返回 `input_sent`，不核验菜单、手持物或库存是否发生变化。** `RootFailureWatch` 只处理 `error`/`failed`，因此收不到可计数失败。

实测：四次点击同一 token `F29A1E4630109431`、同一 `id=c12`，回执、手持箱子、库存全部未变。前三次后观察者准备暂停，第四次在暂停落地前执行。

## 3. 对用户四项观察的核实

### Q1 「到商店就不动了，然后直接到新一天」——成立，而且比观察到的更严重

实测（报告 §5）：春1 约 14:00 出发，**14:50 进入 SeedShop，18:20 离开**，18:50 回家入睡。

**在商店里站了 3 小时 30 分钟（210 游戏分钟），没有打开商店、没读报价、没买任何东西，现金不变。**

这 210 分钟占春1 全天 770 分钟的 **27.3%**——春1 的「受阻 40.69%」里有 27 个百分点是这一次站桩。

根因链（报告 §4D 有证据）：

1. `policy.Enabled` 与 `routine.Enabled` **始终 false**，模型多次明确表示未启用、不投资
2. 模型能走到种子店，但**到店后没有调用 `shop.read`**
3. 提交过 `tool=plan.submit, args={}` 的无效购买计划
4. F5 的报价候选依赖「已批准目标存在缺口」，而**首次批准目标直到春2中午才出现**

所以：**到店 ≠ 能买。「经营方向 → 批准需求 → 报价 → 采购」这条链在最上游就是断的。** 用户说的"把到商店和买东西串联起来，告诉 AI 有什么买让他挑"，正是要补的这一段。

### Q2 「走路应该清理路径杂物；59/68/87 格长距离调动」——现象成立，**但根因不是绕路**

实测三次长距离（报告 §5）：

| 时间 | 路径 | 步数 | 原因 |
| --- | --- | ---: | --- |
| 春1 09:30 | (17,49)→(64,30) | 86 | **开始另一清理子任务** |
| 春2 06:00 | (64,15)→(25,24) | 58 | **前日 general 订单抢先恢复** |
| 春2 08:10 | (61,25)→(13,30) | 67 | **浇水完成后恢复 general 清理** |

并且出现「西侧清理 → 东侧浇水 → 西侧清理」的折返。

报告同时确认：**同片区的小目标步数中位数是 1**，BFS 就近优先工作正常。

> **结论：长距离全部来自任务区域切换，不是路径绕行。清障寻路修不了这个——挖开路上的石头，不会让 86 格的跨农场跳跃变短。**

真正要修的是**任务按地理位置聚类调度**：同区域的清理、浇水、采集合并成一次出行，而不是按任务类型来回穿插。

这也再次说明 R-B1 清障寻路放在 14 天闸门之后是对的。

### Q3 「解锁鱼竿时不先放箱子；制作台因材料不够卡住」——现象成立，**但不是不想放**

实测：春2 12:50 背包 12/12，**农场没有任何仓储**（报告 §4C：已部署生产/仓储资产 = 0）。报告 §4B：「本轮没有真实仓库存放，重复 store 是无可用仓库时的尝试」。

**不是不想放，是根本没有箱子可放。**

真根因是**开局仓储次序**：等到背包占满最后一格才想起要仓储，而那时造箱子又需要空格——这就是 R-A1 修过的那个死结的变体，只不过这次不是检查顺序错，而是**时机太晚**。

至于「制作台卡住」：容量保护正确拒绝了，但菜单没关，模型从 `menu.choose` 绕过去了——即 §2.2。

## 4. 本轮暴露的共同模式

三轮阻断分别是：Squad `DebrisCollector` 抢跑、容量恢复深度未复位、菜单层绕过业务校验。

**它们都在接缝上，不在任何单个子系统内部。** 模式是一致的：

> **程序有保护，但保护有旁路；程序有能力，但能力没接进决策链。**

- 容量校验有 → `menu.choose` 绕过
- 采购能力有（`shop.read`/`player.buy`）→ 上游「批准缺口」链断了，候选永远不产出
- 百科有 → 没接进候选生成
- 清理有 BFS 就近 → 任务调度层没有空间聚类
- F1 修好了容量标量 → 菜单观察又造出第二个矛盾来源

**由此确立一条通用检查**（本方案要求写进实施纪律）：

> 每新增或修复一处业务保护，必须回答：**这个保护有没有旁路入口？**
> 每新增一处事实来源，必须回答：**同一事实是否已有另一个来源？两者会不会矛盾？**

## 5. 修复方案与优先级

| 编号 | 内容 | 对应 | 优先级 |
| --- | --- | --- | --- |
| **S1** | 菜单观察与输入的统一边界 | §2.1/2.2/2.3 | **P0（本轮停止直接原因）** |
| **S2** | 生产事务与手持产物追踪 | §2.2 后果 | **P0** |
| **S3** | 开局仓储次序 | Q3 | P1 |
| **S4** | 经营链路：方向→批准缺口→报价→采购 | Q1 | P1 |
| **S5** | 任务空间聚类调度 | Q2 | P1 |
| **S6** | 百科与任务接进候选生成 | Q4 | P2 |

### S1：菜单统一边界（P0）

**S1a 可操作性标注。** `NativeMenuTools` 读取必须区分：可用格 / **未解锁格** / 已占用格。未解锁格**不得**标 `empty`，应标明 `locked` 或直接不产出为可选项。材料可行性要结构化输出，**不要把 `ingredients=False` 藏在字符串里**——报告记录模型把它误解成材料充足。

**S1b 保护不得有旁路。** `menu.choose` 走到制作/购买路径时，必须复用与 `PlayerProduction`/`PlayerShopping` **同一套**容量、授权、保护校验。

配套：正常生产被拒绝且没有 `heldItem` 时，**执行器应干净退出自己打开的菜单**，不留下绕行入口。

**S1c 输入必须核验实际变化。** `Choose` 不得无条件返回 `input_sent`。要核验菜单状态 / 手持物 / 库存是否变化：

- 无变化 → 登记结构化「无效果」根因，计入重复失败监控
- 同一 (token, id) 第三次无效果 → **在执行控制层停机并保留现场**，不依赖观察者采样

令牌只证明观察未过期，**不证明点击有效**。

### S2：生产事务与手持产物（P0）

原生制作已产出但未入包/未部署的手持物，必须被显式追踪为事务的中间态。

- **不得**退回「重新采 50 木材再制作」——那会重复消耗
- **不得**为解围而丢弃手持物或强塞入背包
- 事务应能恢复：找到放置点 → 放置 → 完成；或明确阻塞并保留手持物

### S3：开局仓储次序（P1）

**在占满最后一格之前**规划真实仓储，而不是满包后才触发。

触发条件建议（由 Codex 按实际数据定阈值）：可用格低于某水平、或首次产出型任务开始前，即安排仓储建设。这是**预防**，不是恢复——`CapacityRelief` 是最后手段，不应成为常规路径。

### S4：经营链路接实（P1，对产品最关键）

这是连续两轮零采购的根因，也是春1 那 27% 站桩时间的来源。

1. **经营政策的启用路径要走通。** 查明 `policy.Enabled` / `routine.Enabled` 为何始终 false：是模型没调、还是候选没给、还是初始化就没接。**先取证再改。**
2. **「批准缺口」不能只来自已创建目标。** 开局阶段应能从季节、现金、农田容量推出可批准的种子采购需求，否则永远没有第一个缺口，采购候选永远不产出。
3. **到店即可读价。** 进入商店后应自动或强提示 `shop.read`，把真实报价交给模型挑选——用户要的「告诉 AI 有什么买，让他挑」就是这一条。
4. **无效购买计划要拒绝并给出正确形状。** `tool=plan.submit, args={}` 这种应在声明期拒绝并返回可用模板。

**不得**用「提示词里写勤快一点」代替链路修复。

### S5：任务空间聚类调度（P1）

同一次出行合并同区域工作，按地理位置而非任务类型排序。

- 跨区域切换设成本，只有当本区域可做工作耗尽、或有时效约束（作物、营业时间、剧情）时才切换
- 每日必需农务（浇水、照料）与可选清理**先合并再排序**，不要「浇水完成后恢复 general 清理」造成折返
- 目标：消除「西侧清理 → 东侧浇水 → 西侧清理」这类往返

**不开发 R-B1 清障寻路**——§3 已证明长距离来自任务切换而非路径绕行。

### S6：百科与任务接进候选（P2）

延续 F5 的做法，把 `knowledge.*`、`progress.dependencies`、`quest_board.read` 接进候选生成：当前目标存在未解析依赖时，产出查询候选。

**每个候选仍须带真实可行性证据，不可行就不产出。**

## 6. 验证要求

### 6.1 组合检查

1. 菜单读取中未解锁格标为 locked，模型不再把它当空格；材料可行性结构化可读
2. 容量保护拒绝后，`menu.choose` 走同一校验被同样拒绝；执行器干净退出自己打开的菜单
3. 同一 (token, id) 第三次无效果 → 执行控制层停机并留证（不依赖观察者）
4. 手持产物事务：制成未入包 → 找位放置完成；或明确阻塞且手持物保留，无重复采料
5. 背包未满时即已建成仓储（S3 生效）
6. 进入商店后取得真实报价并完成一次原生采购（S4 端到端）
7. 一次出行合并同区域的清理与浇水，无跨农场折返（S5）

### 6.2 第三轮三天基线

修复后从独立起点重跑三个完整游戏日，**不拼接本轮 1 天**。报告沿用 A–E 结构，并保留第二轮新增项（工具调用分布、运输分类、空转次数），另加：

| 项 | 要求 |
| --- | --- |
| 商店 | `shop.read` 次数、实际采购笔数、金额、现金变化曲线 |
| 政策 | `policy.Enabled` / `routine.Enabled` 的状态变化时间点与触发来源 |
| 空间聚类 | 跨区域切换次数、单次出行覆盖的工作数、折返次数 |
| 菜单 | `menu.choose` 调用数、其中无效果次数、被业务校验拒绝次数 |
| 仓储 | 第一个仓储建成时间、当时的可用格数 |

### 6.3 仍然不变

G3 阈值待三天数据齐备后由用户确定，**不允许先设数字再凑**；14 天闸门不豁免不拼接；R-B1 清障寻路仍在闸门之后；阶段 B 仍需等 14 天通过。
