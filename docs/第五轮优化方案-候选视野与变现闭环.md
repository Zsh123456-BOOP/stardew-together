## 2. 核心诊断：模型的视野 ≈ 候选表，而候选表只有"维持"没有"变现"

### 2.1 事实

`OperatingOpportunities.cs` 当前共 **7 类候选**：

```
infrastructure:storage   建仓
harvest                  收获成熟作物
water                    浇水
mail                     读信
production               收取加工
fish-income              钓鱼
forage:<地图>            顺路采集一个
```

**缺失的类别：**

| 缺失候选 | 后果（对应用户观察） |
| --- | --- |
| **卖货 / 变现** | Q1 不卖鱼、Q9 出货只在晚上 |
| **空地扩种** | Q11 大片空地闲置却去钓鱼 |
| **接任务** | Q13 七天零接任务 |
| **查百科 / 依赖展开** | Q3 遇阻不查资料、Q13 不推进成就 |
| **成就 / 长期目标推进** | Q13 |

### 2.2 证据：工具调用分布（255 次）

| 工具 | 次数 | | 工具 | 次数 |
| --- | ---: | --- | --- | ---: |
| `work.run` | 77 | | `shop.read` | 2 |
| **`player.social`** | **31** | | `player.buy` | 2 |
| `player.travel` | 24 | | `player.procure` | 1 |
| `inventory.read` | 17 | | **`knowledge.search` / `knowledge.get`** | **0** |
| `progress.read` | 12 | | **`tools.lookup`** | **0** |
| `plan.submit` | 11 | | **`quest_board.read` / `player.accept_quest`** | **0** |
| `farm.plan` | 10 | | `farm.production` | 1 |

> **`player.social` 31 次，百科 0 次，接任务 0 次，工具发现 0 次。**

### 2.3 用户截图给出了直接证据

游戏内状态框显示：

> 「原因 服务台失败原因明确：鱼店柜台不可达（），不再重复同一接口。**今天核心改为直接发现与推进社交**。取舍（）」

**模型在被阻断后，兜底行为是「去和村民聊天」。** 这不是模型偷懒——候选表耗尽后没有任何有依据的替代项，模型只能自由发挥，而社交是它唯一想得到的、总能执行的动作。

用户 Q12「感觉 AI 纯随便找事情干」的判断是准确的，且**根因在候选表，不在模型**。

### 2.4 这与前四轮是同一条主线

| 轮次 | 结论 |
| --- | --- |
| 第二轮 | 候选表只有劳动类，没有"获取能力"类 → 补了 F5 |
| 第三轮 | 采购链上游"批准缺口"断 → 补了 S4 |
| 第四轮 | 模型没参与选品 → 补了 T4 |
| **本轮** | **候选表只有"维持"，没有"变现"和"扩张"** |

每一轮都在同一个地方：**程序有能力，但能力没进候选表，模型就看不见。**

## 3. 对用户 13 项观察的逐条核实

### Q1「为什么不卖鱼？不知道卖鱼有钱吗」

**候选表没有"卖货"类。** 模型不是不知道鱼能卖，是它的决策视野里没有"你现在有 N 件可售物、价值 M 金"这条有依据的候选。

叠加 Q9 的出货门（见下），即使它想卖，17:00 前也会被吞掉。

### Q2「不知道几点开门？来回走？为什么要和 NPC 交流」

三个问题，根因不同：

- **开门时间**：`OperationsRuntime` 的 `ServiceWindow` 已从原生 `LockedDoorWarp` 读取营业窗口（第三轮已接）。第 4 天早晨的来回走**需要取证**——是窗口没生效，还是目标切换造成（第三轮已证明长距离来自任务区域切换）。
- **和 NPC 交流**：见 §2.3，是候选耗尽后的兜底行为。
- 用户判断「不应该有任务才交流吗」**成立**：当前没有把社交与任务/礼物收益关联，社交是无条件可用的。

### Q3「遇到问题 AI 有去查百科吗？感觉在简单摸索」

**没有。`knowledge.search` / `knowledge.get` / `tools.lookup` 七天合计 0 次。**

Codex 报告 §「能力发现与经营取舍仍不足」已自行确认此点。百科系统（`KnowledgeService`、`KnowledgeCatalog`）完整存在但从未被调用。

### Q4「店铺导航走到 NPC 侧边无法交互」

`PlayerServices.cs:81` 有柜台朝向处理（注释：*Legacy counters require approaching from below*），:91 有 `Adjacent(counter); Face(counter)`。

但 Codex 报告已确认一个**分类错误**：`Town+FishShop`、`Farm+build` 这类**地点/服务不匹配**被报成 `no_reachable_native_service_counter`（物理不可达），与真实路径不可达混为一类。

用户看到的「走到侧边无法交互」**需要取证**：是站位选择错误，还是参数不匹配被误报。两者修法完全不同。

### Q5「在商店误调田块规划后，按位置错误自行改正」

`farm.plan` 在非农场调用会返回 `plan_on_farm_or_greenhouse_first_travel_to_Farm`（前几轮日志中出现过 2 次）。模型据此自行改正属于**正常恢复**，不是算法缺陷。

**但这暴露一个设计问题**：工具在错误地点被调用时才报错，而候选/工具描述没有在事前表达"此工具需在农场调用"。应在声明期前置检查，而非执行期。

### Q6「已开拓的田块不计算，重新开拓」

`FarmPlanningRuntime.cs:219` 的 `PlotClearCost` 对已耕空地（`HoeDirt{crop:null}`）不返回 0，即**接受**它为可用地块；执行期 :167 也是向空 `HoeDirt` 播种。

**但地块选择是否对已耕地给予成本优势，本次未取证。** 这是需要 Codex 用实际数据回答的问题，不是我能静态断言的。

**取证要求**：记录每次 `farm.plan` 选出的地块中，已耕地 vs 未耕地的数量与评分，确认是否存在"放着已耕地不用、另选生地重新翻"的实例。

### Q7「不要限制 AI 几点回家，让它自己决定」

`SurvivalPolicy.NightGuard`：`time>=2200 && !effectivePlan`。

**这是安全网，不是硬限制**——只在 22:00 后**且没有有效计划**时才接管。七天中第 5、7 天各触发 1 次。

用户的诉求可以满足：把 22:00 从"硬接管"改为"分级"——先提示模型剩余时间与风险后果，模型仍无有效计划时才接管。**但不能完全取消**：它是防止凌晨 2 点昏倒的最后防线，取消会直接威胁 14 天闸门。

`work.run` 的 `until` 默认 2200/2300 属于劳动窗口，与此不同，可放宽。

### Q8「从箱子一样一样拿去卖」

**需取证。** 未在代码中找到明确的"逐件"实现。可能来自：取货按品质分批（K 轮曾修过"多品质被当作同一物品估算空间"）、或容量模拟导致的保守分批。

**取证要求**：记录一次出货的完整子动作序列（取货次数、每次数量、往返次数），判断是算法分批还是单件循环。

### Q9「卖东西不要限制在晚上」

**确认，而且是个坏 bug：**

```csharp
// AgentScheduleRuntime.cs:156
if(Data.Business.Enabled && task.spec.tool is "player.ship" or "player.ship_items"
   && !task.spec.id.StartsWith("closing-")
   && Game1.timeOfDay<1700 && CapacityAdapter.Of(Game1.player).FreeSlots>0) {
    CompleteScheduled(task, {status="succeeded", deferred=true, note="未出货、未移动…"});
    continue;
}
```

**模型 17:00 前的明确出货调用被吞掉，并回报 `status="succeeded"`。** 模型以为卖了，实际没卖。Codex 已在报告中记录第 5 天 06:30 的实例：该批订单当天晚间兜底也没兑现，直到第 6 天才卖出。

### Q10「地上两种杂草，只清理一种」

**算法是对的，沟通是缺的。**

```csharp
// FarmMaintenance.cs:44
Allowed(kind,zone,...) => kind=="grass" ? zone is "crop" or "production" or "roads"
                        : kind is "weed" or "twig" or "stone" ...
```

地上是两种不同对象：`weed`（杂草，广泛可清）与 `grass`（牧草，只在作物区/生产区/道路清理）。**牧草被故意保留**——它能割成干草喂牲口，清光了以后养动物要花钱买草。

用户看到"只清一种"是**正确行为**，但界面和回执都没说明原因。应在状态框/回执中给出理由。

### Q11「AI 看不到空地吗？很多空地闲着却去钓鱼」

**候选表有 `fish-income`，没有"空地扩种"候选。**

模型去钓鱼正是因为钓鱼在候选表里、扩种不在。这不是模型偏好，是视野问题。

### Q12「和 NPC 聊天是纯随便找事干」

**成立。** 见 §2.3 的截图证据：受阻后"今天核心改为直接发现与推进社交"。`player.social` 31 次是全部工具中第二高。

### Q13「任务和成就能看到吗？为什么不主动推进」

`progress.read` 调用了 12 次，说明**能看到**。但：

- `quest_board.read` / `player.accept_quest`：**0 次**
- `progress.dependencies`：报告称有查询，但未产生行动
- 没有任何候选把"可推进的目标"转成可执行工作

**能看到 ≠ 能行动。** 缺的是从"目标"到"今天该做的一步"的转换。

| 编号 | 内容 | 对应 | 优先级 |

| **U2** | 出货生命周期：不吞调用、不误报成功 | Q9 | **P0** |
| **U3** | 受阻兜底：给有依据的替代项，而非自由发挥 | Q12 | **P0** |
| **U4** | 参数错误与物理阻碍分类 | Q4/Q5，Codex §新问题 | P1 |
| **U5** | 夜间守护分级 | Q7 | P1 |
| **U6** | 保护性行为的理由可见 | Q10 | P1 |

### U1：补齐候选表（本轮主线）

每个新候选**必须带算法算出的真实依据**，不可行就不产出。沿用 F5/T4 已确立的做法。

| 候选类 | 触发条件 | 必须携带的依据 |
| --- | --- | --- |
| **变现** | 库存中有可售且非预留物 | 件数、预估总价、出货箱位置与距离、哪些受预留保护 |
| **扩种** | 存在可用地块（含已耕空地）且季节可成熟 | 空地数量与位置、当前现金、可买种子及其预期回报（复用 T4 的决策依据） |
| **接任务** | 任务板有可接且条件满足的任务 | 任务 ID、条件、奖励、截止日 |
| **目标推进** | `progress.*` 中存在今日可推进一步的目标 | 目标 ID、下一步具体动作、已满足/缺口 |
| **查百科** | 当前目标存在未解析依赖 | 未解析的具体依赖项 |

**关键设计：候选必须是"今天可执行的一步"，不是"一个长期方向"。** Q13 的根因正是"能看到目标但不知道今天该做哪一步"。

### U2：出货生命周期（P0）

1. **删除 17:00 前吞掉显式出货调用的分支**，或改为：保留该订单的独立待办（意图、数量、来源），在合适时机真实执行。
2. **绝不以 `status="succeeded"` 回报未执行的动作。** 没有原生出货证据就不是成功。这违反项目最核心的纪律（"命令被接收不等于执行成功"）。
3. 批量减少路程可以作为**可解释的建议**返回给模型，由模型决定是否合并，**不能悄悄吞掉调用**。

### U3：受阻兜底（P0）

当模型的候选被阻断时，系统应返回**有依据的替代项**，而不是让模型自由发挥。

- 阻碍回执中附带"当前仍可执行的候选"列表
- 社交不应成为无条件可用的兜底。若要保留社交，必须带依据（生日、任务需要、礼物收益、关系阈值），**无依据的闲聊不产出候选**

### U4：参数错误与物理阻碍分类（P1）

- 地点/服务不匹配（`Town+FishShop`、`Farm+build`）→ **声明期**报参数错误，给出正确取值
- 真实路径不可达 → 执行期报 `no_reachable_native_service_counter`
- 缺少必填参数（第 2 天 `location=Farm` 缺 `item`）→ 声明期报缺参，**不得**宣称"背包没有箱子"
- 工具的地点前置（如 `farm.plan` 需在农场）→ 声明期前置检查，不等执行期

### U5：夜间守护分级（P1）

22:00 从"直接接管"改为两级：

1. **22:00 提示**：告知剩余时间、体力、未完成工作与昏倒后果，模型仍可自行安排
2. **更晚的兜底线**（由 Codex 按原生昏倒时间定）：仍无有效计划则接管返家

**不得完全取消兜底**——它是 14 天闸门的最后防线。`work.run` 的 `until` 默认可放宽。

### U6：保护性行为的理由可见（P1）

牧草保留、受保护树木、预留材料等"故意不做"的行为，要在状态框与回执中给出理由。用户看到"只清一种草"时应能看到"牧草保留用于制作干草"。

复用第四轮 T5 的意图链机制。

### U7：三项取证（P1，先取证后改）

| 项 | 要回答的问题 |
| --- | --- |
| Q6 已耕地 | 每次 `farm.plan` 选出的地块中已耕/未耕各多少、评分如何；是否存在放着已耕地另选生地的实例 |
| Q8 逐件出货 | 一次出货的完整子动作序列：取货次数、每次数量、往返次数 |
| Q4 服务台 | 失败样本中，参数不匹配 vs 真实站位不可达各占多少 |

**取证结论出来之前不改对应算法。**

## 6. 验证要求

### 6.1 组合检查

1. 库存有可售物时出现变现候选，模型据此在**任意时间**完成一次真实出货（非 17:00 后）
2. 有空地且现金充足时出现扩种候选，完成"买种→播种"链
3. 任务板有可接任务时出现接任务候选
4. 目标存在未解析依赖时出现百科查询候选
5. 候选被阻断时，回执附带仍可执行的替代项；无依据社交不产出候选
6. 显式出货调用在任何时间都不被吞掉，也不误报 `succeeded`
7. 参数错误在声明期被正确分类，不报成物理不可达
8. 牧草保留、受保护对象的理由在状态框可见

### 6.2 第五轮七天试玩

修复后从**全新起点**重跑七个完整游戏日，不拼接本轮。

沿用既有 A–E 结构与历轮新增项，另加：

| 项 | 要求 |
| --- | --- |
| 候选覆盖 | 每类候选的产出次数、被模型采纳次数、采纳后成功率 |
| 变现 | 出货次数、时间分布、总收入；被吞/误报次数（应为 0） |
| 再投资 | 作物回款后的再投资链是否闭合（**G4**） |
| 社交 | `player.social` 次数及每次的依据（生日/任务/礼物/关系）；无依据社交应为 0 |
| 百科与任务 | `knowledge.*` / `quest_board.read` / `player.accept_quest` 调用次数 |
| U7 三项 | §5 U7 所列取证数据 |
| 上下文 | 单次输入 token 与缓存命中率，与本轮 15,729 / 25.9% 对比 |

### 6.3 仍然不变

G3 阈值待用户在可信数据后确定；**14 天闸门不豁免不拼接**；R-B1 清障寻路仍在闸门之后；阶段 B 仍需等 14 天通过。

本轮七天**不并入**十四天。
