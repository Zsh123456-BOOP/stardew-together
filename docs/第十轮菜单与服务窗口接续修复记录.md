# 第十轮：菜单与服务窗口接续

2026-09-22，承接第九轮七天尝试。不是新能力，也不更改三次重复失败阈值。

## 两个根因

1. **任务板死锁（实测＋代码）：**春2 12:30 原生 `player.service daily_quests` 已打开 Billboard，后继社交/采木仍排队。`NeedsAgentMenuDecision` 只列举少量菜单而遗漏任务板；`CanDefer` 把后继队列视作工作，阻止模型观察/关闭菜单。游戏时间被菜单暂停，夜间守护无法触发。
2. **关门后空等（实测＋代码）：**春1 19:50/20:10 社交的原生门禁已关闭，`PrepareServiceWindows` 将 not_before 提至2600，但 deadline仍2500；后续观察被 DecisionContinuation 等待屏障占住，直到夜间守护返家。不是没有营业时间，而是时间信息没有正确改变执行生命周期。

## 修改

- 菜单决策由所有权判断：原生执行器仍忙且未要求选择时由它继续处理；它结束后仍有菜单，就必须允许模型观察。普通通知/无分支升级继续由原生自动确认。任务板、特殊任务板以及未知菜单不再靠白名单枚举才获得决策机会。
- 如果未完成后继动作与菜单相互等待，取消尚未应用的模型调用续接、保留已排任务并记录剩余调用，唤醒模型读取当前菜单；已经完成前置时仍允许正常 shop.read 等观察继续。
- 窗口与任务截止时间无交集时，当前任务成为 blocked，回执明确 `executed=false/completed=0`、窗口与原因；它不是成功或物理故障。保留目标供新安排，不篡改到明天，也不隐藏延误。独立 sequence_after 工作可以继续，真正 after 依赖保持受阻。
- `needs_menu_decision` 加入诊断，便于以后区分等待执行器与等待模型。

## 实施纪律核对

- 旁路：普通模型请求与 DecisionContinuation 两个入口都覆盖菜单；窗口统一在队列派发前处理，原生执行前仍保留既有门禁复核。
- 单一事实：沿用 Game1.activeClickableMenu、执行器Busy和已有 ServiceWindow；没有第二份营业时间表。
- 全局不变量：本批无玩家位置、选中格、物资、货币、技能或进度赋值。关闭菜单仍走原生 menu.close，未丢弃手持物或自动确认未知分支。
- 新算法位于已注册的 AgentDecisionPacing / OperationsState，无新增遗漏编译的域文件。
