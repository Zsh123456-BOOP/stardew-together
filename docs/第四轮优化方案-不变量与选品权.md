## 2. 致命阻断：选中槽位不变量被破坏

### 2.1 事实链（实测，`day-0.jsonl` 行号见交接报告 §3.1）

1. 出行整备把**包括锄头在内**的 10 堆共 43 件物品存入箱子，玩家背包变成 12 格全空
2. 模型提交 `work.run goal=forage`，执行器去 Town(10,74) 采集
3. 采集抛 `ArgumentOutOfRangeException`
4. 原生 `Farmer.draw` 与 `Game1.UpdateControlInput` 连续 `NetList.get_Item` 越界，SMAPI 无法恢复绘制，**进程退出**

### 2.2 根因（静态确认）

```csharp
// PlayerExecutor.cs:491
... FirstOrDefault(... Hoe, -1)   →  Game1.player.CurrentToolIndex = -1
```

`TaskPreparation.cs:65` 把采集/收获描述为**只需产物空间、不需要锄头**，因此整备可以合法卸走锄头。两层各自成立，**组合后把 `CurrentToolIndex` 写成 -1，破坏了全局玩家状态**。

原生 `Farmer` 的 `CurrentItem` 及相关访问只检查上界或直接索引，负数直接越界。

### 2.3 这是第四次同类问题

前三轮的阻断分别是：Squad `DebrisCollector` 抢跑、容量恢复深度未复位、菜单绕过业务校验。**本轮是第四次接缝问题**——整备层与执行层各自的假设不一致。

第三轮方案第 4 节确立的两条检查（保护有无旁路、事实有无第二来源）仍然成立，本轮**新增第三条**：

> **任何写入全局玩家状态的赋值，必须先满足该状态的不变量。**
> `CurrentToolIndex` 的不变量是 `0 <= index < Items.Count`。

## 3. 经营链阻断：整备把未来产物当成当前前置

### 3.1 事实（实测，交接报告 §3.2）

10:10 已买 4 包 Kale。准备第二种种子（防风草 `(O)472`）的 `player.service` 时，声明期报 `loadout_missing:(O)472 缺 1` → 投资转 blocked → 后续买防风草、播两种种子全被依赖阻塞。

**不是钱不够**：当时 220 金，再买 1 包 20 金仍符合保留 200 的政策。

### 3.2 根因（静态确认）

- `TaskPreparation.cs:26–33` 的 KitTrip 向后合并最多三个后继任务的需求
- `DescribeKit:53–57` 把**后续播种节点需要的种子**计入当前必须携带，**却不扣除中间已排 `player.buy` 将产生的种子**
- 第一次 service 的视野只有购买节点，所以成功；第二次 service 已能看见播种节点，于是要求"先有种子才能去买种子"
- `FarmInvestmentRuntime.cs:44–51` 的部分采购恢复只识别 `player.buy` 失败，本次失败发生在 `player.service` 的整备阶段，**没有被接住**

## 4. 对用户四项观察的核实

### Q1「种子只买 4 个，而且一直买同一种」

**买 4 个是预算算出来的。** Flash 自己设定预算 300、保留 200；现金 500 → 可支配 300；Kale 单价 70 → 4 包 280，5 包 350 超预算。

**「一直买同一种」不成立。** 它本来要买第二种（防风草 `(O)472`），被 §3 的整备 bug 阻断。

**但用户问题背后的直觉成立且重要**：

| 工具 | 模型直接调用次数 |
| --- | ---: |
| `player.buy` | **0** |
| `player.procure` | **0** |
| `shop.read` | **1** |

采购由获批的投资计划执行（原生任务 1 次、商品结算 4 次）。**模型没有从完整货架上选品**——它只设了预算，具体买什么是算法定的。

所以答案既不是「没看就买」，也不是「看了全部再决定」，而是**模型压根没参与选品**。这是本轮要改的（见 T4）。

### Q2「看不出 AI 这一步想做什么；状态框要透明」

**透明度已可配置**：`Settings.AgentOverlayOpacity`，`DrawAgentOverlay` 中 `Math.Clamp(..., .2f, .9f)`。用户可能不知道该设置存在——应在面板或文档中暴露。

**「看不出想做什么」是真缺陷**，两个原因：

**第一，模型的解释经常被整句丢弃**（`AgentOverlay.cs` 的 `OverlaySentence`）：

```csharp
if(text.IndexOfAny(new[]{'{','}','[',']','_','`'})>=0) return "";
```

只要模型的 `plan` 文本里出现一个下划线或方括号（`stock_target`、`request_id` 这类词极常见），**整句被丢弃**，"打算"那一行就消失。截图中只剩「想做/现在」两行正是此因。

**第二，缺少「为什么现在做这个」。** 现有行是 `想做`（总目标）、`现在`（当前动作）、`接下来`、`目标`、`打算`。**从总目标到当前动作之间的因果链没有显示**——用户看到"收集木材"，不知道它服务于哪个已批准的需求。

### Q3「经营政策是给选项还是自己规划」

**Flash 自己规划的。** 08:40 主动调用 `farm.business`，来源标记 `farm.business_explicit_call`，预算 300、保留 200 由模型自行设定。不是从选项中挑选，也不是模型启动前人工置 true。

### Q4「为什么反复选择一个失败的？记忆没做好？」

**记忆是好的。** `known_failure` 空转本轮 **0 次**（三轮走势 14 → 2 → 0）。

**真因是回执语义。** 本轮 4 次 `no_effect_action`：11:50/12:50 两次 water、13:20/13:50 两次 forage，回执均为 `completed=0`。

> **「范围内没有目标可做」与「执行失败」返回同样的 `completed=0`，模型无法区分，于是重试。**

且每组只重复 2 次，未达三次阈值，所以监控正确地没有停机——**这不是监控漏停，是回执信息不足**。

### 补充：第三次出现「同一事实多来源」

交接报告 §3.4 记录：`Facts.SpentToday=0` / `Purchased={}` 与真实采购结算不一致，而原生现金与采购回执是正确的。

这是第三轮方案第 4 节那条检查的第三次命中（前两次：容量标量 vs 菜单观察、F1 之前的压缩 vs 查询）。**该原则是承重的，必须继续执行。**

## 5. 修复方案与优先级

| 编号 | 内容 | 对应 | 优先级 |
| --- | --- | --- | --- |
| **T1** | 选中槽位不变量 | §2 | **P0（致命崩溃）** |
| **T2** | 整备按净需求计算 | §3 | **P0（阻断经营链）** |
| **T3** | 回执区分「已满足」与「失败」 | Q4 | P1 |
| **T4** | 采购选品权交给模型 | Q1 | P1 |
| **T5** | 状态框意图链与文本过滤修复 | Q2 | P1 |
| **T6** | 已批准种植受阻时保留劳动预算 | 交接 §3.3 | P1 |
| **T7** | 采购账本单一来源 | §4 补充 | P2 |

### T1：选中槽位不变量（P0）

1. 裸手动作选择**合法的中性槽位**，全程维护 `0 <= CurrentToolIndex < Items.Count`
2. **失败清理路径也必须维持该不变量**——异常回滚不能留下非法索引
3. **不要**通过强制所有任务携带锄头来掩盖隐式依赖

建议增加一个集中的赋值入口（而非散落的直接赋值），在入口处断言不变量，违反时抛明确错误而非写入。

### T2：整备按净需求计算（P0）

1. 整备需求按**有序任务的输入/输出依赖**计算「出发时必须携带」的**净需求**
2. 中间任务（`player.buy`、`player.craft`）**将要产生**的物品，从后继任务的需求中扣除
3. **但绝不能提前记入真实库存**——未来产出仍是待核验依赖，不是已有物资
4. 合并多个后继的材料需求**不能简单求和**
5. `FarmInvestmentRuntime` 的部分采购恢复要能接住**发生在 `player.service` 整备阶段**的失败，不只是 `player.buy` 失败

保留原生扣料、授权与守恒不变。

### T3：回执区分「已满足」与「失败」（P1）

`completed=0` 必须携带明确的处置语义，至少区分：

| 处置 | 含义 | 模型应有反应 |
| --- | --- | --- |
| `already_satisfied` | 范围内没有目标（作物已浇完、无可采集物） | **不重试**，换别的工作 |
| `no_candidates_found` | 有目标但当前不可达/不合条件 | 可换条件重试 |
| `failed` | 执行失败 | 按失败记忆处理 |

`OperationsPolicy.Outcome` 已有 `already_satisfied_or_observed` 这个 disposition，**要检查它是否真的传达到了模型看到的回执里**，而不是在中途被压成 `completed=0`。

**这是回执信息不足，不是模型理解力问题，不得用提示词措辞代替。**

### T4：采购选品权交给模型（P1）

用户要的「告诉 AI 有什么买，让它挑」是对的方向，但**不能让模型凭记忆猜**。

设计：到店后 `shop.read` 的结果，除真实报价外，**附带算法算出的每项决策依据**：

| 字段 | 由算法计算 |
| --- | --- |
| 季节内能否成熟 | 剩余天数 vs 生长期 |
| 单位成本 / 预期售价 | 真实报价与原生数据 |
| 预计所需劳动 | 浇水次数、收获次数 |
| 当前可支配预算内的最大数量 | 现金 − 保留 |
| 是否多次收获 | 原生 regrow 数据 |

**模型在这些有依据的候选中选择，算法负责计算与校验，模型负责取舍。** 这与项目既有分工一致（程序负责可靠劳动与核算，模型负责经营方向）。

**不得**让模型直接凭作物名下单而不经过报价与预算校验。

### T5：状态框意图链与文本过滤（P1）

1. **修复 `OverlaySentence` 的过滤**：现在只要含 `{}[]_`` ` 任一字符就整句丢弃。应改为**清洗**（移除或替换技术片段）而非**丢弃整句**；仍然禁止 JSON、错误码、ID 进入显示面。
2. **增加意图链**：当前动作要显示它服务于哪个已批准需求。建议行形如：
   `现在  收集木材  ← 为「建造第二个储物箱」准备材料`
   来源应是任务的 `intent_id` / `purpose` / 所属目标节点，**不是模型自由文本**。
3. **暴露透明度设置**：`AgentOverlayOpacity` 已存在且可调（0.2–0.9），应在面板或使用文档中让用户能找到。

### T6：已批准种植受阻时保留劳动预算（P1）

交接报告 §3.3：投资 blocked 后，自动 general 清理用掉了大部分劳动预算（体力 108→32），随后 `farm.plan` 只能给出 1 株方案，模型把 `compact_plot_reduced_for_space_access_or_labor` 误解成土地不足。

要求：

1. **已批准且种子已到货的种植，在依赖受阻期间保留其劳动预算**，不被可选清理挤占
2. 受阻时给出**实际可恢复节点**，而不是降级成无关联清理
3. **分解 `compact_plot_reduced_for_space_access_or_labor` 这类多义 stop reason**——空间限制与劳动限制必须分开报，否则诱导模型误判

### T7：采购账本单一来源（P2）

`Facts.SpentToday` / `Facts.Purchased` 与真实采购结算不一致。先取证该账本是否进入模型的经营计算，再决定是修正还是移除。**同一事实不允许两个来源。**

## 6. 验证要求

### 6.1 组合检查

1. 出行整备卸走锄头 → 采集/收获 → 正常绘制与后续任务；**单独核验无目标情况**（这是 -1 产生的场景）
2. 任何路径都无法把 `CurrentToolIndex` 写成非法值（含失败回滚路径）
3. 两种种子连续采购 → 播种全链跑通；整备不再索要尚未购买的产物
4. `player.service` 整备阶段失败时，投资计划得到可恢复结果
5. `completed=0` 的三种处置在模型回执中可区分；`already_satisfied` 不触发重试
6. `shop.read` 返回带决策依据的候选，模型完成一次有依据的选品采购
7. 状态框显示意图链；含下划线/方括号的模型解释被清洗后仍显示，而非整句消失

### 6.2 第四轮三天基线

修复后从**全新起点**重跑三个完整游戏日，不拼接本轮不足一天的数据。

沿用 A–E 结构与前两轮新增项，另加：

| 项 | 要求 |
| --- | --- |
| 选品 | 每次采购的候选集大小、模型选择与算法推荐是否一致、选择理由 |
| 种植链 | 从采购到播种到浇水的完整链路是否跑通；断点在哪 |
| 回执语义 | `already_satisfied` / `no_candidates_found` / `failed` 各自次数；重试次数 |
| 劳动预算 | 已批准种植保留的预算 vs 可选清理占用的预算 |
| 状态框 | 意图链覆盖率（有多少比例的当前动作能显示其服务的需求） |

### 6.3 仍然不变

G3 阈值待三天数据齐备后由用户确定；14 天闸门不豁免不拼接；R-B1 清障寻路仍在闸门之后；阶段 B 仍需等 14 天通过。

**本轮仍未取得任何完整游戏日，A 表的 劳动 14.92% / 运输 33.99% / 受阻 44.26% 只是 630 分钟观察窗口，不作为 G3 依据。**
