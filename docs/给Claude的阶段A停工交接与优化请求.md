## 5. 首要根因：背包问题不是“找个箱子存进去”

### 5.1 已定位缺陷

- `mod/Together/PlayerProduction.cs:54`：`couldInventoryAcceptThisItem(expected)` 在配方消耗之前执行。
- `mod/Together/StorageExpansion.cs:63`：直接要求 `Items.Any(i => i == null)`，没有模拟制作释放空间。
- 实测背包满 12 格，其中木材 50。其余包括五件初始工具、鱼竿、水仙 3、石头 15、纤维 20、混合种子 1、黏土 1。造箱正好消耗这 50 木材，存在释放一格的机会，却在执行前被拦。
- 这是**静态确认的前置检查顺序问题＋实测错误码**；“修改后原生制作一定通过”尚未验证，必须测试菜单 heldItem、批次数及原生扣料顺序。
- 存储失败传到采集、收获、制作等任务，又触发当日睡眠降级。次日重置失败状态，容量条件没变，重新进入同一循环。

### 5.2 请设计统一容量预测，而非固定留一个空格

输入需要包括：行动者真实背包、最大格数、物品原生可堆叠关系及上限、品质与实例属性、菜单手持物、任务预留、预期输入消耗和输出、可达仓库容量、当前已承诺的其他动作。

对一段操作按实际顺序模拟：**取料→扣料→产出→入包→交付/存放**。区分峰值占用与最终占用；不能只看最终净数量，也不能只看目前空格。规划使用副本，执行仍走原生扣料与入包，不直接改真实库存来“兑现预测”。

必须覆盖以下来源和去向：

| 情境 | 容量风险 |
| --- | --- |
| 采矿、砍树、除草、觅食 | 一次多种掉落；延迟掉落；满包未收物需记录位置并返回 |
| 收获、动物收产、钓鱼 | 品质分堆、额外产物、钓鱼宝箱、工具/饵料格占用 |
| 制作、烹饪、机器投料收货 | 扣料后腾格、整批/分批、燃料与调料、产物暂留菜单或机器 |
| 采购、邮件、礼物包、任务奖励 | 钱扣了但装不下的边界、多项奖励、不可关闭的待领取菜单 |
| 玩家与伙伴交接、箱子运输 | 双方容量分别验算；部分转移、剩余物归属及总量守恒 |
| 建造、升级、出售、出货 | 原料和工具离包/回包、交易后容量变化、预留物不得误售 |

## 6. 新需求：能清障的路径规划

用户偏好是：**遇到普通、允许清除且工具能处理的障碍，要能挖开走近路，而不是把它永远视为墙绕远路。** 必须把此偏好落实到路径候选和执行链，不能只给模型一句“优先清理”。

请评审以下方案：

1. 地图节点区分可走、可清除、不可清除、保护对象。可清除节点带对象 ID、工具/等级要求、击打次数估计、耗时/体力、掉落及容量需求。
2. 路径可同时包含 `move` 与 `clear`。比较绕行与清障直达的总成本：实际行走时间＋工具击打/动画＋必要拾取/卸货＋体力约束；满足用户近路偏好，同时不能为省两步尝试工具打不动的巨石。
3. 田区通道、保留树、作物、机器、建筑和景观保护保持有效；“看起来挡路”不自动等于获准破坏。跨图门口与交互站位要考虑动作可达性。
4. 到障碍相邻有效站位→原生挥工具→核验对象消失/通道可走→拾取或登记未收掉落→继续原路径。导航和动画跨帧推进，绝不跨帧持有 ActingFarmer，不瞬移、不直接删除障碍。
5. 局部变更、工具不符、体力不足、对象受保护、收不下掉落时，重算可行路线或选择明确恢复动作。不得变成“为开路满包→想存箱→存箱路径又堵”的递归死循环。
6. 稳定目标优先，避免每帧因微小成本变化改路；日志记录候选路径、选路理由、清障与绕行成本、实走长度、清障耗时、重算原因、残留掉落。

请先审查复用点：`PlayerRouteController.cs`、`PlayerExecutor.cs` 的 Walk/Passable/目标站位路径、`SemanticWork.cs` 的劳动编排、`InventoryWork.cs`、`StorageExpansion.cs`、现有 FarmLayout/FarmDistrict 算法。Squad 的 AStarPathfinder 与 FollowerManager 移动保留，不建议为了此需求替换整个导航系统。这些是审查入口，不表示已经确认每个函数适合直接复用。
