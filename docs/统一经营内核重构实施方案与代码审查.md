## 1. 目标、问题判断与停止条件

目标：Flash 控制一个真实玩家，与我们创建的 NPC 分工，在正常游戏速度下完成连续四个完整游戏日的自主经营。程序负责可靠劳动、补给、排期、记账；Flash 负责经营方向、投资和不能由规则解决的取舍。四天之后继续验证畜牧、加工和扩产，不能用开局四天代替中后期能力验收。

当前主要是**工程设计与模块衔接缺陷**。项目确有长时间状态变化、原生交互和多人归属的难度，但“知道没开门仍反复出发”“有一格空位却在补给循环卡住”不应交给模型猜，更不需要昂贵模型来补救。

此次重构的单位是完整业务链：

> 发现经营需求 → 比较可行方案 → 确认计划与预算 → 准备物资 → 连续执行 → 核验原生结果 → 更新账本与约束 → 继续生产或重新规划。

**恢复长程试玩前的门槛：**本文 R01–R07 完成，组合用例全部取得证据；已知必经流程不再要求人工补操作。不能只修店铺冷却就重开四天，也不能把局部测试全部通过等同于经营合格。

### 2.2 不能现在武断认定的原因

1. **思考瞬间卡顿**：已有后台模型请求和部分后台种植计算，不是所有计算都在主线程。主线程全图快照、序列化，以及 `MemoryArchive.Append → Flush → File.WriteAllText/File.Move` 的同步写盘仍是风险点。必须用既有 `FrameStage` 分项测量，不能直接把卡顿归咎于网络或宣布移动算法已查清。
2. **钓鱼air阶段反复超时**：I轮现象确认；取消后原生鱼竿状态残留是待核查方向。需要记录原生阶段转换、取消回执和下一次抛竿条件，不能用强行清游戏状态字段代替定位。
3. **统一收益是否显著提高**：减少空转很有价值，但尚不能承诺具体利润。必须同时核对作物周期、真实报价、投入、库存和原生到账收入。

## 4. 目标架构与数据契约

流程：游戏线程采集不可变快照 → 经营/农务/任务/伙伴模块提出需求 → 统一规划器合并与核算 → Flash选择有取舍的方案 → 调度器确认资源及角色 → 原生执行器连续执行 → 结果核验 → 更新事实、目标和经验。

以下为拟新增或整理的契约，不表示已有这些类型。应放在可脱离SMAPI测试的核心层，游戏API只留在适配边界。

| 契约 | 必需字段与约束 |
|---|---|
| `WorldSnapshot` | 存档epoch、游戏日期时间、角色状态、地图版本、真实库存/现金/任务/设备、数据来源及观察时间。后台只读快照，不访问 `Game1` |
| `WorkIntent` 持续目标 | 稳定ID、来源、父经营项目、期望结果、已验证成果、剩余缺口、目的地/片区、期限、角色能力要求、预算、状态、暂停原因；文字说明不承载唯一执行依据 |
| `Prerequisite` | 业务前置、可用时间窗、资源准备、能力/身份条件，分别建模；角色互斥不写成业务依赖 |
| `ActorLease` | 角色、父目标、当前阶段、可中断边界、子动作ID；同一角色最多一个实际执行租约 |
| `ResourceHold` | 项目/任务ID、物品及品质数量、来源容器/可达范围或现金额度、已提交/已消费/已释放数量、证据ID；不得重复占用同一份资源 |
| `TripManifest` | 出行目的、固定工作地点、出发与返程条件、需要的工具/物品/容量/补给、交付地点、返回后继续的阶段 |
| `ActionOutcome` | 动作是否结束、目标是否达成、停止原因、验证过的数量变化、剩余量、等待条件、恢复点、原生证据；不能只有success/error |
| `ConstraintFact` | 主体ID、限制原因、依赖的条件、来源及置信状态、何时解除、证据ID；只跟踪与原因有关的状态 |
| `DecisionPacket` | 当前经营目标、必要事实、相关约束、少量候选及代价、需要选择的问题、依据版本、调用预算。模型回复引用目标/候选ID |

### 4.1 目标和动作状态分开

目标状态使用 `proposed / approved / ready / running / waiting_condition / suspended / completed / abandoned / needs_review`。动作可以正常结束但目标未完成，例如截止前钓了3条、目标5条。

典型结果：

```json
{
  "intent_id": "fish-income-spring5",
  "action_state": "finished",
  "goal_state": "suspended",
  "stop_reason": "time_budget_reached",
  "verified_catches": 3,
  "remaining_catches": 2,
  "resume_location": "Forest",
  "evidence_ids": ["native-catch-001", "native-catch-002", "native-catch-003"]
}
```

这条结果不能生成“Forest不能钓鱼”。同样，`already_satisfied` 表示需求已满足，不表示又劳动成功一次；买到部分商品须写部分消耗，不能失败后按全量重买。

### 4.2 幂等和重载

区分提交ID和业务ID。旧提交ID去重继续保留；新增业务指纹，例如“项目P为田块F补足种子S”，不能靠换GUID、改数量重新申请同一完整目标。

存档恢复后，先核对原生物品、任务、地图和角色，才决定目标继续、已完成或需复核。购买/制作/出货遇到“操作可能成功但回执丢失”，必须先对账，不能盲目重放。未完成的动画和旧菜单坐标不作为可直接恢复命令保存。

## 5. 统一调度：不抢活、不堵队、不随意改目的地

### 5.1 调度过程

1. 收集需求；同一目标合并，扣除已完成、实际拥有、已承诺和可信在途数量。
2. 判断真实前置和能力，不可行任务进入明确的等待状态，不占角色执行租约。
3. 在全部已批准任务中选择可执行项。先处理安全和有期限的必要工作，再考虑经营收益、就近合批、劳动和资金成本。
4. 保留当前任务连续性；新候选收益很小不改派。菜单交易、工具动画、过夜保存等阶段不可被普通清理打断。
5. 获得角色与资源租约，执行完整技能。子动作之间直接衔接，不逐步调用模型。
6. 结果更新后，检查同一目标下一步；目标等待时释放角色，选择其他有价值工作。
7. 只有重要取舍、现有计划失效或无可执行安排时，才向 Flash 请求新决策。

**A02修复反例必须成立：**先提交9点可采购任务，再提交独立浇水任务，6点应浇水；采购失败不能取消浇水。但“购买种子→播种这些种子”是真实依赖，不能为了并行把顺序打乱。

### 5.2 开门条件与出行批次

商店事实使用原生条件/已适配规则、营业日、事件状态、已观测柜台等。不能把所有商店统一硬编码9点，不能把未知当作已关闭。暂时无法解析的动态条件允许有理由的一次现场观测；取得关闭证据后，按条件等待，不反复探门。

采购目标本身可提前建立；出发时间由开放窗口、路径耗时及途中顺路任务计算。到店前再次核对可用性，门前检查不能是唯一检查。早间有完整农务可做时先安排农务，不为了几小时后的采购提前空等。

同一地点的报价、采购、交付可合并为一次出行，但必须分别有用途和预算。没有可买商品、无须更新的报价、没有待交付物品时，不派“去商店看看”。预算之外的购买仍需经营取舍。

### 5.3 外出与清理

钓鱼、下矿、采购都有持续父目标。补水、存箱、进食、掉落物拾取属于父目标子流程；恢复地点由父目标提供，不重新取“当前地图”。

清理分成：已批准用地的必要清障、项目所缺材料采集、预算内环境整理。前两种绑定项目，第三种服从生产和返程预算。选择目标考虑真实可达路径、连续片区与顺路拾取，不能只挑同工具对象导致跨地图往返。

目标/区域、工具、预算没有变化时，算法继续选择附近对象；不能每清三块就请求模型。掉落物按本次劳动追踪，离开前核验可达未拾取物；满包则保存拾取位置、卸货后续接。不可达或掉水产物必须单独记录，不能伪造全捡完。

## 6. 条件记忆：让碰壁真正改变后续行为

### 6.1 失败按原因记录

| 原因 | 约束主体与真正关联条件 | 解除方式 |
|---|---|---|
| 尚未开门/今日休息 | 店铺、日历、营业条件、相关事件/解锁 | 下次有效窗口或相关条件变化；走几格、少一点体力不解除 |
| 容量不足 | 当前任务准备要求、背包堆叠与受保护物品 | 补给后满足清单，或改变工作批量/任务 |
| 工具缺失/等级不足 | 角色工具、目标能力要求、升级状态 | 原生工具变更并验证 |
| 某片区没有目标 | 片区、目标类别及地图内容版本 | 对应片区出现相关对象；换数量不解除 |
| 路径阻塞 | 目标、路线相关格子、动态障碍 | 相关通行条件变化或找到替代路线 |
| 时间预算结束 | 本次目标与日程 | 目标延期/次日继续，不把地点封禁 |
| 原生动作异常 | 角色、工具、动作阶段和恢复证据 | 有限原生恢复并核验空闲；失败则隔离该技能并安排替代工作 |

两个接口访问同一店铺，读取同一个主体约束；同一理由换说法不会绕过。原始错误保留，结构化分类不明确时标为待诊断，不编造原因。

### 6.2 四类记忆的职责

- **事实**：以原生数据为准，保存出处和时效。今天库存重新读取，不能用昨天摘要代替。
- **计划**：项目、剩余目标、日程、预留和恢复点，程序维护；模型可以提出修改，修改需重新核算。
- **经验约束**：当前仍有效的失败条件及恢复方式；自动进入相关任务的决策包，不依赖模型主动搜索。
- **经历关系**：偏好、承诺和共同经历；保留陪伴扩展，不干扰经营事实。

检索沿用ID、别名、关键词和条件过滤。排序优先“相关主体＋仍有效条件＋原生证据”，再考虑时间；模型计划属于低可信建议，不与原生成功/失败混成事实。当前这次查询前刚写的计划默认不作为经验返回。

### 6.3 压缩、费用与卡顿

不再用字符串包含error判断重要性。未解决约束、未完成目标、资源预留、玩家承诺进入结构化常驻集合；已解决重复错误合并成“次数＋最近时间＋证据链接”，原文继续在归档。

建议首版决策包目标输入预算：常规重新安排不超过约4000 token，复杂投资比较不超过约6000 token；这是待校准预算，不是已达到的指标。优先移除无关候选和原始日志，关键内容超预算则缩小本次决策范围、按需查询，不能静默截断约束。使用服务返回的usage核对估算，记录实际费用所采用的配置单价。

只在早晨安排、重要解锁、计划失效、重大资金/产能变化、无法自行恢复的故障时调用。普通收获、下一块石头、补水和存箱不调用。事件合并，避免同一变化连续唤醒。

性能处理：先测 `FrameStage` 与决策准备、序列化、地图扫描、磁盘写入耗时；快照采集按变化更新，复杂计算在后台读取不可变数据。日志后台批量写入，过夜/退出时确保关键检查点可靠落盘。线程不能在后台读写游戏对象；缓冲满需明确背压与落盘状态，不能丢失交易证据。

## 7. 补给与资源：一个账本、一份准备清单

### 7.1 背包不是“满了才整理”

任务准备计算：必需工具、待用材料、预计产物种类及堆叠空间、预计工作长度、恢复需求、交付/献祭保护物品、临时奖励容量。

例如本次钓鱼需要2空格，现有1格：允许把可存鱼获放箱子；食物按预计需要恢复的体力、允许食用范围和携带效率选取，而非每种鱼固定留下2条。售卖和食用都不能消耗已承诺材料。

补给步骤：计算缺口 → 选可达仓库及运输成本 → 生成明确存取清单 → 原生执行 → 重新检查容量与物资 → 恢复原任务。若没有可释放物品、箱子不可达或容量不足，返回可执行替代方案/扩容需求；同一条件下不能反复执行零变化存箱。

不需要补给时可以跳过，但回执只能说“要求已满足”，不能虚报存入物品或新增工作成果。普通整理与为任务准备空间是不同用途，后者不能被“白天背包未满”拦截。

### 7.2 物资与资金核算

可用资源 = 原生实际库存/现金 − 已确认占用。尚未到账销售、预计钓获、机器未来产物不能当作现有资源；NPC在途货物列明可交接时间，不允许玩家立刻消费。

每次预留只属于一个项目；候选方案比较不同时占用全部候选的材料。采集目标使用“需要补足的总库存”和“新增采集数量”两种明确字段，不继续让 `count` 在不同模式下改变意义。

统一流水：申请占用 → 执行前复验 → 按真实消耗结算 → 释放未使用部分。提交异常、取消、部分购买和存档恢复都覆盖；已有数量/品质分配算法继续用。旧模块预算字段可暂时作为展示视图，不能再独立决定可花资金。

### 7.3 出货与材料用途

沿用配方和用途图，但只对已批准项目、持续生产及可解释的近期运营需要形成预留。固定库存只在信息不足时作为明确的兜底策略，不可由多个模块叠加。

出售前同时比较：可售余量、已具备加工产能、加工占用时间、现金需求和下一轮原料。不能无限囤积“以后有用”的材料，也不能为了眼前收入把已批准设备的材料卖掉。

零散低价值出货结合回家/仓储路线合批。当天急需现金与次日才到账的出货要区分；如果允许且有实际价值，评估原生可即时收款的销售途径，不能把出货箱当立即到账。

## 8. 经营规划：把种植、清理、解锁、加工和伙伴接起来

### 8.1 今日机会来自全农场与已知世界

机会包括现有农务、机器收取、动物饲料与照料、成熟和季末期限、采购窗口、任务/信件带来的经营解锁、项目材料缺口、可行钓鱼/采集、扩种和扩产。

程序先计算能不能做、需要多少劳动和钱、何时回款。Flash比较3–5个主要经营方案并可查询其他方向；底层工具入口同样校验条件，模型自由查询不等于允许绕过限制。

领取鱼竿、开启矿洞等按真实进度转换为能力前置。已持有鱼竿即更新获得目标，不能继续攒钱买同一用途的工具。既有NPC收获不能替代Farmer原生任务的步骤，要提前分工，不能事后直接改任务标记。

### 8.2 种植与空间

当前 `FarmEconomyRuntime` 已接分区、通道、水源距离、已有灌溉、成熟期、种子容量和有限加工收益；复用这些计算，不再从“随便选空地”重写一套。

需要统一以下承诺：

1. 主田区、道路、仓储与扩建区跨天保存；已有作物不为新规划强拆。
2. 候选田块先检查整片可准备性和清障成本；先补主田空位，再连片扩展。保护门口、机器操作位、牧草和保留林区。
3. 扩种同时扣除未来每日浇水负担、伙伴可持续劳动量和必要采集/采购时间，不能只看当天还有多少体力。
4. 买种前确定可用田块、预计成熟日、资金和容量；实际播种前复验地图变化。无效部分缩减/重算，已购买种子有库存归属和后续用途。
5. 收益比较以真实可得种子、当前机器容量和回款时间为基础；不能把尚未解锁的酒桶收益算成现有能力。
6. 主仓储选址用住宅、主田和机器间的运输代价；现有箱子搬迁是完整任务，先转存再原生搬运/放置并核验，不能直接改坐标丢失物品。

### 8.3 从开局到持续生产

必须接通三条链，而不只提交一个建造动作：

| 业务链 | 完整执行与反馈 |
|---|---|
| 种植与再投资 | 选种及布局 → 采购/取种 → 清地播种照料 → 收获 → 预留/加工/销售 → 次日核对收入 → 比较补种、工具、灌溉和扩产 |
| 设备生产 | 确认配方与价值 → 准备材料/解锁 → 制作放置 → 原料与燃料供给 → 投料收货 → 原生销售 → 根据闲置/积压调整产能 |
| 畜牧 | 建筑及工期 → 可承担饲料和劳动 → 买动物 → 日常照料 → 收产加工 → 销售与补料 → 满足预算后扩养 |

每一环均列出对应现有执行工具及完成证据；缺工具就登记实现缺口，不能输出“等待玩家”后算自动经营完成。高级链先用专门存档组合验证，正式四天仍保持原生初始条件。

### 8.4 伙伴分工与收工

NPC按已核验能力接任务，派单前计算全天可用劳动和交接收尾能力。玩家和NPC分别领取就绪任务；某角色等待时展示“等材料/额度用尽/能力不足”等原因。不能因为自定义伙伴功能启用，就把闲置伙伴自动算作工作已覆盖。

每日总投入考虑：必要农务、收入与发展机会、工具等级、路径时间和返程风险。评价指标不是把体力耗到0；应指出“仍可做的有价值工作为何未执行”，拒绝无用途清图与明显机会闲置两种极端。

收工由显式决策记录触发。核对必要事项及替代工作的收益后，连续完成返程、上床、原生结算、升级选择、保存。普通采集不打断已批准收工；真正的安全/存档问题可以中断并给出原因。

每阶段本地commit；仅提交相关源码、测试和文档。当前未跟踪的 `mod/Together/ProgressGraph.cs` 不属于本次审查修改，不覆盖、不删除、不顺带提交。

### 迁移方法

先建立契约适配器再逐个接入，避免同时重写所有动作。旧工具名称可以兼容，但兼容层必须生成 `WorkIntent` 并经过统一准入；原生执行器内部子动作沿用租约，无须为每次挥工具重新入经营队列。

**营业约束与新Ready选择必须一起生效。**若先给旧队首补900时间，A02会让早间任务更容易堵住。开发中的新调度可离线比较输出；实机只能有一个调度器执行，不能双写观察效果。

升级保存格式增加版本号。旧未完成任务、旧预算和旧失败哈希先转为待复核，不无条件重放；历史日志继续可读。明确列出各 `Tick*` 迁移后只产生何种需求，最后检查所有自主执行入口。不得长期保留“新内核失败就退回旧自动派单”的隐式回退。

## 10. 集中验收矩阵

开发过程中允许必要编译和静态检查；不每做一个小动作就开一轮真人试玩。功能验证按下表成组进行。纯域测试、适配器组合测试、原生实机测试分别标识，不相互冒充。

| 用例 | 场景 | 必须观察的结果 |
|---|---|---|
| T01 早到商店 | 先提交稍后采购，后提交独立早间农务 | 先做农务，到有效时间再出发；跨工具换参数不能绕过同店约束 |
| T02 真依赖 | 采购失败，队列有播种该种子和独立照料 | 依赖种子的播种等待；独立照料继续；不把整条角色队列判死 |
| T03 关店条件 | 关闭后人物/体力/背包改变；随后到有效窗口 | 无关变化不重复探店；开放后可恢复，今日休息有正确下一窗口 |
| T04 外出所有权 | 钓鱼出行同时出现可选清理 | 清理不能利用子动作间隙召回；只有明确更高优先级事件可改派 |
| T05 容量循环 | 仅1空格、多种少量鱼获、体力充足 | 按需求存货而非每种留2；补给后能续钓，无法释放则明确改派，无零变化循环 |
| T06 地点续接 | Forest作业→Farm补给→继续 | 返回已批准Forest地点；不因当前地图改变捕鱼范围 |
| T07 部分完成 | 要40木材，已有27且伙伴在途若干 | 只补实际剩余缺口；计入交接条件，不追加完整40 |
| T08 收尾与掉落 | 砍树散落、满包、跨片区、暂停恢复 | 跟踪原生掉落，顺路与末尾补捡；可达遗漏不能标完整成功 |
| T09 目标级停滞 | 持续往返但采购/生产毫无推进 | 移动回执不清除该目标的停滞；有条件等待有唤醒点，无子动作循环及时诊断 |
| T10 预算异常 | 提交抛错、部分买到、回执丢失、重载 | 按真实物资/现金对账，释放未用占用，不双买、不虚构现金 |
| T11 身份归属 | 玩家任务需要一次原生收获，NPC负责日常 | Farmer保留并完成必要一步，NPC做其余；物品入账和原生任务分别核验 |

## 11. 日志与四天报告

每条事件至少关联：`save_epoch / run_id / game_time / actor / intent_id / parent_id / phase / decision_id / evidence_id`。按真实用途记录路径和动作，才能回答“为什么又去那里”。

新增必要事件：

- `intent_proposed / admitted / merged / deferred`：来源、用途、被选或拒绝原因。
- `constraint_created / retained / released`：主体、相关条件与实际解除证据。
- `lease_acquired / yielded / resumed`：谁拥有角色，何时允许改派。
- `supply_plan / supply_verified`：要求几空格、实际释放多少、为什么保留某物。
- `resource_held / consumed / released`：材料和资金流，关联原生前后状态。
- `goal_progress / no_progress`：目标变化，不能用动作数替代。
- `route_planned / route_completed`：起终点、用途、实际长度、重算次数、补给绕行；高频位置采样可单独限量。
- `decision_usage / frame_cost`：调用原因、输入输出token、采用单价、延迟；快照/搜索/写盘/计算耗时。

四天报告同时评价：

1. **连续性**：第1天早晨至第5天早晨，4次原生过夜，保存与升级菜单正常。需要人工救场或中途改代码则本轮失败，修复后重新开始干净连续验收。
2. **经营成果**：期初期末现金、已到账销售、采购/建设支出、分类库存、作物及成熟日、设备/动物/建筑、必要解锁。不能把原材料都当利润。
3. **资源利用**：必要照料是否完成、可行工作为何放弃、运输与补给占比、伙伴实际工作、重复访问/重复失败次数。体力剩余单独解释，不设“耗尽才合格”。
4. **模型与系统成本**：每个游戏日的调用和token、哪些调用没有新增信息、卡顿阶段、故障及恢复。

硬性缺陷门槛：已知关闭条件未变化时重复空访为0；同一补给条件无进展死循环为0；重复消耗或误售已承诺物资为0；任何长时间等待均有原因、解除条件和记录。收益门槛需结合选定经营路线与实际回款日事先定义；不能事后只挑有利数字宣称成功。
