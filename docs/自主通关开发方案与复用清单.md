## 1. 目标、顺序和范围

当前主目标调整为：让 DeepSeek Flash 在正常游戏时间下，读取结构化状态和百科，控制一个 Farmer 与一个 Squad NPC，从零经营农场，逐步发展种植、畜牧、加工和后期生产，能够跨季持续经营、获得实际收益并合理再投资。算法负责机械操作、预算计算和恢复；模型负责发展方向、重要取舍、分工与朋友式互动。

**2026-09-20 用户调整优先级：先完整经营，再扩展成就。**成就清单保留为后续能力覆盖和验收参考，不再驱动当前开发顺序。任务、技能、献祭或区域解锁仅在服务经营发展时进入当前计划；不为刷成就打断农务或投入无关资源。此前的已完成代码保留复用，未接入的通用进度图不抢占经营主线。

执行顺序遵循用户要求：**先补齐长期规划和完整操作体系，再集中功能测试，再连续自主经营验收。**开发中的编译和静态检查不作为实机验收，也不在每加一个动作后启动一轮模型试玩。七天只是第一轮连续运行门槛，不是完整通关标准。

- 使用现有 C# 运行架构；Python 保留为开发与验收脚本，不再引入一个必须常驻的规划服务。
- 不依赖视觉、BM25、向量数据库，不加速、不冻结正常游玩时间。
- 算法和数据读取在本地运行；模型使用 Flash，不自动切换 Pro。
- 玩家拥有原生任务和成就身份；NPC 能帮忙，不意味着 NPC 产出必然计入玩家制作、钓鱼、技能、击杀等统计。
- 明确区分：原生成就、平台成就、完美度、剧情/任务、重复委托。它们不是同一个清单。重复生成的任务不能定义成“永远全部清空”。
- 建立当前版本的条目清单；若路线互斥导致一个存档不能覆盖所有目标，显式标记并规划独立 AgentLab 路线存档，不能改标记绕过。是否互斥逐项核对，不凭印象认定。
- 正常游玩用真实操作与原生结果；测试夹具只用于 AgentLab，并与真实开局长程证据分开。
- 本文重点是技术复用。来源链接服务于定位代码和后续迁移，不把“找到源码”写成“已经兼容或接入”。

### 1.1 当前经营主线与完成标准（优先于原全成就顺序）

不是“每天种完就睡”，也不是把农场铺满同一种最贵作物。核心闭环是：**盘点资产和现金 → 比较可行投资 → 采购、生产和照料 → 真实收获、加工与销售 → 收款核账 → 扩大产能或解决瓶颈 → 重算下一阶段。**

经营规划使用同一资源账本与动作队列，不新增一套与现有系统争夺库存和角色的控制器。现有作物布局、多轮现金流、采集补给、仓储、建造和原生机器接口继续复用；“已有动作接口”与“可以自动经营完整产业链”分开验收。

| 优先阶段 | 必须串联的业务 | 完成判据与当前缺口 |
|---|---|---|
| E01 开局与现金周转 | 规划可达地块、按季节选作物、采购、播种照料、收获出货、留种/留料、次日再投资；开局缺钱时选择采集或钓鱼等实际可行收入 | 不能把待结算出货款当现金；按照料能力扩种。已有作物排期基础，自动供给与完整开局经营仍须整合 |
| E02 产能提升 | 比较背包、工具、洒水器、箱子、机器和建筑投入；把实际瓶颈转为材料、解锁与建造计划 | 先算节省的劳动、现金回收期和土地/资源占用；无配方、无材料、无预算时自动准备前置，而非反复尝试同一动作 |
| E03 畜牧经营 | 选择并建造畜舍、购买动物、准备饲料和空间、日常照料、收产品、加工出售、按供料能力扩群 | 购入动物前核对可用容量、施工和饲料；冬季/雨天等情境重新估算供料，不能只实现抚摸与收蛋 |
| E04 加工与酿酒 | 选择有现实供给的加工链，准备/解锁机器，布局放置，备料装机，按原生时间收货，保留周转资金后出售与扩容 | 种植/畜牧原料数量与机器吞吐量匹配；持续缺料或积压时调整投资，不因单件售价高就全部囤去酿酒 |
| E05 跨季与后期发展 | 季末收尾、次季资金/种子/用地安排、温室及经营需要的后期区域、长期稳定生产线、存档重载后的续作 | 经营目标根据实际解锁与瓶颈推进；跨季维持供给和现金流。不能把七日农务成功当作从零到后期完成 |

本批实现、实际验收范围与日志入口见 [经营自动化实现与运行记录](经营自动化实现与运行记录.md)。工程子项与完整产业链验收分开勾选。

实施清单（以下为尚未整体完成的业务链，子工具已完成不自动勾选）：

- [ ] E01 自动开局、农务闭环与真实收入再投资。
- [ ] E02 统一投资候选、成本/回收期/劳动容量比较及前置准备。
- [ ] E03 畜舍建设到购买、供料、照料、产物处理的完整链。
- [ ] E04 原料生产到设备制造/放置、连续加工、销售和扩容的完整链。
- [ ] E05 季节转换、经营必需解锁、后期生产与跨日/读档续接。
- [ ] E06 将以上业务链合并进行功能验收，再从真实开局连续经营并验证跨季与后期发展。

算法负责的经济计算：

- 收益分别记为已到账现金、待结算出货、原料库存、在制品和固定资产，避免重复计算财富或使用未到账的钱。
- 比较直接出售与加工后的增值，同时扣除原料的出售机会成本、购买成本、燃料、加工时间和来回操作劳动；自采材料也有用途与时间成本。
- 将种植数量、动物数量、饲料供给、机器产能、仓储容量和角色每日劳动预算联算；瓶颈决定扩建方向。
- 考虑现金周转和回收期：初期保证能买下一批种子/饲料，后期逐步投资回收较慢但稳定的生产设施。不得只追求账面库存价值。
- 在真实可用地块上布置通道、灌溉与设备；保护既有设施和保留区，新增面积必须能够到达、照料和收获。
- 先分区再选田：门前院子、建筑操作缓冲和服务道路为硬性禁种区；在剩余区域规划紧凑田块，先清完整块障碍，再翻土、播种和浇水。洒水器中心留空，不能因矩形约束丢掉周围有效覆盖。长期畜牧/加工/扩建总图仍单独验收，详见经营运行记录。
- 用已知的季节、营业时间、配方与游戏数据筛选方案，未知价格、天气和随机产出分别标注；未来方案按实际结果逐日重算，不声称全局最优。
- 每日维护先进入独立角色队列；一个角色结束后续领工作，不等待另一个角色。普通补水、进食、存取、再装机和已批准的采购由算法完成。

Flash 只在经营方向或重大取舍上决策，例如优先扩种还是建畜舍、是否投入酿酒链、是否推进温室解锁；它可以主动查询账本和百科解释选择。预算范围内的常规维护与已批准生产不逐动作请求模型。玩家临时要求同行或休闲时，调度保存生产安排并按时效协商，而不是永久变成无条件刷钱脚本。

集中验收同时检查：实际净现金变化、必要维护完成率、有效劳动与空闲原因、作物/饲料/原料断供、机器闲置与积压、扩建前后的实际产能、跨季损失、恢复与人工介入次数。对“收益高”的判断在相同日期、地图、初始资源和正常时间条件下比较现有策略基线，不用作弊加速、额外物资或账面估值证明进步。

## 2. 调研方法与结论

本轮通过 Exa 进行了 6 组成功搜索，共返回 30 条候选结果（有重复），再通过作者仓库、GitHub 文件和 API 文档核对关键实现；并检查本地源码、提交历史和已有验收文档。搜索结果只是发现线索；下表区分源码检查、作者说明和待验证内容。

技术复用分三种：

1. **原地复用**：本项目已经接入或已有代码，直接扩展，不重新移植旧提交。
2. **提取后适配**：迁移明确的纯算法、数据解析和规则，接入现有执行器与回执。
3. **可选集成/参考**：上游控制不同角色、改变游戏操作方式、依赖过重，或只有产品说明，不能直接当现成能力。

## 4. 统一架构和动作契约

```text
原生世界快照 + 事件 + 百科规则
                 ↓
经营目标与生产依赖 + 资源账本 + 农田/经济排期
                 ↓
可行方案 → Flash 选择目标、策略和分工
                 ↓
独立双角色队列 → 连续技能状态机 → 原生游戏操作
                 ↓
结果核验 → 更新账本/记忆 → 继续下一项或触发重规划
```

每个技能统一具备：`capabilities`、前置条件、角色/资源/地块占用、预算、执行阶段、可取消点、部分完成、结果核验、恢复策略。任务有 `command_id`、`idempotency_key`、`save_epoch`、`plan_revision`，防止模型重试或读档后重复买卖、制作、交付。

建议返回字段：`status`、`phase`、`actual_progress`、`resource_delta`、`native_progress_delta`、`stop_reason`、`retryable`、`resume_token`、`evidence_ids`。收到命令、动画结束、物品消失均不是独立的完成证明。

- 游戏对象只在主线程读取/修改。规划在不可变快照上计算，后台不能持有实时 Game1 对象。
- 执行前重验快照版本、目标、成本和权限；已经变化的地块/价格/库存触发局部重排。
- 统一暂停入口取消执行权并保留实际进度；模型返回晚到时不得恢复已暂停角色。
- 每个角色只由一个执行器控制；自主生活、玩家命令、工作和战斗共用调度。
- 输入合法但缺能力时返回明确缺口；不把所有异常交给模型无限尝试。

| F27 | 无进展检测、恢复预算、配置版本、重载去重、控制权交还 | 无法局部恢复时改目标 | 保留现有 session/queue/reply guards，补完整链路 |

完整覆盖的做法：将 F22 枚举得到的每个原生目标连接到 F01–F27 的具体步骤和核验器。未匹配目标自动进入缺口清单；“有通用 interact”不能自动把所有 NPC、建筑和剧情标为支持。

## 6. 种植规划：明确种什么、种多少、种在哪里、何时种

### 6.1 空间和经济分开计算

空间层产出可操作的地块方案，经济层产出种子/肥料/播种日/收获日/预算方案；二者互相约束。最大利润计算器不懂农场堵路，地图摆放器也不懂现金流，不能只装其中一个。

初版以当前季剩余日期和必要跨季作物为窗口，日末滚动更新；遇任务期限、购买节日、设施升级等关键事件才扩大窗口。输出是有预算的近似可行解，不宣称数学全局最优。

### 6.2 地块选择流程

1. 从真实地图建立网格：可耕、可通行、水源、现有作物/肥料、树木、建筑、出口、箱子、机器、洒水器、稻草人、已保留区域。
2. 排除不可种、未经授权清理、建筑门口、交通节点和保留用地；现有成熟多年作物/果树/设备不能因为布局分数低就拆掉。
3. 以屋门、箱子、水源和已有农田为锚点，按**真实路径长度**计算工作成本。不能用直线距离把隔着水或围栏的地算成最近。
4. 生成紧凑连通的候选块；已有农田优先、邻接扩展其次，只有收益足够时才开另一片。清理成本和每天补水往返都计入。
5. 按实际洒水器类型与升级后的有效格子生成候选覆盖，不硬编码所有机器都是 3×3；读取地点限制、设备是否可用，记录首次生效时间。今天新放的设备不能被假定已经完成今天浇水。
6. 洒水器/稻草人选择使用带成本的覆盖贪心，再做局部移动/替换；先满足已种地块，减少重复覆盖和无效覆盖。没有设备时按手工照料预算缩小种植规模。
7. 架子作物必须在**未来被占用后的地图**中验证每株至少有一个可达交互站位；不能种成密实方块堵死内部。普通作物是否需要通道按碰撞规则判断，不一律浪费一格做道路。
8. 检查角色从入口可达每个必要交互点、箱子、水源和出口；规划失败返回冲突格及替代布局。
9. 根据未来建筑、果树生长、巨型作物等已选目标保留特定空间；这些是条件化布局模板，不是默认把整个农场强制铺满。
10. 输出有版本的 `FarmLayoutPlan`：格子用途、种子/肥料、灌溉与保护覆盖、通道、清理清单、预估工作量、未用地原因。界面可预览，模型拿摘要和方案 ID。

### 6.3 作物与排期算法

输入来自游戏已加载数据和现有百科：种子实际可获得途径/价格/库存、当前地点生长条件、成长阶段、复收、肥料和职业影响、已有地块、预算、任务/献祭/烹饪/出货缺项、工具和两角色每日劳动能力。

约束包括：

- 每日资金不得低于保留金；购物/建造/升级已有预留不可重复支出。种子在背包或箱中则计实际库存，不能重复购买。
- 每个时段种植数受合法地块、播种耗时、每日浇水/收获负担、补给和角色其他任务限制；NPC 没有 Farmer 原生体力条，用其实际能力与耗时约束。
- 成长日期按实际机制和生长夜晚计算，包含肥料/职业/地点、复收、跨季、缺水情况；不能用一个随意的“总天数减百分比”代替分阶段取整规则。
- 今天收获、今天补种、店内现卖与次日出货到账分别建模，避免提前花未来收入。
- 时间受限的任务作物先满足下限，再给现金作物/经验/收藏分配剩余土地；需要特定品质的产物用概率和备选余量，不能保证一定产出。
- 加工利润受真实机器数量、工时、燃料、原料、销售时间限制；没有桶不能按酒价算全部收成。
- 商店休息、限定购买窗口、路线和到店时间限制真实可买种子；未知未来天气不当作必然降雨。
- 混合种子等随机产物不能计作某个指定目标的确定数量；随机掉落与产量使用保守区间。

先移植 C# planner 的排期/现金流结构，结合 Stonks 的复收、肥料、跨季规则。对支配劣势方案剪枝：相同完成效果下更贵、更费工、更晚且无其他收益的方案淘汰。对不同地块和资金进行受控分桶，用有限宽度搜索保留候选，再用真实约束回验和修复；不能把取整近似方案直接执行。

优先级采用分层目标：**硬约束可行 → 到期目标和农场维护 → 选定发展目标 → 资金/经验收益 → 路线与操作成本 → 布局稳定性。**收益权重由策略决定，不能为了多赚一点把承诺和任务全部挤掉。

返回最多三套差异明确的方案，例如省体力、推进收集、资金增长；Flash 选择后执行器按地块走完“备料→清理→翻土→施肥→播种→补水/浇水→核验”，同一方案内不再逐株问模型。若只有一个可行方案且符合已有策略，直接继续。

### 6.4 性能与变更

地图索引按事件增量更新；发生建筑、对象、地形或移动障碍变化时局部失效。规划使用不可变快照和可取消后台计算；默认候选数、搜索宽度、内存与时间均有限。先设 1 秒左右的规划时间预算作为待测配置目标，超时返回最好的已回验可行方案，不在游戏主线程穷举、不承诺该性能已实现。

临时障碍只重排当前路线；种子不足或价格变化只调整有关批次；扩建/换季等再重算区域。保留已做劳动，避免每天重新开地。

## 7. 记忆、压缩与模型调用

### 7.1 已有能力与明确不足

已有 `AgentContext` 的去重、回执摘要；`MemoryRecall` 的话题/近期排序；`Social.CloseDay` 的真实事件日记。**这些不是一个已经完整的长期记忆压缩系统。**当前 `AutoplayDomain` 日志超过 32 条直接裁剪，经历超过 120 条裁剪，日记保留 28 条，聊天/记忆文本也有限长；若只增加模型上下文，并不能避免丢失长期事实。

复用这些入口，补“归档后再裁剪”和明确的层次，不重新装另一套记忆服务。

### 7.2 四类数据和保留规则

| 层 | 内容 | 压缩/存储方式 |
|---|---|---|
| 事实账本 | 当前库存、资金、任务、解锁、关系、地块、在制品 | 原生快照/结构化表；日期数量不交模型概括；可重读的状态只保留版本和差异 |
| 当前计划 | 目标依赖、任务状态、分工、材料预留、承诺、失败阻碍 | 持久化结构；未完成/未解除的承诺不因窗口满被删除 |
| 事件与经验 | 操作结果、失败码、替代方式、成功次数、适用条件 | 按日追加本地记录，索引 goal/entity/actor/location/skill；原始证据可按 ID 查，不塞整条轨迹 |
| 关系与叙事 | 玩家偏好、共同经历、聊天主题、朋友自己的目标 | 保留有依据的事实和来源 ID；日摘要→季摘要；表达可由模型润色，不允许改事实 |

所有记录绑定 `save_id + farmer_id + companion_id + timeline_epoch`。读旧档或测试重置后，不能把未来取得的物品、关系、目标进度当成现在已经发生。

### 7.3 压缩过程

1. 高频移动/工具事件先合并为同一任务的阶段与实际累计结果；不保存每帧到模型上下文。
2. 完成/失败/取消产生结构化摘要，包含剩余数量、原因和证据 ID。重复错误合并次数，不重复全文。
3. 日结束计算真实收支、关键进度、未完成目标和明日限制；先用模板生成，无需每天额外付费总结所有日志。
4. 保留稳定偏好、承诺和重要关系事件；普通重复劳动转为统计。热缓存满前写入归档，不能只 TakeLast 然后遗忘。
5. 只有有新且重要的关系内容、或确需归纳长对话时，才调用 Flash 生成叙事摘要；结构化事实与来源不变，无法核验的内容不写事实账本。
6. 摘要保存 `source_ids/covered_until/schema_version`；按版本原子替换，保留可回溯上一版。禁止不断“摘要的摘要”后丢失来源。
7. 失败经验带工具版本、地图条件、日期和失效条件。例如商店关门不是永久不可买，昨日障碍不是今天永久不可达；条件改变即可重新尝试。

检索先按存档、实体、目标、技能过滤，再按相关性、重要度、时效和未解决状态排序。中文俗称仍使用现有别名/模糊规则，不新增 BM25/嵌入模型。SPIKE 的状态—动作—结果图可压成轻量邻接表；不用向量服务也能按离散前置条件找到经验。

### 7.4 上下文预算与触发器

模型输入按“当前目标/约束→必要世界差异→两角色队列→直接相关知识→相关记忆→未解决错误”装配。固定工具说明继续复用缓存前缀，按任务暴露相关工具组，避免每轮发送全技能说明。

初始预算建议（配置值，待集中验收调优）：动态上下文软目标 6–10k token；必须保留当前任务、承诺、失败原因和资源约束。达到上限时削减旧叙事/无关状态，完整事实通过有界分页工具查询；不能截断 JSON 或用字符数冒充准确 token。API usage 用于实际计费复核。

模型唤醒：首次设目标、早晨需要调整计划、重要解锁/期限变化、所有合适工作用尽、无法局部恢复、玩家新指令、需要表达/协商。子动作完成、补水、卸货、进食、普通确认、领取队列下一项都不调用。

空闲角色先执行已批准队列/条件规则；只为该角色缺少工作时请求必要重规划，不能等另一角色结束。错误通知去重，模型请求在途期间合并事件，迟到回复重验 revision。API 失败时仅继续已批准且仍然有效的动作，必要恢复/回家按已定策略处理，不擅自扩大目标。

“喜欢钓鱼”保留为朋友自身偏好；在自主通关模式中通过共同策略与任务预算协调，在陪伴模式中提高个人活动与聊天权重。两种模式共用事实和动作，不能各运行一套互抢控制权的 Agent。

| 组合场景 | 一起覆盖的能力 | 关键证据 |
|---|---|---|

动作自然性单独检查：移动、转向、挥工具、打击结算、收尾和中断恢复；成功回执不能证明画面流畅。程序按动画/原生时点结算；必要时录像检查表现，录像不作为模型观察输入。

平台成就需要实际平台环境验证，开发启动未连接 Steam 时只报告存档原生进度。完整成就与朋友体验分别验收：前者证明执行与规划能力，后者还需自主偏好、互动、记忆和共同经营的长期试玩。
