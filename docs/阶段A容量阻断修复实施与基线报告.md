## 3. R-A1：统一模型及原生制作结果

`CapacityModel.cs` 不引用游戏类型：`StackKey`、`CapacitySnapshot`、`TakeOp`、`PutOp`、`RequireFreeOp` 和 `CapacityPlan.Simulate`。逐步核验，失败指出步骤；原始快照不变；单操作失败不保留部分模拟写入；峰值占用包含初始占用。扣料按原生逆序扫描背包。

## 4. R-A2 与 R-A3

`CapacityRelief.cs` 是纯候选筛选；`CapacityReliefRuntime.cs` 生成可审计操作序列，先整理堆叠，再评估已批准机器投料/交付/制作、单份可用补给、仓储和预算内造箱。缺料、未批准、没有有效站位、不能净腾格等分别记录排除原因；不能递归调用下一层腾格。

生产候选来自已经批准且依赖满足的队列。算法不会新造一个生产项目；多批制作作为腾格候选目前要求拆为已批准单步，普通连续制作仍支持多批。补给只考虑单件、可食用、非任务/献祭/预留物，且确有体力恢复价值。出售与背包升级只返回需显式授权的理由，由批准的原生交易任务执行，不能由算法自行购买/出售。

`CapacityConstraints.cs` 与 `CapacityConstraintRuntime.cs` 把根因按行动者保存。版本指纹不含日期、时间、体力、任务 ID；包括库存、可用仓储、保护需求、已批准用途。相同用途重提不应因新任务 ID 自动释放约束。前置预测仍可行的动作（例如消耗腾格制作）不被“存在容量约束”一刀切禁止。

`native-constraints/` **实测**：

1. 真实满包，创建容量根因约束，Version=1。
2. 收获、觅食两个不同工具请求被同一根因拦截。
3. 真实回床→原生保存→次日，库存未变，Version 仍为 1，约束保留。
4. 原生制作/放置箱子、卸货后，Version=2，约束清除。
5. 该检查用到的原存档先备份到其证据目录，未改材料、钱或日期。

错误码与 `RecoveryPolicy` 的等待分类同步；容量不再作为每个工具独立的六次错误。**但这不等于消除了重复派单：基线证明存货入口仍绕过根因阻拦，详见第 7 节。** 瞬时异常仍按原有机制恢复。旧 Squad 货袋相关分支保留，不以玩家端收敛冒充 D6 迁移完成。

### 7.2 阻断一：根因已经统一，但同根因动作仍被豁免（实测＋代码）

### 7.3 阻断二：种植目标与所调用工具不一致（实测；后续设计待讨论）

06:30 的队列中，模型命名为 `till-parsnip` 的任务实际是 `work.run(goal=cleanup)`；命名为 `plant-parsnip` 的任务实际是 `work.run(goal=harvest)`。

两条回执均为零生产进展：前者 `cleanup_yield_to_production`，后者 `all_current_targets_completed`，`Completed=0`、`BusinessProgress=false`，并有 `no_effect_action` 日志。调度状态仍为 `succeeded`，仅表示请求处理结束。它们**不能证明翻土或播种成功**，本次质量账本也没有给这些无效果请求增加种植记录。

现有真实种植接口是 `farm.plan` 返回 `plan_id`，再 `work.run(goal=plant,plan_id=...)`；`SemanticWork.cs:144–146` 会检查该方案。核心工具简版 `AgentToolDiscovery.cs:10` 对 plant 只要求先查完整定义；本轮模型并未稳定遵守这个流程，后来仍提交不带 `plan_id` 的 plant 请求。

因此，不能声称仅修复容量就能自动恢复经营。已有工具契约、目标完成判定和下游依赖如何消费“零效果成功”，仍需合并审查；不应把名为“播种”的任务完成状态当成播种证据，也不能在后台把模型调用悄悄改成别的操作。
